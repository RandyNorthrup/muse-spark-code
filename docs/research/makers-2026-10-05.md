# M103 research and plan draft — Makers: boards, firmware and machines

Draft for the lead, 2026-10-05. Research and design only: no repository
change, no commit, no model or paid call was made. Code facts were read with
`git show` / `git grep` from `origin/main` (`8c894b60`, 0.13.0 plus #121)
and `refs/remotes/kubuntu/m95/int` (`d323028a`, the M95 providers
integration); the M100 plan from `refs/remotes/kubuntu/feature/m100-multi-device`.
Web facts carry their URL; anything not confirmed says "unverified".

The owner asked (2026-10-05): "is there anything we can include that will
make this harness have useful features for creators and tinkerers ie people
who program raspberry pi or esp32 or like robotics and cncs and 3d printers
etc?"

Short answer: yes, and most of the value is cheap. Makers mostly need
knowledge, a build → flash → watch → simulate loop that ends on its own, and
an assistant that can read the board or machine without any chance of
moving it unasked. Our permission engine is the thing that sets us apart:
no competitor found puts a hard, per-action, unbypassable human approval
between a model and a heater or a spindle. The hazards section (§3) matters
as much as the features: our shell tool can already flash a board or send
G-code today, and Bypass runs it.

The owner added a rule while this draft was written (2026-10-05): "all of
the editors should have equivalent functionality even if we need to develop
it ourselves". D83.16 therefore puts every maker feature in the portable
engine, the runtime and the shared React UI, and carries an editor matrix,
including the editors makers use most (Arduino IDE 2, PlatformIO, Thonny,
the Espressif IDE).

## 2. Findings with links

Checked 2026-10-05. "Unverified" marks what could not be confirmed on a
primary page; "secondary" marks a third-party source. Two read-only
PowerShell probes were run on the host PC (marked "checked on the host").

### 2.1 Microcontroller toolchains

**PlatformIO**

- A project is a `platformio.ini`
  (https://docs.platformio.org/en/latest/integration/ide/vscode.html).
  `pio` is often not on PATH: `~/.platformio/penv/bin/pio`,
  `%USERPROFILE%\.platformio\penv\Scripts\pio.exe`
  (https://docs.platformio.org/en/latest/core/installation/shell-commands.html).
- `pio device list --json-output` gives `port`, `description` and `hwid`
  (`USB VID:PID=10c4:ea60 SNR=0001`)
  (https://docs.platformio.org/en/latest/core/userguide/device/cmd_list.html).
- `pio device monitor` has `--rts`/`--dtr` (the initial line state), `--raw`,
  `--quiet` and filters, and **no timeout option**
  (https://docs.platformio.org/en/latest/core/userguide/device/cmd_monitor.html).
  - Piped stdin crashed it (issue #5113); fixed in Core 6.2.0
    (https://github.com/platformio/platformio-core/issues/5113,
    https://docs.platformio.org/en/latest/core/history.html).
  - SIGINT did not always end it (https://github.com/platformio/platformio-core/issues/3841).
  - So bound it with our process-tree kill, never a key.
- `pio run -t upload|uploadfs --upload-port`
  (https://docs.platformio.org/en/latest/core/userguide/cmd_run.html).
- `pio test --json-output-path` with Unity, GoogleTest or Doctest; `-e native`
  runs on the host
  (https://docs.platformio.org/en/latest/core/userguide/cmd_test.html).
- `pio check --json-output --fail-on-defect` (Cppcheck by default)
  (https://docs.platformio.org/en/latest/core/userguide/cmd_check.html).
- The PlatformIO IDE extension is not on Open VSX: it hard-depends on
  Microsoft's C/C++ extension (https://github.com/VSCodium/vscodium/issues/637).
  The `pioarduino-ide` fork is on Open VSX (secondary,
  https://community.platformio.org/t/platformio-in-cursor-publication-to-openvsx/48602?page=2).
  Our users in forks may therefore have the `pio` CLI but no IDE extension.
- There is no official PlatformIO AI or MCP (absence unverified). Community
  MCP servers:
  - https://github.com/powerdragonfire/platformio.mcp (29 tools: build,
    flash-then-verify, monitor sessions, crash decoding);
  - jl-codes `platformio-mcp` v2
    (https://community.platformio.org/t/launched-platformio-mcp-server-v2-antigravity-claude-codex-cline/54105).

**Arduino**

- arduino-cli is at v1.5.1, released 2026-06-05
  (https://github.com/arduino/arduino-cli/releases).
- The global `--json` flag arrived in PR #2587; `--format json` is still
  accepted (https://github.com/arduino/arduino-cli/pull/2587).
- `board list` returns `detected_ports[].port{address, protocol,
properties{vid,pid,serialNumber}}` plus `matching_boards[]{name,fqbn}`
  (https://arduino.github.io/arduino-cli/1.0/UPGRADING/).
- `upload` does not compile first
  (https://arduino.github.io/arduino-cli/1.5/commands/arduino-cli_upload/).
- `monitor` has no timeout flag
  (https://arduino.github.io/arduino-cli/1.5/commands/arduino-cli_monitor/).
  **With stdin closed it reads EOF and exits after about 1.2 s with no
  output** (https://github.com/hardware-mcp/arduino-mcp-server/issues/13).
  Our shell tool leaves stdin closed (`src/host/backend/toolIo.ts`: "ordinary
  shell tools leave stdin closed"), so the skill's bounded recipe must keep
  stdin open, e.g. `sleep 10 | arduino-cli monitor …` on POSIX. Lane S
  checks every monitor recipe against a socat port.
- Arduino IDE 2 is Theia/Electron over an arduino-cli daemon, with no AI
  (https://github.com/arduino/arduino-ide).

**ESP-IDF**

- How to detect a project: `CMakeLists.txt` with
  `include($ENV{IDF_PATH}/tools/cmake/project.cmake)`, plus `sdkconfig`,
  `sdkconfig.defaults`, `main/`, `idf_component.yml` and `dependencies.lock`
  (https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/build-system.html).
- **idf.py monitor**
  (https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/tools/idf-monitor.html):
  - It resets the target over DTR/RTS on connect unless `--no-reset` or
    `ESP_IDF_MONITOR_NO_RESET` is given.
  - `--print-filter` takes `tag:L` pairs; `--timestamp-format` is available.
  - Ctrl+] ends it.
- **When stdin is not a TTY, esp-idf-monitor takes commands from stdin**
  (`reset`, `expect [--timeout s] <regex>`, `send`, `exit`, …). Its README
  example is `printf 'reset\nexpect --timeout 10 ALL TESTS PASSED\n' | idf.py
monitor` (https://github.com/espressif/esp-idf-monitor/blob/master/README.md).
  This gives a bounded run that exits on success. The version that added it
  is unverified.
- **esptool v5** (https://docs.espressif.com/projects/esptool/en/latest/esp32/migration-guide.html):
  - The command is `esptool`; the `.py` name is deprecated.
  - Subcommands use dashes (`chip-id`, `read-mac`, `write-flash`); the
    underscore forms still work with a warning.
  - Reset control is `--before default-reset|no-reset|…` and
    `--after hard-reset|no-reset|…`. **The guard table must match both
    spellings.**
- `idf.py mcp-server` (ESP-IDF v6.0+, 2026-04-28) is a stdio MCP server:
  - tools `set_target`, `build_project`, `flash_project`, `clean_project`;
  - resources `project://config|status|devices`;
  - no monitor;
  - approval is left to the MCP client
    (https://developer.espressif.com/blog/2026/04/esp-idf-tools-mcp-server/).

  It is a **physical** MCP server by D83.4.

- The ESP-IDF VS Code extension:
  - contributes a `#espIdfCommands` chat tool and registers Espressif's docs
    and component-registry MCP servers
    (https://docs.espressif.com/projects/vscode-esp-idf-extension/en/latest/additionalfeatures/language-tools.html);
  - has eFuse, NVS and partition editors, OpenOCD and QEMU
    (https://docs.espressif.com/projects/vscode-esp-idf-extension/en/latest/);
  - since v2.1.0 runs its installer over SSH, Dev Containers and WSL
    (https://developer.espressif.com/blog/2026/05/esp-idf-vs-code-extension-v2-1-0/).
- Espressif's web extension flashes over WebSerial/WebUSB in VS Code Web and
  Codespaces only, not desktop
  (https://docs.espressif.com/projects/vscode-esp-idf-extension/en/latest/additionalfeatures/web-extension.html).

**ESPHome** (Home Assistant devices)

- `esphome run` validates, compiles, uploads and shows logs; `esphome
upload` uploads the last build.
- `--device` takes a serial port, or an IP address for an OTA update
  (https://esphome.io/guides/cli/).
- So a network address can be a _program_ target: the guard and the flash
  identity check cover OTA hosts as well as ports.

**MicroPython, CircuitPython and the Pico**

- **mpremote** (https://docs.micropython.org/en/latest/reference/mpremote.html):
  - `connect list` (or `devs`) prints text columns (port, serial, VID:PID,
    manufacturer, product); no JSON.
  - `fs cp` marks device paths with `:`.
  - `run` executes a local file from RAM; `exec`, `eval`, `mount`,
    `soft-reset`.
  - `repl` ends with Ctrl-] or Ctrl-x.
- The raw REPL and raw-paste protocol are documented and could be spoken
  from TypeScript over any byte stream
  (https://docs.micropython.org/en/latest/reference/repl.html).
- ampy's last release was 2021 and it is dormant
  (https://pypi.org/pypi/adafruit-ampy/json).
- **CircuitPython** (https://docs.circuitpython.org/en/latest/docs/workflows.html,
  https://docs.circuitpython.org/en/latest/shared-bindings/supervisor/index.html):
  - The CIRCUITPY drive is writable by the host and auto-reloads `code.py` on
    a write.
  - **Opening the port at 1200 baud and closing it reboots the board into its
    bootloader.**
  - `boot_out.txt` names the version and the board
    (https://github.com/adafruit/circuitpython/issues/10717).
- **CircuitPython's web workflow**
  (https://docs.circuitpython.org/en/latest/docs/workflows.html):
  - `CIRCUITPY_WEB_API_PASSWORD` in `settings.toml` turns it on.
  - It serves `/fs/` (GET/PUT/MOVE/DELETE, HTTP Basic auth), `/cp/*.json`
    and a `/cp/serial/` WebSocket at `circuitpython.local`.
  - A write returns 409 while USB is mounted.
  - A PUT there is a _program_ action.
- **MicroPico** 4.6.1 ships one universal VSIX but depends on `serialport`
  with the native `@serialport/bindings-cpp` prebuilds
  (https://raw.githubusercontent.com/paulober/pico-mpy-com/main/package.json).
  It needs VS Code 1.137+ and has no Windows arm64 build
  (https://github.com/paulober/MicroPico).
- **The official Raspberry Pi Pico extension** handles the SDK and toolchain,
  CMake/Ninja, picotool and OpenOCD (https://github.com/raspberrypi/pico-vscode).
  picotool uses libusb and needs WinUSB via Zadig on Windows
  (https://github.com/raspberrypi/picotool).

### 2.2 Serial access without a native module

**Node and VS Code**

- `@serialport/bindings-cpp` is a native N-API module with per-platform
  prebuilds and a node-gyp fallback
  (https://serialport.io/docs/guide-installation). We reject it (§9).
- Microsoft's Serial Monitor extension exports `listAvailablePorts`,
  `startMonitoringPort` and `stopMonitoringPort`. The returned `Port` has
  only `stopMonitoring()` and `onClosed`, so **no other extension can read or
  write through it** (https://github.com/microsoft/vscode-serial-monitor/blob/main/api.ts).
  The repository is archived (https://github.com/microsoft/vscode-serial-monitor).
- Eclipse CDT's "Web and Desktop Serial Monitor" 2.0.0 uses `serialport` on
  desktop and WebSerial in the browser, and is `extensionKind: ui`
  (https://raw.githubusercontent.com/eclipse-cdt-cloud/vscode-serial-monitor/main/package.json).
- **Web Serial:**
  - VS Code Web has `workbench.experimental.requestSerialPort` for web
    extensions and webviews (https://github.com/microsoft/vscode/pull/152310).
  - It is not Baseline in browsers
    (https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API).
  - Desktop webviews have no documented support (unverified); Electron needs
    a main-process `select-serial-port` handler
    (https://github.com/electron/electron/issues/22478).
- **Remote windows:** "extensions that access locally attached devices will
  be unable to connect to them when running remotely"; the fix is a
  companion UI-side extension
  (https://code.visualstudio.com/api/advanced-topics/remote-extensions).

**POSIX**

- `stty -F` (GNU) or `stty -f` (macOS) with `raw -echo`
  (https://man7.org/linux/man-pages/man1/stty.1.html). stty itself asserts
  DTR on open, even with `-hupcl`
  (https://lists.gnu.org/archive/html/bug-coreutils/2017-01/msg00018.html).
- An Uno resets on every software connection
  (https://store.arduino.cc/products/arduino-uno-rev3). ESP32 boards may be
  held in reset by RTS/DTR on open
  (https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/boot-mode-selection.html).
- **Node `fs` reads on a blocking character device occupy a libuv thread,
  cannot be cancelled and can keep the process alive**
  (https://nodejs.org/api/fs.html). So our POSIX fallback reads through a
  child process under the existing process-tree kill, never `fs.read` in the
  extension host.
- pyserial is the better POSIX helper where Python is present: it sets DTR
  and RTS, and esptool and PlatformIO already install it
  (https://raw.githubusercontent.com/espressif/esptool/master/pyproject.toml,
  https://raw.githubusercontent.com/platformio/platformio-core/develop/platformio/dependencies.py).
  `python -m serial.tools.list_ports -v` lists ports
  (https://pyserial.readthedocs.io/en/latest/tools.html).
- On macOS use `/dev/cu.*`, since `/dev/tty.*` waits for carrier (secondary,
  https://pbxbook.com/other/mac-tty.html).
- On Linux `/dev/serial/by-id/…` gives stable names (secondary,
  https://www.marcusfolkesson.se/blog/naming-your-serial-ports/).
- Native-USB ESP chips vanish from the host in deep sleep and re-enumerate
  (https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/usb-serial-jtag-console.html).

**Windows**

- `SerialPort` is in `System.dll` on .NET Framework.
  `GetPortNames()` reads `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM` in no fixed
  order and can return stale entries
  (https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.getportnames).
- PowerShell 7 ships `System.IO.Ports.dll` as well
  (https://raw.githubusercontent.com/PowerShell/PowerShell/master/src/Microsoft.PowerShell.SDK/Microsoft.PowerShell.SDK.csproj).
  Checked on the host: pwsh 7.6.6 loads it and `GetPortNames()` works.
- Checked on the host:
  `Get-CimInstance Win32_PnPEntity -Filter "PNPClass='Ports'"` lists
  "… (COMn)" names with device IDs. **Bluetooth serial ports (`BTHENUM\…`)
  appear too and must be filtered out.**
- So the `jobBuild` C# helper (D83.13) needs nothing that is not already on
  every supported Windows.

**USB IDs** (https://raw.githubusercontent.com/usbids/usbids/master/usb.ids)

- USB-serial chips: `10c4:ea60` CP210x, `1a86:7523` CH340, `0403:6001`
  FT232 (also 6010/6014/6015).
- `2341` Arduino (`0043` Uno R3, `8036` Leonardo); `239a` Adafruit.
- `303a` Espressif (https://github.com/espressif/usb-pids), with `303a:1001`
  the native USB-Serial/JTAG unit.
- `2e8a` Raspberry Pi (https://github.com/raspberrypi/usb-pid):
  - `0003` RP2040 boot;
  - `0005` MicroPython;
  - `000a` Pico SDK CDC;
  - `000c` Debug Probe;
  - `000f` RP2350 boot.

**Virtual ports for tests**

- socat `PTY,link=…,raw,echo=0` pairs (https://linux.die.net/man/1/socat).
  Linux ptys do not reliably support the DTR/RTS line-control calls, so they
  test the data path only, not resets (secondary,
  https://github.com/Br1Red/modem_simulator).
- tty0tty is a kernel module and needs a rebuild per kernel
  (https://github.com/freemed/tty0tty).
- com0com 3.0.0.0 dates from 2017. Windows 11 users report Code 52 and fall
  back to the signed 2.2.2.0 x64 build
  (https://sourceforge.net/p/com0com/discussion/440109/thread/ef3d18924d/).
  Whether it loads under Secure Boot is unverified, so it is optional on the
  Win11 VM and never in CI.

### 2.3 3D printers

**Klipper and Moonraker**

- **Limits in `printer.cfg`** (https://www.klipper3d.org/Config_Reference.html):
  - `max_velocity` and `max_accel` are required, and `SET_VELOCITY_LIMIT`
    can change them at runtime.
  - `position_min` and `position_max` are set per stepper.
  - Extruder and bed `min_temp`/`max_temp` are required; the MCU shuts down
    outside them.
  - `[verify_heater]` is on for every heater by default.
  - `[force_move]` is off by default; FORCE_MOVE and SET_KINEMATIC_POSITION
    "may place the printer in an invalid state".
- Moving before homing fails with "Must home axis first"
  (https://github.com/Klipper3d/klipper/blob/master/klippy/kinematics/cartesian.py).
- **Live limits** come from `toolhead.axis_minimum`, `axis_maximum`,
  `homed_axes` and `max_velocity`, and `configfile.settings`
  (https://www.klipper3d.org/Status_Reference.html). D83.6 reads these
  rather than parsing files.
- **Moonraker endpoints** (https://moonraker.readthedocs.io/en/latest/external_api/printer/):
  - GET `/printer/info`, `/printer/objects/list`;
  - POST `/printer/objects/query`;
  - POST `/printer/gcode/script`, `/printer/emergency_stop`,
    `/printer/restart`, `/printer/firmware_restart`;
  - `/printer/print/start|pause|resume|cancel`;
  - a JSON-RPC websocket at host port 7125, path `/websocket`, using plain `ws` without TLS
    (https://moonraker.readthedocs.io/en/latest/external_api/introduction/).
- **M112 through `/printer/gcode/script` is queued "after all previous
  gcodes are complete"; the stop is `/printer/emergency_stop`.**
  `gcode/script` also waits behind a running temperature wait
  (https://www.klipper3d.org/API_Server.html).
- **Pause, resume and cancel run the printer's own macros** (`PAUSE`,
  `RESUME`, `CANCEL_PRINT`; https://github.com/Klipper3d/klipper/blob/master/klippy/extras/pause_resume.py).
  Mainsail's `PAUSE` parks the toolhead and `CANCEL_PRINT` can park before
  turning heaters off
  (https://github.com/mainsail-crew/mainsail-config/blob/master/client.cfg).
  They are _actuate_, not stop.
- **Uploads** (https://moonraker.readthedocs.io/en/latest/external_api/file_manager/):
  - `/server/files/upload` with `print=true` starts a print;
  - with `root=config` it rewrites `printer.cfg`.
- **Power and the host machine:**
  - `/machine/device_power/*` switches power
    (https://moonraker.readthedocs.io/en/latest/external_api/devices/);
  - `/machine/shutdown|reboot|services/*` controls the host machine
    (https://moonraker.readthedocs.io/en/latest/external_api/machine/).
- **Authorization** (https://moonraker.readthedocs.io/en/latest/external_api/authorization/):
  - `X-Api-Key`, a JWT bearer token, or a 5-second one-shot token.
  - **There are no roles**: a key has all access or none.
  - `trusted_clients` and the unix socket `~/printer_data/comms/moonraker.sock`
    need no authentication at all.
  - So every limit is ours to enforce, and a command reaching the socket
    from the shell is in the guard table.
- **Simulation:**
  - Klipper's batch mode (`klippy.py printer.cfg -i test.gcode -o test.serial
-d out/klipper.dict`) checks G-code against a config without hardware
    (https://www.klipper3d.org/Debugging.html).
  - `virtual-klipper-printer` (GPL-3.0, last push 2026-01-10) runs
    simulavr, Klipper and Moonraker in Docker on port 7125
    (https://github.com/mainsail-crew/virtual-klipper-printer). It is our
    real-API test target on Kubuntu.

**OctoPrint**

- **Auth** is `X-Api-Key` or a bearer token. The **appkeys flow**:
  - probe, request, then poll;
  - the user approves in OctoPrint's own UI;
  - the request goes stale if not polled for 5 s.

  So the machine wizard never asks the user to paste a key
  (https://docs.octoprint.org/en/master/api/general.html,
  https://docs.octoprint.org/en/master/bundledplugins/appkeys.html).

- **Endpoints:**
  - GET `/api/printer` is status;
  - POST `/api/printer/printhead`, `/tool`, `/bed`, `/chamber` and
    `/command` (arbitrary G-code) need CONTROL
    (https://docs.octoprint.org/en/master/api/printer.html);
  - POST `/api/job` starts, cancels or pauses
    (https://docs.octoprint.org/en/master/api/job.html);
  - a file upload takes `print=true`
    (https://docs.octoprint.org/en/master/api/files.html).
- **Access control** has been mandatory since 1.5.0, with a built-in
  "Read-only Access" group
  (https://docs.octoprint.org/en/maintenance/features/accesscontrol.html).
  A status-only machine can use a key that cannot move anything, and the
  wizard offers that first.
- **Emergency commands** default to `["M112","M108","M410"]` with
  `emergency_parser: True`, sent out of band
  (https://github.com/OctoPrint/OctoPrint/blob/master/src/octoprint/schema/config/serial.py).
- The bundled Virtual Printer plugin simulates temperatures and responses
  (https://docs.octoprint.org/en/master/development/virtual_printer.html).
  It is our second real-API target.
- OctoPrint's own blog calls exposing it to the internet "a terrible idea"
  (https://octoprint.org/blog/2018/09/03/safe-remote-access/). D83.9 keeps
  public addresses refused.

**PrusaLink and Bambu Lab**

- **PrusaLink** (https://github.com/prusa3d/Prusa-Link-Web/blob/master/spec/openapi.yaml):
  - digest auth;
  - `/api/v1/info|status|job`, PUT pause/resume, DELETE a job, PUT a file
    with `Print-After-Upload`;
  - **no raw G-code, jog or temperature endpoint.**

  Through PrusaLink we offer status and job control only.

- **Bambu Lab:**
  - Authorization Control (2025-01-16) gates LAN and cloud print starts,
    motion, temperatures and fans
    (https://blog.bambulab.com/firmware-update-introducing-new-authorization-control-system-2/).
  - Developer Mode leaves MQTT, the live stream and FTP open at the user's
    own risk and without support
    (https://blog.bambulab.com/updates-and-third-party-integration-with-bambu-connect/).
  - The MQTT details are community reverse-engineering only
    (https://github.com/Doridian/OpenBambuAPI/blob/main/mqtt.md).
  - We do not build against it (§9).

**Marlin over USB serial**

- M112 shuts down; M410 stops the steppers and loses position; M108 breaks
  heating waits.
  - Each needs `EMERGENCY_PARSER`, which is commented out by default;
    without it they wait behind the queue
    (https://marlinfw.org/docs/gcode/M112.html, https://marlinfw.org/docs/gcode/M410.html,
    https://github.com/MarlinFirmware/Marlin/blob/bugfix-2.1.x/Marlin/Configuration_adv.h).
  - Whether the firmware has it is read from `M115`'s capability report
    (lane M confirms the field). Without it the panel says the printer's
    own switch is the only immediate stop.
- Thermal protection is on by default
  (https://github.com/MarlinFirmware/Marlin/blob/bugfix-2.1.x/Marlin/Configuration.h).
- Persistent or destructive codes (https://marlinfw.org/meta/gcode/):
  - M500 save, M502 factory reset, M997 firmware update;
  - M80/M81 PSU power, M42 set pin;
  - M303 PID autotune (heats).

### 2.4 CNC routers, mills and lasers

**GRBL 1.1**

- **Real-time bytes are acted on at once, never buffered**
  (https://github.com/gnea/grbl/wiki/Grbl-v1.1-Commands):
  - `?` status, `!` feed hold, `~` resume;
  - 0x18 soft reset, 0x85 jog cancel;
  - 0x90 and above are overrides.
- `$J=` jogs need a feed rate.
- **`$C` check mode** parses every block without moving, with the spindle
  and coolant off, and checks soft limits. Leaving it soft-resets
  (https://github.com/gnea/grbl/wiki/Grbl-v1.1-Interface).
- **Settings** (https://github.com/gnea/grbl/wiki/Grbl-v1.1-Configuration):
  - `$20` soft limits need homing and correct `$130–132` travel;
  - `$22` homing locks G-code until `$H` or `$X`;
  - `$32` laser mode carries a fire and eye warning;
  - **`$N` startup lines run on every reset and can contain motion**, so a
    soft reset as a stop is safe only if `$N` holds no motion. The Stop
    reads `$N` once at connect and warns when it does.
- `$X` "should only be used in emergency situations".

**grblHAL and FluidNC**

- grblHAL adds 0x19 stop and 0x87 full status
  (https://github.com/grblHAL/core/blob/master/grbl.h).
- **Alarm 10 is E-stop in grblHAL but a homing failure in GRBL 1.1**
  (https://github.com/grblHAL/core/blob/master/alarms.h). Alarm tables are
  per firmware.
- FluidNC: per-axis `max_travel_mm` and `max_rate_mm_per_min`, and
  **`soft_limits` defaults to false**
  (https://github.com/bdring/FluidNC/blob/main/FluidNC/src/Machine/Axis.cpp).
  Its network ports are unverified (sources conflict).

**Senders**

- CNCjs (MIT): socket.io `command`/`write` events
  (https://github.com/cncjs/cncjs/wiki/Controller-API).
- UGS: a pendant API at `/api/v1`, secondary only.
- They stay the user's senders (D83.1).

**Offline checks**

- CAMotics `camsim in.gcode out.stl` simulates the cut (GPL-2.0+; the
  user's install)
  (https://github.com/CauldronDevelopmentLLC/CAMotics/blob/master/src/camsim.cpp).
- cncjs's `gcode-parser` 2.2.0, `gcode-interpreter` 3.0.0 and

  analyser (rule 9 decides; lane M prefers a small in-house tokenizer).

  "Always allow" lets the agent act unsupervised.

  arbitrary Python by default; https://github.com/RobertCoop/openscad-mcp
  has `allowed_paths` and a threat model.

**The lesson.** A `confirm` flag or a token the model can see or set is not
human approval. Only a prompt from the host or client (MCP elicitation, our
modal) involves a person. So D83.4 treats every such server as physical and
asks itself, whatever flags the server takes.

**Incidents.**

- In LLM-3D Print (https://arxiv.org/html/2408.14307), full firmware docs
  in context led to "unintended LLM-driven shutdowns". The fix was to
  exclude shutdown, restart and firmware commands from what the model may
  send: D83.6's refused set.
- Server READMEs: gating "is not a substitute for a human watching hot,
  moving hardware. Keep an emergency stop within reach" (nixkor); "Know
  where your E-stop is" (ugs-mcp).

**Standards.**

- ISO 13850:2015 §4.1.1.3: the emergency stop "is a complementary
  protective measure and shall not be applied as a substitute for
  safeguarding". It is one human action, always available, and overrides
  other functions (secondary summary,
  https://machinerysafety101.com/2026/05/18/iso-13850-emergency-stop-requirements/;
  iso.org refused).
- IEC 60204-1:2016 defines stop categories 0 and 1
  (https://webstore.iec.ch/en/publication/26037; category text secondary,
  https://www.se.com/us/en/faqs/FA122781/).
- "A software stop is not an emergency stop" is our synthesis, from these
  and from the facts above:
  - M112 can be queued (Moonraker `gcode/script`, Marlin without
    `EMERGENCY_PARSER`);
  - the host link can fail;
  - Marlin calls M112 a control stop.
- Bambu says never to leave a laser job unattended
  (https://bambulab.com/en-us/h2d/faq).
- No regulator guidance on unattended printing was found (unverified).

  - flash actions "can require explicit approval";

    D83 adopts the lease idea (§6 lane P).
- **Microchip MPLAB AI Coding Assistant** is built on Continue and has an
  agent mode (https://marketplace.visualstudio.com/items?itemName=Microchip.mplab-ai-coding-assistant).
  How it approves actions is unverified.
- **Nordic** (2026-05-28) has nRF Connect SDK and nRF Cloud MCP servers,
  with no safety notes
  (https://devzone.nordicsemi.com/nordic/nordic-blog/b/blog/posts/bringing-ai-assisted-development-to-nrf-connect-sdk-and-nrf-cloud).
- **Espressif** has `idf.py mcp-server` and docs MCP servers (§2.1);
  approval is left to the client.
- **ST** has no official MCP server. TI, ADI and Silicon Labs ship
  hardware-bound MCP servers (https://veecle.ai/blog/hardware-mcp-servers-2026).
- **Flux.ai** is a browser PCB copilot whose actions the user accepts
  (https://www.flux.ai/p/blog/design-circuits-with-natural-language-copilot-upgrade).

**The gap.** Vendors leave approval to the client, and the client (Copilot,
Cursor, Claude Code, us today) treats flashing, GPIO and `cmd_vel` as
ordinary commands with session rules and auto-approve. Only niche servers
(armguard) bound motion, and only Embedder leases hardware. A harness-level
physical action class with hard per-action approval, irreversible-operation
refusal, simulate-first recipes, honest privacy routing (Wokwi uploads,
QEMU and Renode do not) and a hardware lease is something nobody ships.

### 2.14 What the findings change in the design

- Monitors are bounded by our process-tree kill, never by their exit keys;
  arduino-cli needs stdin held open; esp-idf-monitor's stdin command mode
  (`expect --timeout`) is the preferred ESP-IDF recipe.
- The POSIX fallback reads through a killable child, never `fs.read`;
  pyserial first where present.
- Connect is its own class because opening a port resets boards, and a
  1200-baud open reboots CircuitPython boards into their bootloader.
- Ports are filtered for Bluetooth (`BTHENUM`) on Windows.
- `wok_` tokens join the redaction table; Wokwi is labelled as a cloud
  service.
- `idf.py mcp-server`, PlatformIO, Arduino and ROS MCP servers are
  physical by default (D83.4).
- One holder per port or machine at a time (the Embedder lease idea), across
  windows and the ACP agent.
- A 32-bit Pi gets neither Remote-SSH (VS Code ≥ 1.123) nor Muse Code (the
  launcher), and only Node 22. The Pi story is arm64.
- Local models: a PC or GPU box, not the Pi; photo review only on models
  with both vision and tools.
- **Stop paths are out of band and never gated:**
  - Moonraker `/printer/emergency_stop` (never M112 through `gcode/script`);
  - GRBL `!`, then 0x85 and 0x18;
  - OctoPrint's emergency commands (sent out of band by its emergency
    parser);
  - Marlin M112/M410 only where `EMERGENCY_PARSER` is built in.
- **Pause and cancel are not stop:** Klipper's `PAUSE` and `CANCEL_PRINT`
  are user macros that move the toolhead, so they are _actuate_.
- **Approval comes only from the host's own UI.** A token or `confirm` flag
  the model can see or set is not a person.
- **Limits are trusted only after homing.** Read Klipper's `homed_axes`,
  GRBL's alarm state and `$20`/`$22`, and FluidNC's `soft_limits` (off by
  default). No homing or no soft limits means no model-proposed motion.
- **Moonraker has no roles,** and its unix socket and `trusted_clients`
  skip auth. Every limit is ours, and the socket is a guard row.
- **The refused set for model sends:**
  - M112 (outside Stop), M997, M502, M500;
  - `FIRMWARE_RESTART`/`RESTART`, `SAVE_CONFIG`;
  - Moonraker `/machine/shutdown|reboot`;
  - GRBL `$X`, `$RST`, `$N` writes;
  - Marlin M80/M81/M42/M303.

  The user does these in their own UI (LLM-3D Print's lesson).

- **The editors:**
  - an Arduino IDE 2 build of the VSIX (API 1.96, Node 20.14, Chromium 124);
  - a Thonny plugin with the companion page and Thonny as serial provider;
  - our Eclipse plugin for Espressif-IDE, STM32CubeIDE and MCUXpresso (Edge
    forced in SWT);
  - CLion through ACP, with registry auth and an optional JCEF plugin.

## 3. What our harness already has, and the hazards it has today

### 3.1 Pieces that fit (read from the code)

- **Bounded device commands already work (M92b, D71).** The shell tool's
  `timeout_ms` (default `SHELL_DEFAULT_TIMEOUT_MS` 120 s, cap
  `SHELL_MAX_TIMEOUT_MS` 600 s, `src/shared/constants.ts`) returns the output
  it captured with `isTimedOut` and kills the whole process tree on all three
  OSes, so "flash, then capture N seconds of serial output" is one call. M92
  proved it with a fake never-ending monitor. Every recipe below builds on it.
- **A first-party skill folder exists (M92c).** `first-party-skills/muse_gadgets/SKILL.md`
  on main is read as a second `bundled` root (`FIRST_PARTY_SKILLS_DIR`,
  `src/core/context/skills.ts`), lowest precedence, under
  `museSpark.bundledSkills` (default `true`, machine scope). It already
  covers ESP-IDF build/flash/monitor and COM-port naming for gadgets. The
  catalogue (id and description) goes into the instructions, so every new
  skill grows the request prefix: maker skills must only enter the catalogue
  of a workspace that looks like a maker project (§6 acceptance 5). D71 says
  the Muse Code installer copies only the vendored package, so on Muse Code
  first-party skills do not reach the model today.
- **The exact precedent for a hard guard (M92e).** `permissions.ts` settles a
  shell command holding a detected secret as `settledBy: 'secretDetected'`:
  it asks in every mode, Bypass included, on the Model API; no allow rule,
  session rule, profile or hook answers it; the card offers no session
  choice; the Auto reviewer never sees it (`isReviewableApproval`,
  `src/core/agent/approvalRules.ts`, and `approvalSecrets.ts`). A
  `hardwareDetected` settle is the same mechanism with a different table.
- **The exact precedent for an ask no backend mode can skip (M69).**
  `src/host/web/webFetchConfirm.ts`: Muse Code's web fetch through the `ide`
  server asks in a native modal for every call, "whatever mode Muse Code runs
  in (its approval covers using the tool; this one covers the extension
  sending the request from the user's machine)". Device tools served by the
  `ide` server (`src/host/ide/ideMcpServer.ts`) use the same pattern, so a
  physical action asks even under Muse Code Bypass.
- **Tool lists are opt-in per feature.** `toolDefinitions(platform, options)`
  in `src/core/backends/modelapi/tools.ts` adds tools by flags
  (`hasWebFetch`, `hasBrowserCheck`, `hasCodeIntel`, `checks`…). A
  `hasDevices` flag keeps every other workspace's request bytes (and the
  golden fixtures) unchanged.
- **Tool classes.** `ToolClass = 'read' | 'edit' | 'shell' | 'interactive' |
'paid' | 'mcp' | 'spawn' | 'network'` with `verdictFor(mode, class)`. A
  `device` class (asks in every mode, Bypass included, like `paid`; refused
  in Plan; never a session rule or the reviewer) fits beside them.
- **Windows serial without a native module.** `src/host/backend/jobBuild.ts`
  compiles C# once with Windows' .NET Framework `csc.exe`, referencing
  `System.dll`, into the extension's storage, named by the source digest
  (M27's job helper, M50's MCP launcher). `System.IO.Ports.SerialPort` lives
  in `System.dll` on .NET Framework (see §2.2), so a `MuseSparkSerial` helper
  costs no shipped binary and no new dependency.
- **The extension runs where the workspace is.** `extensionKind:
["workspace"]`: over Remote-SSH to a Raspberry Pi the extension host, the
  shell and the serial ports are the Pi's. A board plugged into the user's
  PC is not reachable from a remote window (say so in the skill).
- **Muse Code on a Pi.** Meta's launcher (`https://api.meta.ai/muse-launcher.sh`,
  fetched 2026-10-05, lines 92–97) maps `Linux:aarch64` to `aarch64_linux`
  and dies with "unsupported platform" for anything else on Linux but
  x86_64: a 64-bit Raspberry Pi OS can run Muse Code; a 32-bit one (armv7l)
  cannot and gets the Model API backend only. The x64 Linux binary is about
  314 MB (D1a); its memory use on a Pi is unmeasured.
- **The ACP agent on a Pi.** Its only native dependency, `@napi-rs/keyring`
  2.1.0, is prebuilt for Linux arm64 and arm (D61). On Linux it needs a
  Secret Service; a headless Raspberry Pi OS Lite has none, and the agent
  has no plaintext fallback by design, so the Model API key cannot be stored
  there until the user runs a keyring or uses the Muse Code backend. Our CI
  already does the headless recipe: `dbus-run-session -- sh -c "printf
'…\n' | gnome-keyring-daemon --unlock --components=secrets && …"`
  (`.github/workflows/hosts.yml`, the `agent` job). The Pi guide makes it a
  user recipe; the unlock password comes from the user's terminal, never a
  file.
- **Free arm64 CI.** The repository is public
  (`RandyNorthrup/muse-spark-code`); GitHub's `ubuntu-24.04-arm` runners are
  free for public repositories and generally available since 2025-08-07
  (https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/,
  https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
- **Local models are already providers (M95).** Presets `ollama`,
  `lmstudio`, `vllm`, `llamacpp` (`src/core/providers/presets.ts` on
  m95/int), the local probe on loopback (`src/host/providers/localProbe.ts`),
  and capability records (`toolCalling`, `vision`, `reasoning`,
  `parallelToolCalls`, `src/core/providers/capabilities.ts`) with Zed's
  conservative defaults (`vision: false`) for unknown local models.
- **But the endpoint policy keeps plain HTTP on loopback.**
  `src/core/providers/endpointPolicy.ts`: "HTTPS only, with plain HTTP only
  to a loopback address … An HTTPS address on a private network asks once
  when it is saved". An Ollama box or a printer on the LAN usually speaks
  plain HTTP, so neither works today without a tunnel (§8 Q-M103a).
- **A workspace never names an address.** `workspaceSuggestion.ts`: "a
  workspace file can never set an address". Machine endpoints follow the same
  rule (§5 D83.9).
- **Check commands (M68).** `museSpark.checkCommands` (`src/core/verify/checkCommands.ts`)
  runs the user's checks with timeouts and feeds the verify loop: `pio run`,
  `idf.py build`, `arduino-cli compile`, `kicad-cli sch erc`, `colcon test`
  and a simulator run with an expected line are natural presets.
- **PDF input on the Model API.** `read_file` returns a PDF whole for the
  model to see (`tools.ts`), so datasheets kept in the repository work on
  providers that take PDFs; Muse Code's MSP 1.3.0 cannot take a PDF part
  (README).
- **Workspace grants live in `workspaceState`** (`src/host/paid/paidHost.ts`,
  `paidWorkspaceGrants`), not in a repository file: the per-workspace hardware
  switch goes there too.
- **Budgets are tight.** `dist/extension.js` 600 KiB budget (the 0.14.0
  train measured 612,921 of 614,400 bytes before ACTDIET), the webview's
  startup bundle at 918,663 of 921,600 bytes, the universal VSIX budget
  2200 KiB (`scripts/check-vsix-size.mjs`) with the merged inputs measured
  over it (ACTDIET, scratchpad state 2026-10-05). Everything maker goes into
  lazy bundles with D6's "measured + 15 %, rounded up to 25 KiB" budgets, and
  activation gains nothing.

### 3.2 Hazards in today's harness (fix these first, whatever else ships)

- **H1 — the shell is already an actuator.** Nothing stops the model from
  running `pio run -t upload`, `idf.py -p COM5 flash`, `espefuse.py
burn_efuse …`, `echo 'G1 Z-5' > /dev/ttyUSB0`, `curl -X POST
http://printer.local/printer/gcode/script?script=M104%20S260`, `gpioset
gpiochip0 17=1` or `ros2 topic pub /cmd_vel …`. In Bypass the Model API
  runs them without a card; in Auto the reviewer (M78/M90) may allow one that
  looks simple; an allow or session rule answers the exact line again. On
  Muse Code in Bypass the CLI sends no approval at all (§9 residual
  RVM92E-BYPASS-MUSE), so the extension cannot even see it.
- **H2 — Muse Code edits workspace files without asking, even in Manual**
  (`src/shared/permissionModes.ts`). A workspace that _is_ a CIRCUITPY drive
  (CircuitPython restarts `code.py` on save) or a Klipper config folder
  opened over Remote-SSH turns an unasked edit into a device change (a new
  program running, or a `max_temp` raised before the next restart).
- **H3 — opening a serial port is not a read.** On boards with the classic
  DTR/RTS auto-reset circuit (most ESP32 dev boards, Arduino Uno/Mega, many
  Marlin printer boards) opening the port resets the microcontroller (§2.2):
  a "read the serial log" can reboot a board or kill a print in progress.
- **H4 — hardware MCP servers are ordinary MCP tools.** An OctoPrint or
  Moonraker MCP server's `send_gcode` gets "Allow for this session", the Auto
  reviewer and Bypass like any MCP tool; a `readOnlyHint` it sets on itself
  runs without a card in Auto (`permissions.ts`, `mcpVerdict`).
- **H5 — unattended surfaces.** Timed sends and schedules (M88), loops and
  goals, subagents (M48), team workers (M96), best-of-N and remote lanes
  (M100) can all reach the shell with nobody at the machine.
- **H6 — maker secrets.** Wi-Fi passwords in `secrets.h`, `settings.toml`
  (CircuitPython web workflow password), ESPHome `secrets.yaml`, OctoPrint
  and Moonraker API keys, Wokwi CI tokens, Adafruit IO keys. Only
  prefix-bearing tokens can join the shared redaction table without false
  positives (a 32-hex Moonraker key looks like an MD5); the others are
  redacted by value once the extension stores them.

## 5. Proposed D83

### D83 — Makers: boards, firmware and machines, with a human at every actuation (M103, 2026-10-05)

The owner asked (2026-10-05): "is there anything we can include that will
make this harness have useful features for creators and tinkerers ie people
who program raspberry pi or esp32 or like robotics and cncs and 3d printers
etc?" The research, its sources and the ranked list are in
`docs/research/makers-2026-10-05.md` (this draft, once landed).

Physical machines can injure people and start fires. A model is wrong
sometimes, and a prompt in a datasheet, a README or a fetched page can steer
it. These decisions keep every physical effect behind a person who sees
exactly what will be sent.

1. **Help with the work; the user's hand moves the machine.** The extension
   helps write, build, flash, simulate and read devices and machines. It is
   not a print host or a G-code sender: OctoPrint, Mainsail/Fluidd, CNCjs,
   UGS and FluidNC's WebUI stay the user's tools for running jobs.
2. **Six action classes, and stop,** decided by our code, never by the
   model or a server's own hint:
   - _offline_: edit, build, simulate, render, ERC/DRC, G-code analysis —
     ordinary tools and checks;
   - _observe_: list ports (opens nothing), read a registered machine's
     status over its HTTP API, ROS 2 introspection, `vcgencmd`, `gpioinfo`;
   - _connect_: open a serial port (it may reset the board), mount a device
     file system;
   - _program_: flash, upload, erase, OTA update, write files to a
     development board, reset a development board (a microcontroller, not a
     printer's or CNC's controller, whose restarts and settings are
     _refused_ below);
   - _actuate_: anything else sent to a machine — motion, homing, probing,
     jogging, heaters, spindle, laser, fans, pumps, relays, power, starting,
     pausing or cancelling a job (Klipper's `PAUSE` and `CANCEL_PRINT` are
     macros that move the toolhead), ROS motion topics, actions and
     services, `gpioset`. A command or macro the classifier does not know is
     _actuate_ (fail closed).
   - _refused_: what the model may never send, even with approval. The user
     does these in their own tools:
     - firmware updates and factory resets (M997, M502);
     - saved settings (M500, `SAVE_CONFIG`, GRBL `$` writes, `$RST`, `$N`);
     - restarts and host shutdown (`FIRMWARE_RESTART`, `RESTART`,
       Moonraker `/machine/shutdown|reboot`);
     - power and pins (M80/M81, M42);
     - autotune (M303);
     - GRBL `$X` (alarm unlock);
     - uploads into Moonraker's `root=config`;
     - the irreversible chip operations of D83.4.
   - _stop_ is not a class the model can compose: it is the machine's own
     fixed stop sequence (D83.5).
3. **Connect, program and actuate ask every time, in every mode.** The maker
   engine asks from inside the tool, through its host's approval surface
   (D83.16): in VS Code a native modal (the M69 pattern), in an ACP client
   its permission prompt, in the companion page and the native plugins the
   shared dialog. So it asks under any backend mode, Muse Code's Bypass
   included. The approval names the target (port, VID:PID and USB serial, or
   the machine's name and address and what it reports itself as), shows the
   exact payload (bytes as hex where not printable; up to
   `MACHINE_SEND_MAX_LINES` lines, more opens the payload read-only before
   asking again), the analysis (bounds, maximum temperature and feed against
   the limits, unknown commands), and warns that opening a port may reset the
   board. It offers **Send once** and **Reject** only (closing it rejects).
   No session rule, allow rule, "always", Auto reviewer or hook answers it.
   **Approval comes only from the host's own UI:** a token, a `confirm`
   flag or any value in a tool's arguments or results is never approval,
   because the model can read it and set it (§2.11: ugs-mcp hands its token
   to the model).
   An unanswered modal expires as Reject after `MACHINE_APPROVAL_TTL_MS`;
   the machine's state is read again just before sending, and any change
   since the modal opened (a print started, a different board on the port)
   asks again.
4. **The shell and MCP cannot go around it.** A guard table
   (`src/core/maker/guard/`, one table like M92e's secret table) recognises
   flashing, uploading, device writes and machine API calls in shell
   commands (§6 lane G lists them) and settles them `hardwareDetected`:
   asked in every mode, Bypass included, with no session choice, never the
   reviewer, never a hook's allow; Plan refuses them. Irreversible operations
   (eFuse burns, secure-boot and flash-encryption key burns, AVR fuse and lock
   writes, STM32 read-out protection level 2, RP2350 OTP writes) are refused
   in every mode: the reply gives the user the command to run in their own
   terminal. MCP servers the user marks physical
   (`museSpark.physicalMcpServers`, machine scope; a workspace can add a name,
   never remove one) and known hardware servers ask like D83.3. The table
   cannot recognise every program that can reach a port, so in a workspace
   with the hardware switch on: Bypass is unavailable on both backends (on
   Muse Code the CLI emits no approval under Bypass, RVM92E-BYPASS-MUSE), the
   Auto reviewer does not answer shell commands, and README says plainly that
   a program the model wrote can reach a device once the user lets it run.
5. **Stop is always one click away and never asks.** While a machine is
   registered, **Stop machine** is in the panel, the status bar and the
   command palette with a keybinding no OS or VS Code default uses. It sends
   the machine's own stop, out of band:
   - Moonraker: `POST /printer/emergency_stop`, never M112 through
     `gcode/script`, which queues behind earlier G-code;
   - OctoPrint: M112 through its emergency parser, which sends it out of
     band;
   - Marlin over serial: M112 or M410, immediate only where M115 reports
     `EMERGENCY_PARSER`; otherwise the panel says the printer's own switch
     is the immediate stop;
   - GRBL: feed hold `!`, jog cancel 0x85, then soft reset 0x18 (grblHAL's
     0x19 where present), with a warning when `$N` startup lines hold
     motion.

   It stops any stream the extension started and needs no approval. The turn's Stop also stops streams. The model may call
   `machine_stop` without approval. README and the skill say a software stop
   is not an emergency stop: a machine needs its own physical E-stop
   (ISO 13850, IEC 60204-1).

6. **Limits come from the machine and the user, never the model.** Travel,
   temperature and feed limits are the smaller of what the machine reports
   (Moonraker's parsed `configfile`, GRBL `$$`, FluidNC's config, Marlin's
   `M503`) and the limits the user entered when registering it. A command
   outside them is refused without asking. With no limits, only stop and
   observe work. Travel limits count only on a homed machine (Klipper
   `homed_axes`, GRBL not in alarm with `$20` and `$22` on, FluidNC
   `soft_limits` true, which is off by default): an unhomed machine or one
   without soft limits gets no model-proposed motion. Moonraker keys have no
   roles, so these checks are ours. OctoPrint's wizard offers a key from its
   "Read-only Access" group first, through the appkeys flow (the user
   approves in OctoPrint's UI and never pastes a key).
7. **Dry run first.** G-code is analysed locally before any modal; the
   simulators (QEMU, Renode, Wokwi, a virtual Klipper, Gazebo) are the first
   target for firmware and robot work, and the skill says so. CNC and laser
   machines get no model-proposed motion or firing in this delivery
   (status, settings read, alarms, stop only); printers get short approved
   G-code. Widening that is a later owner decision after field use.
8. **Never unattended.** Connect, program and actuate are refused, not
   asked, in subagents, team workers, best-of-N candidates, M100 remote
   lanes, headless `exec` and CI. Timed sends, loops and goals still meet the
   approval, which expires. In the ACP agent device tools exist only with
   `--hardware`, and each action is the editor's permission prompt with
   allow-once and reject-once only (or the companion page's dialog when the
   client has no prompt). Headless `exec` on a Raspberry Pi gets every
   offline and observe tool (build, test, simulate, list ports, read a
   registered machine's status over HTTP); opening a serial port is a
   _connect_ action, so serial reads are not among them. A hard allowlist for headless
   hardware-in-the-loop runs is a separate decision (Q-M103f).
9. **Off until the user turns it on, per workspace, with a reason.** Device
   tools, serial, machine status and sends need **Enable hardware for this
   workspace** (in VS Code a command; in the runtime `hardware enable`, or
   `/hardware` in an ACP client): a trusted workspace, a reason the user
   types (kept in the device log), stored by the host outside the
   repository (VS Code's `workspaceState`; the runtime's data folder, keyed
   like its paid grants), revocable, and never set by a repository file.
   Machines (kind, address, API key, limits) are added by a command into
   machine-scoped storage, the key in the host's secret store (SecretStorage,
   or the OS credential store for the runtime); a workspace may only name
   which registered machines it uses. Plain HTTP to
   a private address is allowed only for a registered machine, with a
   warning that the key crosses the LAN unencrypted; public, link-local and
   metadata addresses are refused, and every request checks the resolved
   address again (D74's checks). The guard (D83.4), the skills, detection,
   the analyser and the offline tools are on by default.
10. **Flash the board that is meant.** Before a _program_ action the card
    shows the port's identity next to the project's target (PlatformIO
    `board`, `CONFIG_IDF_TARGET`, the FQBN); a known mismatch (a Pico's
    2E8A on the port of an ESP32 project) is refused with the reason.
11. **Everything sent is logged.** An append-only, size-capped JSONL device
    log in the host's per-workspace storage (outside the repository): time,
    machine, class, payload (redacted) and its SHA-256, the approval, the
    outcome. **Open device log** shows it. It never reaches the model or an
    export unless the user chooses.
12. **Multi-vendor, by capability (D81.2).** Skills and the guard are on for
    every provider; tools only on tool-calling models; photo review and
    render feedback only where `capabilities.vision`; PDFs where the
    provider takes them. Nothing is withheld because one vendor's model
    lacks it.
13. **No native modules, no startup growth.** Platform tools first
    (`pio`, `arduino-cli`, `idf.py`, `mpremote`, `esptool`), then our
    fallback: on Windows a C# helper compiled on first use by `jobBuild`
    (`System.IO.Ports` in .NET Framework's `System.dll`), on Linux and macOS
    pyserial where present, else `stty` with reads through a killable child
    process (never `fs.read` on a device in the host), under the existing
    process-tree kill. All maker code is in lazy bundles: the portable
    engine `dist/maker.js` (the extension and the ACP package), the VS Code
    adapter's few loaders, and the webview's lazy maker chunks and preview
    page. Activation and the webview's startup bundle gain nothing (D6).
    OpenSCAD, KiCad and the toolchains are the user's installs; nothing GPL
    is bundled.
14. **Privacy.** The device log, machine list and keys stay on the machine.
    Wokwi runs in Wokwi's cloud with the user's own token (§2.5): the skill
    and README say what leaves the machine; QEMU and Renode stay local.
    Secrets:
    - Wokwi CI tokens (`wok_`, 44 characters) join the one shared redaction
      table, as M92a's `mgst_` did.
    - Machine keys are redacted by value.
    - The skills tell the model never to print or commit `secrets.h`,
      `settings.toml`, ESPHome `secrets.yaml` or `sdkconfig` Wi-Fi values.
15. **Amends D71.** The Muse Code bundled-skill installer also copies the
    first-party skills (marked, removable, same setting), so `muse_gadgets`
    and the maker skills reach Muse Code too.
16. **One maker engine for every editor (owner, 2026-10-05: "all of the
    editors should have equivalent functionality even if we need to develop
    it ourselves").**
    - **The engine is portable.** Every maker feature lives in
      `src/core/maker/**`, which imports no `vscode` and is on M60's portable
      list: the guard, detection, ports and serial, flash identity, machines,
      the G-code analyser, CAD and EDA runners, the device log, the lease and
      the approval rules. It is built as `dist/maker.js`, which the
      extension loads lazily and the ACP agent's package ships (as
      `dist/modelApi.js` is today, D6).
    - **Hosts implement one port.** `MakerHost` is the only seam:
      - `confirm(request)`;
      - `notify`;
      - `stopControls(machines)`;
      - `openPreview`;
      - `storage` (workspace and machine);
      - `secrets`;
      - `isTrusted`;
      - an optional `serialProvider`, for a host that already owns the
        device connection (Thonny's backend, D83.17), so the engine goes
        through it and never opens the port a second time.

      There are three implementations:
      - VS Code (`src/host/maker/`): native modal, status bar, SecretStorage,
        `workspaceState`;
      - the runtime (`src/runtime/maker/`): the ACP permission prompt or the
        companion page, its data folder, the OS credential store (D61);
      - the native plugins (M64, M65): they run the runtime and supply only
        the dialog and toolbar through the shared protocol.

    - **The engine decides; surfaces only display.** It mints each approval
      request:
      - an id;
      - the payload's SHA-256;
      - the target's identity;
      - an expiry.

      It accepts only an answer that echoes the id and digest before the
      expiry, so no surface can widen, reuse or extend an approval.

    - **The UI is shared React.** These live in `src/webview/maker/**`,
      lazily loaded chunks behind M61's `HostBridge`:
      - the approval dialog (for surfaces without a native one);
      - the Stop chip;
      - the device panel, machine wizard and device log view;
      - the STL viewer.

      They render the same in a VS Code webview, JCEF, WebView2, SWT's
      browser and the companion page.

    - **Editors without a webview get the companion page.** It is the shared
      React UI, served by our runtime on loopback (`127.0.0.1`, random port,
      a per-launch token, Host and Origin checks, the panel's CSP), opened in
      the user's browser. On a Raspberry Pi it is reached through `ssh -L`.
      It never listens on a LAN address.
    - **Muse Code in the runtime.** When the ACP agent runs Muse Code, the
      runtime serves the maker tools to `muse serve` from its own loopback
      MCP server, as the extension's `ide` server does. Without that, ACP on
      Muse Code would have no device tools.
    - **Stop in every editor:**
      - the panel or companion page;
      - the editor's toolbar or command where it has one;
      - `/stop-machine` among the ACP agent's commands;
      - `muse-spark-code-acp stop-machine [--all]` from any terminal.

      The CLI stop reaches the port's holder over an owner-only local socket
      (named pipe on Windows), and the machine's own API directly for HTTP
      machines.

      A stop never waits behind a running turn. ACP slash commands arrive
      as ordinary prompts (https://agentclientprotocol.com/protocol/slash-commands),
      so `/stop-machine` serves only between turns. During a turn:
      - the client's cancel (`session/cancel`) ends every stream the agent
        started;
      - the companion page's button and the CLI command send the machine's
        stop.

    - **The approval through ACP.** It is `session/request_permission`
      offering only `allow_once` and `reject_once` of the four kinds
      (https://agentclientprotocol.com/protocol/tool-calls), with the exact
      payload as the tool call's text content.
    - **What cannot be equal is said, not hidden.** Ports are the machine's
      the engine runs on. In a cloud workspace (Codespaces, code-server,
      Che, Firebase Studio) there is no USB, so simulators and offline tools
      only. The matrix below records each editor's surfaces, and README
      carries it.

## 8. Questions for the owner

- **Q-M103a — plain HTTP on the LAN.** Printers (Moonraker, OctoPrint,
  PrusaLink) and home model servers (Ollama) usually speak plain HTTP on the
  LAN; D74 allows plain HTTP only to loopback. Default until answered:
  allowed only for a machine the user registered by command, with the
  warning (D83.9); model servers keep D74 and the guide shows an SSH tunnel
  or Remote-SSH.
- **Q-M103b — which machines may receive model-proposed actuation.**
  Default: 3D printers only (short G-code, per-action modal, limits); CNC,
  laser and robots read-only plus stop.
- **Q-M103c — the Auto reviewer in hardware workspaces.** Default: it does
  not answer shell commands there (D83.4).
- **Q-M103d — hardware for certification.** Default: certify on simulators
  and fakes; the hardware rows in §7 stay open and named.
- **Q-M103e — Wokwi.** It needs the user's token and runs in Wokwi's
  cloud. Default: a recipe and a check preset that read the user's own
  `WOKWI_CLI_TOKEN`; never on by itself.
- **Q-M103f — headless hardware-in-the-loop.** Default: not built (D83.8).
  When wanted, it would be an allowlist file the user writes, never the
  model, with these fields: device identity, action, payload digest, limits
  and expiry. Every run's log would be kept as a CI artifact.
- **Q-M103g — the companion page's reach.** Should it be the whole panel
  (chat, approvals, history) for every editor without a webview (D60's
  fourth family), or only the maker pages at first? Default: the maker
  pages in M103 (approval dialog, Stop, devices, log, preview, machine
  wizard), built on the same server and `HostBridge`, so the whole panel can
  follow without a second server.
- **Q-M103h — publishing the maker editor builds.** These need the owner's
  accounts:
  - the Arduino IDE build as a GitHub Release asset (no store exists);
  - the Thonny plugin on PyPI (a new account or token);
  - the Eclipse plugin's update site (with M65);
  - the ACP registry listing (needs Agent Auth or Terminal Auth).

  Default: release assets and install docs; PyPI and the registry wait for
  his token and his go.

## 9. Rejected or deferred

- **Shipping `serialport`.** `@serialport/bindings-cpp` is a native module:
  per-platform VSIXs, Electron ABI rebuilds and fork breakage, against the
  universal VSIX. Rejected for platform tools plus the helpers in D83.13.
- **Web Serial in the webview.** See §2.2; not a dependable path in desktop
  VS Code or its forks.
- **Becoming a print host or G-code sender.** D83.1.
- **Paid part-search APIs (Nexar/Octopart, Digi-Key, Mouser).** They need the
  user's keys and accounts; the datasheet-in-repo workflow covers the need
  without a new paid path (rule 12 would apply if added later).
- **Bundling OpenSCAD, KiCad or three.js.** GPL binaries and size; the
  preview is a small in-house WebGL viewer.
- **Cloud printer accounts (Bambu cloud, Prusa Connect, OctoEverywhere).**
  Credentials and third-party relays; LAN APIs only, and only registered
  machines.
- **Bambu Lab printers.** Control needs Developer Mode (unsupported by
  Bambu) or circumventing Authorization Control. The MQTT protocol is
  reverse-engineered only. Deferred; if added later, only status in
  Developer Mode.
- **Arduino App Lab.** MCP-only Agentic Mode with a closed provider list; not
  reachable.
- **Model-proposed CNC motion, laser firing, homing and `$X`.** Not in this
  delivery (D83.7); a later owner decision after field use.
- **Taking cncjs's MIT parsers as dependencies.** Lane M decides under
  rule 9 and prefers a small in-house tokenizer; the packages are recorded
  as the alternative.
