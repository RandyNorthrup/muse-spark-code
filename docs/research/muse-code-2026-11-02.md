### 1.3 Models, prices and limits (pages read in full, 2026-11-02)

- **Muse Wonder** (`muse-wonder-1.0`) is Meta’s most capable model,
  in preview, 1,048,576-token window, text/image/video/audio/PDF in,
  effort minimal…max. **Standard mode only on Model API — there is no
  Wonder contributor variant to buy.** Prices per 1M tokens: input
  $4.00, cached input $0.20, output $20.00. Rate limit 3,000 RPM /
  4,000,000 TPM, per team. Not available in South Korea.
- **Muse Wonder Full** is subscription-only inside Muse Code (Power
  Usage and Maximum Usage plans), reachable as the served model id
  `muse-wonder-full-1.0` (our captured 1.4.10 model list,
  `test/fixtures/muse-contributor/model-list-1.4.10.json:24-27`);
  setting effort `max` on Wonder does not select it. In Muse Code,
  Wonder and Wonder Full each come in Standard and Contributor mode
  on the plans that include them.
- **Muse Spark** 1.3 (recommended), 1.2, 1.1; same window and
  modalities. Standard: $1.25 / $0.15 cached / $4.25. Contributor
  (1.3, 1.2 only): $0.10 / $0.002 / $0.20. Contributor rate limit is
  150 RPM / 3,000,000 TPM vs Standard’s 3,000 / 4,000,000 — a 20× RPM
  gap that matters for fan-out (our pacing already reads the headers;
  §2). Audio understanding on Spark 1.3 is documented as degraded —
  use 1.2 or Muse Voice Transcribe; matches our 2026-10-05 captures
  (U4/U7). `max` effort is not available on `muse-spark-1.3-contributor`.
- Web search grounding: $2.50 per 1,000 queries. Muse Image: $0.01 per
  returned image, flat. Voice Transcribe: $0.18 per audio hour,
  256 concurrent streams, 16,000 streams/hour. SAM 3.1: $2.50 per
  1,000 images, $0.20 per 1,000 video frames (50-frame minimum).
- Rate limits are **per team, not per key**, per model. Background
  responses (`background: true`) are limited to 600 submissions per
  minute per team. Injected steering tokens are neither billed nor
  counted in `usage` or the token-count endpoints — relevant when
  comparing our estimates with provider-reported spend.
- Subscription shape: 4 plans (Everyday 10–50 prompts per 5 hours;
  High 5×; Power 20× + Wonder Full + early access; Maximum 80×).
  Contributor mode is the subscription default and is a per-computer
  saved setting; `--contributor-mode on|off` and
  `MUSE_CONTRIBUTOR_MODE` override per run (flag wins). A headless run
  on a machine whose settings file exists but never saved the setting
  **can have contributor mode on** — a trap for anyone automating
  `muse exec` who assumes off. Managed configuration can pin it off;
  ZDR accounts never see the row.

### 1.6 Research reading (one paper used, rest noted)

Fan et al., arXiv:2609.20804 (UMass Amherst/UCF et al., 2026-09-17),
ran 176 matched harness configurations (4 models, SWE-Bench Verified

- Terminal-Bench 2.1, fixed loop, varying planning/action
  space/context management). Findings from the abstract (the full text
  was not read in this lane; treat effect sizes as unverified):

1. Context management’s value concentrates on **preventing
   context-overflow failures** as budgets tighten; at large budgets
   it changes little.
2. **Rule-based elision staged before LLM summarization** was the
   most efficient strategy; making elided content recoverable added
   machinery models rarely used, with no accuracy gain.
3. Planning helps weaker models’ accuracy and stronger models’ cost,
   not both.
4. Predefined tools help bash-weak models; bash-capable models do as
   well bash-only at much lower cost.

Relevance, stated as inference: at Meta’s 1,048,576-token window,
finding 1 says compaction sophistication is insurance, not a quality
lever — consistent with our M75/M106 posture of keeping the local
loop honest rather than chasing server compaction. Finding 2 argues
against building a recoverable-elision store. The 2026 compaction
cluster found by search (AutoCompact, CliffCompaction, CompactionRL,
2606.11213, and 2607.13071’s warning that compaction summaries can
launder killed-process output into “confirmed” results) points the
same way: the live research risk is summary _trustworthiness_, not
summary quality. None of these were read beyond abstracts/snippets,
so none is load-bearing in §3; the one actionable, checkable item —
never let a compaction summary upgrade an unverified tool result
into a confirmed fact — is worth a harness-lane look, and it is
noted for RSCH-HARNESS rather than briefed here.

## 3. Ranked: what to do, and what not to do

Ranking is by value to a person, then strength of evidence, then

### Do not

- **Do not adopt `store: true`, `previous_response_id` or background
  responses** to chase server state. The 2026-10-05 privacy posture
  stands and nothing read since changes the trade; background mode
  also inherits the 600/min submissions cap and stored-content
  retention questions for zero interactive benefit.
- **Do not chase server compaction as a quality feature.** At a
  1M-token window the best current evidence (2609.20804, abstract
  read) puts context management’s value in overflow insurance; our
  U11 capture was already inconclusive under `store: false`. Keep it
  an evaluated arm only (RSCH-HARNESS may revisit with full texts).
- **Do not build a recoverable-elision store** (“bring back what
  compaction dropped”). The one ablation study read found models
  rarely use it and accuracy does not move.
- **Do not pin SDK 1.4.14 before 2026-11-03** or bypass
  `min-release-age` for it; the 7-day rule is the supply-chain gate
  working as designed, and 1.4.13 is available today.
- **Do not copy SDK source** even though it is MIT: the repository is
  a mirror (“an edit made to a mirrored file would be silently
  overwritten”), and we consume the versioned package with its
  fingerprint discipline; porting forfeits both. Ideas and wire
  shapes from captures remain the route (rule 14).
- **Do not build a general computer-use surface** on the strength of
  CUA card facts arriving in the protocol. Render the facts (brief
  A); a desktop-driving surface needs demand evidence we do not
  have, and the browser check already covers the verification case
  our users actually run.
- **Do not work around sdk#134** by editing the person’s
  `settings.json` or renaming their MCP servers to get a clean
  worker host. The refusal is upstream’s; until it moves, a worker
  host that must not see user MCP servers needs its own throwaway
  config home (which the issue shows works), not mutation of the
  person’s real one.
- **Do not close #146 or #157 from this research.** #146 awaits its
  reporter; #157 needs one question asked (§1.5). Research verdicts
  are not user confirmations.
