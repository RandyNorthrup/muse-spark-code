## 1. What is new, or what we had not read

### 1.1 The sandbox (the deep read the brief asked for)

**Modes and defaults [code].** `SandboxMode` is `read-only` (the enum
default), `workspace-write`, `danger-full-access`
(`codex-rs/protocol/src/config_types.rs:104`, read 2026-11-02 at the
clone HEAD above).

**Permission profiles [docs]** (`learn.chatgpt.com/docs/permissions.md`,
fetched 2026-11-02). A newer, beta system that does not compose with
`sandbox_mode`: built-ins `:read-only`, `:workspace`,
`:danger-full-access`, plus custom `[permissions.<name>]` profiles
combining filesystem rules (including deny-read and per-path write)
with network domain rules. Two honest caveats OpenAI states itself:
profile domain rules do nothing unless `features.network_proxy = true`
(or managed `[experimental_network]`) — without the proxy, "profile
domain rules do not restrict direct network access"; and enterprise
`allowed_permission_profiles` denies any profile not listed, including
future built-ins.

**Linux [code]** (`codex-rs/linux-sandbox/README.md`, read in full at
HEAD). The design inverted since the early Landlock-first descriptions:

- **Bubblewrap is the filesystem sandbox**: `--ro-bind / /` read-only
  root, writable roots layered with `--bind`, protected subpaths
  (`.git`, resolved `gitdir:`, `.codex`) re-applied read-only, and
  overlapping split-policy entries applied in path-specificity order
  (`/repo = write`, `/repo/a = none`, `/repo/a/b = write` all hold).
- **Seccomp in-process** after `PR_SET_NO_NEW_PRIVS`: restricted-network
  policies block network syscalls; even unrestricted-networking
  filesystem policies block `AF_VSOCK`; **all modes block `io_uring`**
  so socket-family rules cannot be bypassed.
- **Landlock is demoted to "legacy/backup utilities"** and is _rejected_
  for filesystem-restricted policies "because it cannot isolate
  app-server Unix sockets". `features.use_legacy_landlock` must be
  disabled on upgrade. This directly contradicts older third-party
  write-ups (several 2026-09 sources still say "Landlock + seccomp");
  the crate README at HEAD is authoritative.
- System `bwrap` on PATH _outside the current working directory_ is
  preferred; a bundled `codex-resources/bwrap` is the fallback, with a
  startup warning either when falling back or when user namespaces
  cannot be created. WSL1 is rejected up front (no user namespaces);
  WSL2 takes the normal path. Deny-read globs are expanded _before_
  launch (preferring `rg --files`, failing closed on other `rg`
  failures) and masked in the mount view — so a denied file created
  _after_ launch is not covered, the same timing limit the Windows
  docs state explicitly.

**macOS [code]** (`codex-rs/sandboxing/src/seatbelt_base_policy.sbpl`,
read in full). Deny-default Seatbelt profile explicitly derived from
Chrome's macOS sandbox policy (source links in the file header):
same-sandbox process ops, a long allowlist of `sysctl-read` names,
`/dev/null` write, OpenDirectory mach-lookup, POSIX semaphores, PTY
handling. Per-mode file rules are layered on this base by the
`seatbelt.rs` generator (not read line-by-line here — **[inferred]**
from the base file's shape).

**Windows [docs + code]** (`learn.chatgpt.com/docs/windows/windows-sandbox.md`,
fetched 2026-11-02; `codex-rs/mxc-sandbox/`, `windows.rs`,
`windows_mxc.rs` present at HEAD). Three implementations, in
preference order:

1. **`mxc` — Microsoft Execution Containers** (new; the headline
   change). Native process isolation shipping in Windows 11 24H2
   (build 26100.9278) and 25H2 (26200.9278). No administrator-approved
   setup, no additional Windows accounts, no local firewall rules.
   Enabled by `features.prefer_mxc = true`; testable per-command from
   CLI 0.162.0; enterprises can forbid it with
   `[windows] allow_mxc = false` in managed `requirements.toml`.
2. **`elevated`** — the legacy preferred fallback: one administrator-
   approved setup creating sandbox users and firewall rules; commands
   then run unprivileged. (This is the same shape as Muse Code's
   Windows sandbox setup — see §2.)
3. **`unelevated`** — restricted-token fallback: weaker network
   isolation, and it **does not support denied read paths** (stated by
   OpenAI).

The Windows design is the strongest in the field on paper. In practice
it is also where Codex hurts most right now (§1.9): a run of fresh
October–November 2026 issues reports MXC paged-pool leaks, elevated
setup granting ACEs on `C:\`, stale deny-read ACEs never revoked, and a
provisioning failure leaving the user profile at Low integrity. Any
lane that copies this design must budget for that failure class, not
only for the happy path.

**Why this matters beyond Codex.** Sandlock (Wang & Zheng;
arXiv:2605.26298, submitted 2026-05-25; abstract read in full
2026-11-02) **[paper]** independently lands on the same split Codex
uses: static policy compiled to kernel rules (Landlock/seccomp-bpf), a
narrow supervisor only for runtime-dependent decisions, TOCTOU-safe
`execve` argument inspection, ~5 ms startup, no root/namespaces/images
required. Pincer (Rathee et al.; arXiv:2610.02569, 2026-10-01; abstract
read in full) **[paper]** argues tool-call-layer defences (the
Codex/Claude "automode" pattern) need a resource-layer companion that
learns a per-person least-privilege policy. MOSAIC (Wu et al.;
arXiv:2607.02857, 2026-07-03; abstract read in full) **[paper]** is
the offensive counterpart: **96.59% of 2,525 CLI command-composition
trials succeeded** against five production agents under benign tasks,
with no injected instruction at all. Command _composition_, not prompt
injection, is the measured weak point — which is precisely what an OS
boundary, not a smarter prompt, contains.

### 1.2 Approvals: three layers, one retirement, one attack paper

- **Approval policy × sandbox are separate axes [docs]** and Codex says
  so repeatedly: the sandbox is what is _technically_ possible, the
  policy is when it must ask.
- **`approval_policy = "untrusted"` was retired and now prevents the
  client from starting [docs]** (`agent-approvals-security.md`
  migration section, fetched 2026-11-02). The replacement is a
  per-project `trust_level = "untrusted"` in user config, which also
  disables project-local configuration. Issue #39973 ("Retiring
  approval_policy=u​ntrusted without deprecation weakens the
  execution-approval boundary", open, 41 reactions) shows users felt
  this at upgrade time.
- **Guardian / auto-review [code]**: with
  `approvals_reviewer = "auto_review"` (`config_types.rs:177`,
  legacy alias `guardian_subagent`), a reviewer subagent decides the
  requests that would otherwise prompt (sandbox escapes,
  outside-workspace writes, network). The app-server README documents
  a denial circuit breaker (`TooManyDenials`, optionally surfaced as
  `turn.error.codexErrorInfo = "tooManyDenials"` with
  `auto_review.circuit_break_action = "strict"`); a core test names
  the "3 consecutive" denial warning
  (`guardian_subagent_notification_tests.rs`, grepped 2026-11-02). The
  draft's "90 s review timeout" came from a secondary source and was
  **not re-verified in Codex source in this run** — treat it as
  unconfirmed. The secondary report that auto-review became free for
  ChatGPT sign-ins on 2026-10-06 is likewise **[secondary,
  unverified against a primary source]**.
- **Managed human checkpoints [code]** (`codex-rs/app-server/README.md`,
  read): a managed `requirements.toml` prefix rule with
  `decision = "prompt-user"` _cannot_ be satisfied by auto-review or by
  session/persistent approvals — a fresh human decision is required,
  and with no capable client connected the command is rejected. This
  is the one approval idea in Codex we do not have an equivalent of
  (§2).
- **The attack on the third layer [paper, abstract read in full]**:
  Yang et al., "From Approval to Abuse" (arXiv:2610.22987,
  2026-10-16). Adversarial repository context steers an agent into
  _proposing_ a plausibly-justified but dangerously broad allow-rule;
  measured on production Claude Code and Codex CLI: agents elicited
  the target allow-rules in **58%** of instances; acquired rules
  covered **56.9%** of category capability tests; conditional on
  approval, silent goal completion in **47/58 (81.0%)**. Codex's Smart
  approvals (the agent proposes a `prefix_rule` during escalation,
  persisted to `~/.codex/rules/default.rules`) are exactly this
  paper's target shape. Our engine does not let the agent propose
  standing rules at all (§2) — that difference is load-bearing and
  must be kept.
- **The human side [paper, abstract read in full]**: Turan, "Oversight
  Has a Capacity" (arXiv:2606.08919, 2026-06-08). On 125
  hand-labelled adversarially-weighted actions, reviewers only
  moderately agree what is risky (Fleiss' κ = 0.52); modelling the
  reviewer as fatiguing makes realised safety an inverted-U in
  escalation rate, and enables a flooding attack. Honest limit,
  stated by the author: the inverted-U and flooding results are
  _modelling_ results motivating a human study, not human-study
  measurements.

### 1.4 App-server protocol vs our MSP/ACP split

Codex's `app-server` is a JSON-RPC thread/turn protocol (README read
**[code]**: `thread/start`, `thread/list`, `thread/read`,
`thread/memory/read`, read-state receipts with revision tokens,
`item/commandExecution/requestApproval`, `model/list`,
shutdown-admission errors). Three observations matter for us:

1. **It is a product protocol, not an editor protocol.** It carries
   Codex-specific concepts (memory versions, read receipts, Guardian
   errors, "Daybreak" choices). Our split — Muse Session Protocol to
   Muse Code, ACP to editors — keeps editor concerns in the open
   protocol and provider concerns behind `AgentHost`/`AgentSession`
   (`src/core/agent/agentBackend.ts`). Codex needs _both_: app-server
   internally, then a separate ACP adapter (§1.8) for editors.
2. **Capability-gated experimental surface.** Human checkpoints and
   read-state require `experimentalApi: true` at initialize;
   incapable clients simply never receive the requests, and commands
   that need them are rejected. That fail-closed capability pattern
   is worth copying for any future "must have a human" rule of ours.
3. **Lifecycle races are the tax.** The 0.166 notes fix "thread
   startup and shutdown races" and TUI reconnection. Our ACP agent
   (`src/acp/agent.ts:5173`, `session/new`) is one process per editor
   session with no daemon; the daemon-related issue cluster in §1.9
   is a direct consequence of Codex's richer lifecycle.

### 1.5 AGENTS.md, skills, custom agents, hooks

- **AGENTS.md [code]** (`codex-rs/core/src/agents_md.rs`): project
  root found by walking up to a `project_root_markers` entry
  (default `.git`); every `AGENTS.md` from root down to cwd is
  concatenated in that order; `AGENTS.override.md` is the preferred
  local override; `project_doc_fallback_filenames` and
  `project_doc_max_bytes` are configurable; an untrusted project
  loads no project docs. Our loader
  (`src/core/context/rules.ts:64`, `loadRuleFile`) prefers
  `AGENTS.md` then `CLAUDE.md` per directory and loads subdirectory
  files lazily on first touch — Codex's eager root-to-cwd walk is
  simpler but misses files outside the cwd chain. Open issue #12115
  ("Dynamically loading nested AGENTS.md", 127 reactions) asks Codex
  for exactly our lazy behaviour. `AGENTS.override.md` is the one
  Codex idea we lack (§3).
- **Skills [code]** (`codex-rs/skills/src/`): `SKILL.md` front-matter
  metadata, system skills embedded and installed to
  `CODEX_HOME/skills/.system` behind a fingerprint marker, explicit
  `$skill` mentions and implicit invocation detection from commands.
  Our format (`src/core/context/skills.ts:1`) is the same shape
  (front matter + body, catalogue in instructions, body on demand via
  `read_skill`). Codex adds _implicit_ skill access detection —
  inferring a skill from a shell command — which is convenient and,
  after Yang et al., also a place where untrusted text could pull in
  instructions. **[inferred]** We should not add implicit invocation
  without a provenance rule.
- **Custom agents / roles [code]** (`codex-rs/agent-roles/`,
  `codex-rs/core/src/agent/`): TOML-defined roles with discovery and
  a registry. Ours are Markdown agents
  (`src/core/context/customAgents.ts`) whose prompt, tools, model,
  effort and permissions narrow the parent's
  (`src/core/backends/modelapi/instructions.ts:216`). Functionally
  equal; TOML vs Markdown is a taste difference, not a capability
  gap.
- **Hooks [code]**: `HookEventName` at HEAD has **14** events
  (`codex-rs/protocol/src/protocol.rs:1786`: PreToolUse,
  PermissionRequest, PostToolUse, PreCompact, PostCompact,
  SessionStart, SessionEnd, UserPromptSubmit, SubagentStart,
  SubagentStop, Stop, Interrupt, **PreModelRequest,
  PostModelRequest**). Our import table still says "Codex's 12 hook
  events … rust-v0.160.0" (`src/shared/constants.ts:5248`,
  `AGENT_IMPORT_CODEX_EVENTS` at :5252) and lists 12. That is a
  **stale-constant finding**: the two model-request events are new
  since 0.160 and our importer cannot carry them. Our own engine
  fires 20 event names (`src/core/backends/modelapi/hooks.ts:47`),
  so the gap is in the _import mapping_, not in our hook surface.

### 1.6 Compaction: threshold-triggered there, economics-triggered here

Codex compacts when tokens pass a per-model
`auto_compact_token_limit` (`codex-rs/protocol/src/openai_models.rs:475`,
with a config override), building a replacement history around a
summarization prompt (`codex-rs/core/src/compact.rs`, read), with
PreCompact/PostCompact hooks and a remote v2 path. Users ask for
control they do not have: open issue #4106 ("Control over
auto-compaction parameters", 138 reactions).

Our Model API backend instead decides on economics
(`src/core/backends/modelapi/autoCompact.ts:84`): compact only at a
todo-completion transition (or near-window/overflow), only when the
cache-write debt breaks even within the measured remaining horizon,
with a cooldown (`AUTO_COMPACTION_COOLDOWN_REQUESTS = 2`,
`MIN_OCCUPANCY = 1/2`, `NEAR_WINDOW = 9/10`,
`src/shared/constants.ts:3773`). On top of that, ObservationPack
(`src/core/backends/modelapi/observationPacking.ts`) keeps large tool
outputs out of the request entirely after two whole sends — a
mechanism Codex does not have; its closest equivalent is output
truncation. The SoL-Pi numbers in our September read (Codex at 3.054B
tokens / $1,787 for a 34.74 score where Pi used 2.154B / $1,339 for
44.83) are old and **[secondary]** now, but the architectural point
stands: threshold compaction pays the summary cost whether or not it
saves money; ours refuses when it would not. Verdict in §2: **ours is
better** on the Model API backend; on the Muse Code backend
compaction is Muse Code's, and there we are **equal** by definition.

### 1.7 Review, cloud, exec, desktop and IDE

- **Review.** Codex offers `/review` presets and a review pane with
  per-hunk stage/revert and inline comments **[docs]**, plus GitHub
  `@codex review` and a Security Review **[docs]**. Ours: a read-only
  built-in Reviewer (`src/core/backends/modelapi/reviewer.ts`, tools
  limited to readers + diagnostics), git-material collection
  (`src/host/review/reviewCollector.ts`), Plan-mode hold and edit
  review, and a Muse Code reviewer bundle
  (`src/host/review/museCodeReviewer.ts`). We lack the per-hunk
  stage/revert pane and the hosted PR reviewer; the September
  landscape already ranked "no review workflow" as gap #4 and M70
  closed only the first half. Issue #47577 notes fork PRs were
  silently ignored by `@codex review` after 2026-09-20 — a reminder
  that a hosted reviewer is also a hosted _trust_ decision
  (PLAN.md D102 covers our side: no outside code runs without
  vetting).
- **Cloud [docs + code].** Codex Cloud runs tasks in isolated
  containers with a two-phase model (setup with network + secrets,
  then offline agent phase), best-of-N attempts and `codex apply`
  (`codex-rs/cloud-tasks/src/lib.rs:607`, `run_apply_command`). Our
  equivalents are deliberately local: best-of-N in worktrees
  (`src/core/bestOfN/bestOfNRunner.ts`), teams, schedules, and the
  home node (M110) for the person's own machine. There is no hosted
  container tier, by product shape rather than by oversight: we are
  an unofficial client for other people's models and hold no
  credentials to spend in a cloud (AGENTS.md rule 8). Verdict:
  **deliberately not** (see §2); the two-phase secret discipline is
  still worth mirroring in schedules and headless runs.
- **Exec / SDK.** `codex exec --json` emits JSONL with an optional
  `--output-schema` (`codex-rs/exec/src/cli.rs:54`,
  `event_processor_with_jsonl_output.rs`). Ours: `exec` with
  `text|json|jsonl` output (`src/runtime/exec/execArgs.ts:41`),
  versioned schemas (`src/runtime/exec/outputSchema.ts`), a hard run
  budget and per-attempt ledger. Functionally **equal**; ours is
  stricter about money (D65) and Codex's is stricter about nothing
  in particular — its budget story is the account's rate limit.
- **Desktop app and IDE extension [docs/issues].** The ChatGPT
  desktop app (parallel chats, worktrees, scheduled tasks, built-in
  browser, skills) and the VS Code extension are closed-source
  clients of app-server. Their most-reacted bugs are operational:
  macOS `syspolicyd`/`trustd` runaway (#25719, 455 reactions), VS
  Code UI failing to start (#56655, #56691), queued follow-ups
  vanishing (#45019, #44781). Our desktop (`desktop/`) and companion
  are earlier; the lesson is not "build a bigger app" but "a daemon
  plus three clients multiplies lifecycle bugs" (§1.4).
- **Remote/phone.** Codex offers phone control and remote pairing;
  recent issues (#48774, #48555) show pairing loops after account
  switches. Ours: the connector runs on the person's own PC (D240)
  and the home node serves the LAN. Different trust shape; no
  action.

a checklist against our ACP agent (`src/acp/agent.ts:5`, D62):
subagent sessions, steering and async questions are the three to
compare line by line in a follow-up lane (§4, lane D). Our agent
already defers Muse Code questions to a portable registry (M112)
and runs teams over ACP; whether its subagent surface matches the
"native session per child, permissions routed to the root" shape
was **not verified in this run** and is stated as an open question,
not a gap.

"the agent escaped" but "the sandbox broke my machine or my build"
(#13183 .NET builds, #3141 GPU access, #10695 keychain access from
skills). Any confinement lane of ours must ship with an equally
serious unbreak-my-build story (§4, lane A).

**Where Codex is strongest**, on this evidence: (1) the OS sandbox
design itself — three real kernel boundaries with a coherent policy
model on top; (2) the approval layering (sandbox vs policy vs
reviewer vs managed human checkpoint) — the clearest vocabulary in
the field; (3) breadth of supported enterprise deployment (managed
`requirements.toml`, Vertex/Bedrock catalogs, FedRAMP routing in
0.166). **Where it is weakest**: operational reliability of that
same stack on Windows, lifecycle complexity (daemon + app-server +
three clients), and missing table stakes its users beg for (undo,
LSP, workspace scoping) that smaller products already ship.

## 3. What to do, ranked — and what not to do

Ranking weighs value to a person first, then strength of evidence,
then effort. "Evidence" names the weakest link honestly.

### Do

1. **Confine the Model API shell (Linux first).** Value: closes the
   only row where we are unambiguously _worse_ than Codex and Claude
   Code, and the exact hole MOSAIC measures (96.59% composition
   success needs no injection — it needs a shell the OS does not

   silently widens it.
2. **Add the managed human checkpoint.** Value: gives a person (and
   an enterprise admin) a rule class that _no_ automation can
   satisfy — the missing top rung above Bypass. Evidence: **strong**

   model).
3. **Harden the allow-rule surface we already have, and keep the

   but our session rules ("Allow for This Session", exact command

   persistence and deserve the paper's mitigations: show the rule's
   blast radius (what else the pattern matches) before it is saved,
   and never offer a session grant for a command whose text came
   from untrusted content in the same turn. Evidence: **strong**

   Lane C. No new decision: D24/D48 already own these surfaces; the
   lane records the paper in their certification notes.
4. **Refresh the Codex interop table (hooks 12→14, AGENTS.override,

   Evidence: **strong** (enum read at HEAD). Effort: **small** for
   the table; the ACP audit is **medium** and may spawn its own lane.
   Lane D. No decision needed unless the audit finds a protocol gap
   (then record it under D62/M112).
5. **Give the person the compaction knobs Codex users beg for —
   as display first, settings second.** Value: #4106 (138 reactions)
   plus our own opacity (three constants, no surface). Evidence:
   **medium** (issue demand is real; the right _shape_ of control is

   **small** for "show why compaction did/didn't run" (the decision

   defer person-set thresholds until a real-life run shows someone
   reaching for them. No separate lane: fold the display into lane
   D's scope only if it stays small; otherwise record as an open
   question for the synthesis lane.

### Do not do

- **Do not let the agent propose standing allow-rules** (Codex Smart
  approvals shape). Yang et al. is a direct measurement against it,
  and our exact-line session rules already give the fatigue relief
  without the elicitation surface.
- **Do not copy the persistent auto-start daemon.** #48195 (207
  reactions) and the 0.157 Windows startup failure (#48043) show the
  consent and reliability cost. Our per-session processes are slower
  to warm and vastly easier to reason about; if warm-start ever
  matters, it must be opt-in and person-visible.
- **Do not build a hosted cloud tier to match Codex Cloud.** We hold
  no credentials to run one (AGENTS.md rule 8), the product is
  unofficial (rule 11), and the two-phase secret discipline — the
  only part worth having — ports to schedules/exec without a cloud.
- **Do not chase Windows MXC.** It needs Windows 11 24H2/25H2 builds
  most machines do not have yet, its current issue list includes
  kernel-pool leaks, and our Windows sandbox story is Muse Code's
  (elevated setup, same as Codex's fallback). Revisit only when MXC
  is the _default_ Windows sandbox and Muse Code adopts it.
- **Do not add implicit skill invocation** (inferring `$skill` from a
  shell command) without a provenance rule. After Yang et al. and
  MOSAIC, "untrusted text caused instructions to load" is a finding,
  not a feature.
- **Do not retire a config value the Codex way.** The `untrusted`
  removal (client refuses to start, #39973) is the anti-pattern:
  our rule stays "every refusal is said, never silent", with a
  migration message, not a dead client.
