## The rules, verbatim (all read 2026-11-02)

**R1, third-party sign-in and plan credentials.**
<https://code.claude.com/docs/en/legal-and-compliance> (no page date shown):
"Anthropic does not permit third-party developers to offer Claude.ai login
into their own applications, or to route requests through Free, Pro, Max, or
Ultra plan credentials on behalf of their users. Moreover, developers may not
collect, store, or intermediate Claude.ai credentials or session tokens —
sign-in to a Claude account must complete through Anthropic's own flow."
"Anthropic reserves the right to take measures to enforce these restrictions
and may do so without prior notice."

**R2, running Claude Code in a product** (same page, "Can customers offer
Claude Code in their products?"): "The Claude Code binary must not be
modified. Claude Code must be installed and run as published by Anthropic, and
customers may not remove, disable, or restrict any authentication method built
into it (including methods that permit signing in with a Claude account or
the user's own API key)." "Each end user must authenticate with their own
Anthropic API key, Claude subscription plan credentials, or 3P inference
provider credential (Amazon Bedrock, Google Cloud's Agent Platform, Microsoft
Foundry)."

**R3, the Agent SDK.** <https://code.claude.com/docs/en/agent-sdk/overview>:
"Unless previously approved, Anthropic does not allow third party developers
to offer claude.ai login or rate limits for their products, including agents
built on the Claude Agent SDK." Branding: allowed "Claude Agent", "preferred
for dropdown menus"; not permitted "Claude Code" or "Claude Code Agent";
"Your product should maintain its own branding and not appear to be Claude
Code or any Anthropic product."

**R4, the Usage Policy.** <https://www.anthropic.com/legal/aup>, effective
2026-11-12, under "Do Not Abuse Our Platform", "This includes using our
products or services to:"

- "Coordinate malicious activity across multiple accounts, or create multiple
  accounts, to avoid detection, circumvent product guardrails, or generate
  identical or similar inputs that otherwise violate our Usage Policy"
- "Intentionally bypass or interfere with capabilities, restrictions, or
  guardrails established within our products, including by circumvention of
  the account sign-up or log-in process or by instructing the model to produce
  harmful outputs (e.g., jailbreaking or prompt injection), without prior
  authorization from Anthropic"
- "Resell, proxy, or otherwise provide access to Claude through unauthorized
  means, including services that route requests through consumer
  subscriptions or misrepresent the product or client being used"

**R5, authentication precedence.**
<https://code.claude.com/docs/en/authentication>: cloud provider credentials;
`ANTHROPIC_AUTH_TOKEN`; `ANTHROPIC_API_KEY`; `apiKeyHelper`;
`CLAUDE_CODE_OAUTH_TOKEN` ("A long-lived OAuth token generated by `claude
setup-token`. Use this for CI pipelines and scripts"); Anthropic profiles and
federation credentials; "Subscription OAuth credentials from `/login`. This is
the default for Claude Pro, Max, Ultra, Team, and Enterprise users." And: "If
you've set the `CLAUDE_CONFIG_DIR` environment variable, Claude Code keeps the
`.credentials.json` file under that directory instead ... and keys the macOS
Keychain entry to that directory too".

**R6, plan-token variables.** <https://code.claude.com/docs/en/env-vars>:
`CLAUDE_CODE_OAUTH_TOKEN` ("OAuth access token for claude.ai authentication.
Alternative to `/login` for SDK and automated environments ... Generate one
with `claude setup-token`"), `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` ("OAuth refresh
token for claude.ai authentication. When set, `claude auth login` exchanges
this token directly instead of opening a browser. Requires
`CLAUDE_CODE_OAUTH_SCOPES`"), `CLAUDE_CODE_OAUTH_SCOPES`. The adapter's
`src/auth-status.ts` also names `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`.

What the person loses with the keyed preset's own folder: their user-level
Claude Code settings, skills, agents, commands, plugins, user `CLAUDE.md`
memory and user MCP servers in that worker. What is kept: the project's own
`.claude/` folder and `CLAUDE.md`, which Claude Code reads from the workspace.
Without a key the preset reads the person's own configuration (where a Console
login or an `apiKeyHelper` lives) and the adapter's guard refuses a plan.

Other vendors' account records, left as they are (their terms were not re-read
here, so nothing changes them): `on` for the Mistral, DeepSeek and Z.ai APIs
and same-tenant Azure; `notOffered` for Google's consumer plan, Z.ai's coding
plan and the Claude plan; `confirm` for every other row (Meta, OpenAI incl.
the ChatGPT plan, Google's API and Vertex, GitHub, xAI, Groq, Mistral's
consumer plan, OpenRouter, Together, Fireworks, Hugging Face, cross-tenant
Azure), as in `src/core/providers/accountPolicy.ts`.

## Proof with no model request (2026-11-02, rig linuxlt)

Expected model requests: 0. The real adapter `@agentclientprotocol/claude-agent-acp`
0.100.0, installed in a scratch folder, driven over ACP with
`--hide-claude-auth`, no key, an empty workspace, in a clean environment (no
`CLAUDE*`/`ANTHROPIC*` variables) on a machine whose `claude` is signed in on a
plan: `initialize` listed no auth method; the adapter's identity push reported
a plan account; `session/new` answered `-32000 "Authentication required: This
integration does not support using claude.ai subscriptions."` with
`data: {"reason":"claude_subscription_not_supported"}`. No prompt was sent;
the adapter emitted 0 usage updates and 0 message chunks: 0 model requests.
`claude auth status` with an empty `CLAUDE_CONFIG_DIR` and no key:
`loggedIn: false, authMethod: none`; with a placeholder key:
`authMethod: api_key, apiKeySource: ANTHROPIC_API_KEY`. The plan login was not
reachable from that folder.

## What only Anthropic can answer (the lead takes these to Anthropic)

1. **The tension between R2 and R3.** The legal page says a product running
   Claude Code may not "remove, disable, or restrict any authentication method
   built into it (including methods that permit signing in with a Claude
   account ...)"; the Agent SDK page says third parties may not "offer
   claude.ai login". Our preset runs the adapter with `--hide-claude-auth`,
   which hides and refuses the plan login. We read R3 and R1 as governing an
   Agent SDK product and do not settle the tension.
2. Whether a person's own `CLAUDE_CODE_OAUTH_TOKEN` in their own environment,
   passed to their own Claude Code, counts as "route requests through ...
   plan credentials on behalf of their users" when the product is a
   third-party app. We never pass it either way.
3. Whether moving between a person's several Anthropic API organisations on a
   limit is allowed at all; we ask the person first.

## Upstream issue (agentclientprotocol/claude-agent-acp; the lead files it)

Read at v0.100.0 (`981bf9a`, 2026-11-02), `src/hide-claude-auth.ts` and
`src/auth-status.ts`.

> **`--hide-claude-auth` lets a claude.ai plan pay through an OAuth environment token**
>
> `billsClaudeSubscription` returns `false` as soon as `account.tokenSource` is
> set, and `holdsNonSubscriptionCredential` returns `true` for the same case.
> The CLI sets `tokenSource` when `CLAUDE_CODE_OAUTH_TOKEN` (or
> `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`) pays for the turn —
> `auth-status.ts` says so: "the CLI sets it to the OAuth token's origin
> (`CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`, …)".
> That token is a claude.ai plan token: Anthropic's docs generate it with
> `claude setup-token`, "OAuth access token for claude.ai authentication". So
> a user who exported it for CI gets sessions and turns billed to their plan
> under `--hide-claude-auth`, with the guard passing.
>
> Expected: under the flag, a `tokenSource` naming an OAuth token
> (`CLAUDE_CODE_OAUTH_TOKEN*`) counts as a subscription and is refused with
> `claude_subscription_not_supported`, as a `/login` subscription is; a bearer
> `ANTHROPIC_AUTH_TOKEN` (gateway) keeps passing. Alternatively, strip
> `CLAUDE_CODE_OAUTH_TOKEN*` and `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` from the
> SDK's environment when the flag is on. The fail-open when `accountInfo`
> cannot be read is a second, smaller gap worth closing the same way.
