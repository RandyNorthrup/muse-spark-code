## Scope and required integration adapters

This base contains lane 0c and the first S commit, but no M96 `teamTools.ts`,
`roster.ts`, `teamMcpServer.ts` or worker runtime. These new files contain T2's
compositional regions only. Their missing runtime sides are required injected
dependencies, never production fakes:

- `createSchedulerTeamTools` receives M96's five base tools. It preserves the
  base delegate envelope, required fields, schema bounds, command id, dry run,
  plan and pipeline while validating and defaulting the scheduler fields. The
  M96 delegate adapter must validate its base fields and submit the whole batch
  to `TaskBoard` before any worker starts. Its consent, trust, role/depth/slot
  checks and command-id retry handling stay there. Tests use the real board for
  local keys, dependency defaults and atomic cycle/unknown/foreign-edge refusal.
- `TeamMergeEnqueue` is the required lane Q adapter. It receives the parsed
  `task_id` and `on_conflict` (default `rework`), checks review, workspace and
  permission admission, and returns the queued task's one-based position. T2
  validates the receipt and never calls the base immediate merge. Landing's
  approval, protected paths, checks and paid policy remain Q/M96's responsibility.
- `TeamRescheduleBoard` receives only a validated board change. It can be the
  real synchronous `TaskBoard` or an adapter which journals the change and
  acknowledges asynchronously. T2 awaits the acknowledgement, publishes live
  state, and invokes no worker, pool, approval or paid request. S/X2 must keep
  this adapter board-only; the later scheduler sweep/event uses the new order.
- `SchedulerRosterSource.read` supplies S/C/Q snapshots: board, attempt leases,
  merge positions/reasons and scheduler events. T2 validates and appends them
  as JSON data to roster, delegate, collect and reschedule answers. The opaque
  base result remains exact, including headroom, budgets, records and paging.
  Missing/malformed snapshots are errors, with no empty-success fallback.
- Each conversation gets its own `SchedulerStateNote`, fed only accepted state
  events from the scheduler. All eight state event kinds are supported. Usage
  stays in tool answers, recent duplicate deliveries are suppressed across
  drains, and the pending queue is bounded with an explicit error on overflow.
  Notes are one JSON line of data for M96's request-tail integration; no turn
  starts and no instruction prefix is rewritten.
- `teamServerToolList` freezes metadata for one session and marks roster and
  collect read-only. The orchestrator gets six tools; a delegating worker gets
  roster, delegate, collect and cancel only. M96/X2 supplies per-session bearer
  tokens, caller scoping, transport and registration, and never invokes these
  factories in single-model mode. No activation/backend/bundle wiring changed.

The owner's defaults-on/ask-once/shared-budget ruling is preserved by the injected
M96 runtime; T2 adds no paid admission route. No UI key, manifest command, setting,
script, dependency or escape hatch was added. Existing `TEAM_MODEL_TEXT` is reused.
README, CHANGELOG and the milestone-wide record are X2-owned and were not edited.
For X2's `[Unreleased]` note: "Team scheduler tools accept dependencies, priorities,
sizes and planned writes; merge queues reviewed work and reports its position;
reschedule changes the board without starting work; live scheduler data stays in
tool answers and state-change tail notes."
