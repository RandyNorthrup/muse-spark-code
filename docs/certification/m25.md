## Findings recorded during the milestone

- The attachments of a refused send: the host takes the images out of its
  store in `buildParts` before anything that can still throw (the context
  part, the host start, `submit`). A refusal before that point (not signed
  in, no folder, the host not starting) leaves them held, and the chips now
  come back; a failure after it drops the bytes, so a chip restored then
  would name an image the host no longer has and a resend would go without
  it. The companion change is host-side, in `send()`, outside this
  milestone (see the report).
- `turnAccepted` racing `turnCompleted` exists on the host too: `send()`
  sets `activeTurnId` after `submit` resolves, after a fast turn's
  completion was already handled, so the next message tries to steer a
  finished turn (it falls back to a new turn with a log line). Host-side,
  outside this milestone.
- VS Code keeps a webview's `setState` value across a reassignment of
  `webview.html` (the crash screen's Reload) and across a window reload for
  serialised panels, and JSON-serialises it: keys whose value is undefined
  vanish, which is why the row schemas mark those fields optional.
- A sidebar view's state can come back after a window reload too, while
  its host process is new: the `surfaceState` check drops such a
  conversation (no live session) instead of showing it as if it were live;
  the ten-minute rule (M6) resumes it through `historyLoaded` as before.
- The first render of a restored document is the "Connecting…" shell, which
  cannot crash on the restored rows, so the store notes the first render of
  the conversation itself, not of the shell; the loop breaker depends on it.
- The row types are now inferred from the zod schemas (fields that may be
  absent are optional), so a field added to a row cannot be forgotten by
  the restore validation.
- `SignIn` keeps its own polite region on the waiting screen and an alert
  on the error screen: they never render together, so nothing is read
  twice there.
