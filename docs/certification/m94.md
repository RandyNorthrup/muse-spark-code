### What was sent

- **The requests.** The 10 pairs are 5 TypeScript and 5 Python files of 34
  generated functions each. The cursor sits 40% into a statement in the last
  40% of the file, and the rest of that line is the hole. The second request
  of each pair has typed the hole's first three characters. The 10
  multi-line requests use files of 64 functions, with one function body as
  the hole: half put the cursor after the block opener, half on the blank
  indented line below it. Each carries two context snippets, the type's
  definition and a helper file, sorted by path.
- **D73's shape, checked on every body sent.**
  - `POST /responses` with `stream: true` and `store: false`;
  - no `tools`, `tool_choice`, `include` or `previous_response_id`;
  - `reasoning: {"effort": "minimal"}`, with no summary;
  - `prompt_cache_key` `muse-spark-tab-<digest of model and instructions>`
    and `prompt_cache_retention` `in_memory` (the setting's default).

  The client's body type still requires the left-out fields (lane C makes
  the summary optional). So the probe's `fetch` swaps the exact body the
  client serialised for the D73 body, and refuses any other.

- **Output caps.** The probe allowed 1,024 tokens (fast) and 2,048
  (multi-line), so the reasoning it measures is not cut short. D73's planned
  128 and 512 are what it is setting.
- **The instructions** are the first draft of `TAB_MODEL_TEXT.tabSystem`.
  They are lane 0's system text plus two sentences: one names the tags, which
  lane 0's text calls only "the reply tags", and one says where the
  completion starts.

  > You are Tab, an inline code completion engine. Complete the code at the
  > marked hole: output only the missing code, between the reply tags, with
  > no explanations, no code fences and no repetition of the surrounding
  > text. Reply with exactly `<COMPLETION>`, then the missing code, then
  > `</COMPLETION>`, and nothing outside them; if nothing belongs at the
  > hole, reply `<COMPLETION></COMPLETION>`. The completion starts at the
  > exact character where `{{FILL_HERE}}` stands and the suffix follows it
  > directly, so never repeat the end of the prefix or the start of the
  > suffix, and keep the file's indentation.

- **The user message** is lane 0's `tabUserTemplate` filled in, followed by
  one line that bounds the mode. That line comes after the suffix, so it
  never breaks the cached prefix:
  - fast: "Complete only the rest of the current line, or at most 3 lines.";
  - multi-line: "Complete the code block at the hole, at most 16 lines."

- **What the planned caps would have done.** 128 tokens would have cut 19 of
  the 20 fast replies; the smallest fast output was 125. 512 would have cut
  3 of the 10 multi-line replies.
- **The multi-line cap follows the plan's rule (p99 reasoning plus the
  allowance).** Its p99 is the runaway that showed nothing after 33 s. A
  lower cap, such as 1,536, would end runaways sooner and spend less on them,
  at the cost of cutting about one multi-line reply in ten. That is the
  lead's engineering call.
- **The timeout covers the slowest capped request.** At `multi-07`'s rate
  (2,048 tokens in 33 s), a request that reaches the 2,560 cap ends in about
  41 s, under 67 s. So the backstop never cuts a request that would still
  report usage.
- **The debounce rule changed after the run (disclosed).** The rule written
  before the run kept 350 when the median plus 350 fit under the ceiling.
  Otherwise it shortened the debounce to fit, but never below 250 ms, so at
  this median it gave 250. At a 3.8 s median that saves 100 ms of about
  4.1 s, while adding billed requests that are never aborted.
  The probe now carries the corrected rule (`debounceFor`): shorten only when
  a debounce of at least 250 ms then fits under the ceiling, and otherwise
  keep 350. Recomputed from the run's recorded data, it gives 350.

### Findings for lane C

1. **Name the tags in the instructions.** Lane 0's system text does not name
   them. With the probe's sentence, every reply that had text was strictly
   inside them.
2. **Fix the leading whitespace at block holes.**
   - Cursor at the end of a block-opener line: 4 of the 5 TypeScript replies
     left out the leading newline and started with the indented line.
     Inserted as is, they would join that line to the `{`.
   - Cursor on a blank indented line: 2 of the 4 Python replies with text
     repeated the indentation already typed.

   The reply's assembly needs to add the newline after a block opener, and
   to strip indentation the cursor's line already has.

3. **Trim a trailing newline in fast mode.** `fast-05b`'s completion ended
   in a newline inside the tags.
4. **Show the suggestion when the close tag arrives.** Do not wait for
   `response.completed`, which can come seconds later (`fast-06a`: text at
   2.9 s, completed at 15.0 s). The ledger's usage still comes with the
   terminal frame.
5. **Two order notes.**
   - The mode's bound is a line after the suffix, which lane 0's template
     has no slot for.
   - The template puts the file header before the snippets, while D73 orders
     the snippets first. This makes no difference to the cache for
     consecutive requests in one file.
