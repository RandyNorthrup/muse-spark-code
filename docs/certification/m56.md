## What was read

- **VS Code.** `src/vs/workbench/api/node/proxyResolver.ts` at tag 1.125.0
  (the manifest's floor, `@vscode/proxy-agent` ^0.42.0), and the installed
  1.139.0's `extensionHostProcess.js` and `node_modules.asar`. Both replace
  the extension host's global `fetch` (`createFetchPatch`,
  `http.fetchAdditionalSupport`) and global `WebSocket`
  (`createWebSocketPatch`, added in proxy-agent 0.39.0,
  `http.webSocketAdditionalSupport`). Each request gets the proxy for its
  URL, proxy authentication, `http.noProxy`, and the operating system's
  certificates (`http.systemCertificates`), all on by default. So the
  extension needs no proxy client of its own.
- **Muse Code 1.3.0's binary.** It names `HTTPS_PROXY`, `HTTP_PROXY`,
  `ALL_PROXY` and `NO_PROXY` in both cases, and `SSL_CERT_FILE` and
  `SSL_CERT_DIR` beside rustls-native-certs' "failed to read PEM from
  file". It also calls Windows' `CertEnumCertificatesInStore`. Its
  settings keys include `endpoint_transport.proxy`, and its policy plane
  has `execution.approval_modes` and `execution.network_sandbox_modes`.
- **`muse serve --help`, `muse config status`, a wrong `--sandbox-network`.**
  A wrong mode exits 2: "--sandbox-network expects one of
  restricted|enabled|proxy-only". `config status` prints the managed
  planes. With every proxy variable pointed at a recording proxy it made no
  connection. It has no `--json` (exit 2).
- **Meta's docs** (the saved copies of prompt-caching, protocols/responses,
  the Responses schemas, count-input-tokens and pricing-rate-limits):
  "Use one stable key per shared prefix … Don't over-partition: unique keys
  per user or per session lower hit rates". `prompt_cache_retention` is
  `in_memory` or `24h`, "a hint, not a guarantee", and the guide says
  "Set '24h' retention for bursty workloads". The pricing page has one
  cached-input rate.
