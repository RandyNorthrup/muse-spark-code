# M75: paired efficiency evaluation

Recorded 2026-09-28 on branch `feature/m75-eval`, from main `c42c4d5f`.
PLAN.md D49 (the M75 section and the "Measured first" rule) and D48's
paid rules.

## The request

M75 is built first in wave 3 so that M73 and M74 can prove their
token-saving mechanisms against it before they ship. Its scope:

- a task set of repository fixtures with verifiers, in accept and
  held-out splits;
- paired runs with and without a mechanism, on the contributor model on
  the Model API (Muse Code's harness is not ours to vary);
- capability floors fixed in advance, with tokens, cost and the pass
  rate recorded, and attempts counted from the trace;
- a report in `docs/certification/`.

Runs follow the live-spend rules: an empty workspace, the contributor
model, counted and reported.

## The draft, reviewed

A Muse Code instance (contributor model) built a first draft,
`77ddd012`. Its sandbox blocked several checks, so its gate claims were
unverified. The review found it did not meet the scope:

- **It did not measure the extension's harness.** It drove a tool loop
  of its own with three file tools of its own, and a mechanism was a
  string appended to its instructions. M73 (observation packing) and
  M74 (compaction) are changes inside `ModelApiHost`, which that loop
  never ran, so neither could have been measured with it.
- **No workspace.** Fixtures lived in a `Map`, which the draft counted
  as the live rule's empty workspace. The fixture code could not run
  either: `main.js` mixed `require` with `export`.
- **String verifiers.** A right fix spelled differently failed, and a
  wrong one could pass (`' ? '` anywhere satisfied the null guard).
- **Attempts from the driver's own count**, not from the trace.
- **The key outside the live-test pattern.** `--live` read
  `MUSE_SPARK_EVAL_KEY` in a Node script compiled into a temporary
  folder inside the checkout, not through the repo's opt-in live test
  and its key handling.
- **A fake run committed as the baseline.** The committed
  `m75-baseline.json` and `.md` were a fake-API run (10/10 by
  construction, $0.0000), presented as the baseline.
- **A secret finding in its history.** Its fixture key
  (`apiKey: 'sk-live-…'`) is gitleaks' `generic-api-key`, so
  `security:secrets` failed over the branch's history although the
  draft's record said gitleaks passed. The fixture now uses
  `'hardcoded-demo-key'`, which gitleaks leaves alone, and the unpushed
  branch was folded into one commit so the draft's key never enters the
  history; nothing was allowlisted.

The review kept the task ideas, the splits, the floors and the report
shape, and rebuilt the rest.

## What was built

- **Task set** (`src/core/eval/tasks.ts`): ten ES module fixtures, six
  accept and four held-out, each with one planted defect (a loop bound,
  a null guard, a missing `await` on a read, a wrong import path, a
  hardcoded key, an empty average, loose equality, a timer never
  cleared, a text sort, a floating write). Each task's verifier is a
  Node module that imports the fixed files and asserts what they do.
  Task shapes are a zod schema; fixture paths are checked before they
  are written.
- **Folders and verifier** (`src/core/eval/workspace.ts`): a fresh
  folder under the system's temporary folder per task and arm (its
  canonical path), holding the workspace with the fixture files only
  and, beside it, the verifier. The verifier runs as its own Node
  process with an empty environment (on Windows libuv adds back only
  what a process needs to start), a 20 s limit, and its failure kept
  without stack frames or the temporary path.
- **The trace** (`src/core/eval/wire.ts`): the run's `fetch`. Every
  request is recorded with its method, path, model, status and the
  usage Meta returned (read from a copy of the stream with the
  existing `parseSse` and `usageSchema`). Attempts are the
  `POST /responses` sent, retries and any call a mechanism adds
  included. It refuses without sending a model call on any model but
  `muse-spark-1.3-contributor`, any other host, and everything once
  the run's estimate passes $0.50.
- **One turn on the harness** (`src/core/eval/driver.ts`): a
  `ModelApiHost` over the task's workspace, Auto mode, the task's
  prompt as the user's message. A card is allowed once, a question is
  answered "proceed" (`MODEL_TEXT.evalClarification`), and no paid
  feature is on; the paid-use popup is answered no, and a paid use
  that happens anyway is counted. Nothing from the owner's profile
  reaches the prompt: no personal skills, memory or hooks. A mechanism
  is an `EvalHostChange` over the host's dependencies. A shell command
  the model runs is allowed once, in the task's folder, as the owner's
  user, as in the Model API sweep; the verifier runs the model's code
  the same way. Neither is a sandbox, which is why the fixtures are
  throwaway and the run is opt-in.
- **Paired runner** (`src/core/eval/runner.ts`): each task on every arm
  before the next task, then per-split summaries, the floors and the
  verdict. A task passes only when its turn completed, its verifier
  passed, nothing was refused and no paid use happened. The report is
  committed, so the task's temporary path (under the owner's profile)
  is masked as `<task>` in every failure it keeps.
- **Report** (`src/core/eval/report.ts`): zod schemas, JSON and
  Markdown, with a mechanism-against-baseline table per split.
- **Live run** (`test/e2e/eval.live.e2e.test.ts`,
  `npm run test:e2e:live:eval`): opt-in with `MUSE_LIVE_MODEL_API=1`,
  the key in `MUSE_LIVE_MODEL_API_KEY` removed from the environment when
  the file loads, as the Model API sweep does. `MUSE_EVAL_TASKS` picks
  tasks and `MUSE_EVAL_REPORT` names the report's path. It checks that
  no log line, task folder or report holds the key.
- **Shared helpers**: `listWorkspaceFiles` (core) and `filesUnder`
  (`test/unit/helpers/temporaryFolders.ts`) now serve both the sweep and
  the evaluation; `fakeModelApiClientSettings` lets a test put the fake
  API's client behind the trace.

The draft's `scripts/eval-baseline.mjs`, `test/unit/eval/baselineEntry.ts`,
its knip entry and `npm run eval:baseline` were removed. No setting,
command, panel string or paid feature was added, so nothing is
translated.

- `evalDriver.test.ts` (7): a read-edit turn on the harness with every

## The live run

2026-09-28, Windows 11, through the owner's key wrapper (the key
decrypted into the child's environment only and filtered from its
output), `MUSE_EVAL_TASKS=accept-off-by-one,accept-await-read`,
baseline arm only, `muse-spark-1.3-contributor`, each task in a fresh
temporary workspace. Expected 6 to 12 model calls; counted from the
trace:

| Task              | Pass | Model calls | Requests | Input (cached) | Output | Cost    |
| ----------------- | ---- | ----------- | -------- | -------------- | ------ | ------- |
| accept-off-by-one | yes  | 3           | 3        | 7616 (4706)    | 275    | $0.0004 |
| accept-await-read | yes  | 3           | 3        | 7548 (2417)    | 249    | $0.0006 |

Total: 6 model calls in 6 requests (no retries, nothing refused),
$0.0009, 18 s. Each turn read the file and edited it (two tool calls, no
card). No key in the log, the task folders or the report. The verdict
is `incomplete`: the accept floor held at 2/2, and the held-out split
did not run. The report is [m75-baseline.md](m75-baseline.md) and
`m75-baseline.json`. The full ten-task baseline is the next live run.
