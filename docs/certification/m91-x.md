Proven here, by fake-only unit suites plus real local child runs on this
rig (macmini, node v24.21.0): each cline row's stdin shape against the
doc's own examples, each documented output's answer, the engine invariants
over the 9 new rows (the property suite runs them automatically), the
child lifecycle (start, timeout kill, crash, kill on dispose), the
refuse-when-runtime-absent reasons, Cline discovery per platform rules,

continuations), realpath confinement of plugin paths, native Windows
dispatch, the D6 bundle placement of the child entry (the host spawns
`-e <source>` today; a dist file is lane W's call), and the full
`npm run quality`.

## Open points for the lead (defaults chosen, each cited)

1. Cline stdin beyond the doc's examples (taskMetadata, model, attachments,
   preCompact metrics) is never sent; those fields are absent, not guessed.
2. A resumed Cline task maps to SessionStart (TaskResume is explicit).
3. TaskCancel→SessionEnd and Notification ignore `cancel` (observation).
4. `agent.end` continue maps to a Stop block with the user message as its
   reason; `maxContinuations` is left to the dispatcher's existing Stop
   bound (`HOOK_MAX_STOP_CONTINUATIONS`).
5. OpenCode `permission.ask` `allow` becomes a plain completed (never a
   grant); `chat.message` mutations are not applied.
6. One child per hook call (spawn per call, always reaped); session dispose
   kills stragglers via process group (POSIX) or process (Windows).
7. No real `bun` run: bun 1.3.14 exists on this rig but the child source is
   runtime-agnostic JS, proven under node; the opencode paths run through
   the same entry. Bun-absent refusal is proven by resolver tests.
8. Dispatcher wiring, bundle placement and the full quality gate are lane
   W's / the lead's.

### Decisions

- **Which job.** The M27 shell-job DLL is the helper whose preparation
  retries since #118. It keeps background processes alive after a command
  ends normally (by design, as on POSIX), and it joins from inside a
  PowerShell process. M50's MCP launcher is the existing kill-on-close job.
  It also closes that job when the extension host dies. So plugin children
  use M50's launcher. The core interface is `spawn` plus `killTree` rather
  than `attach` plus `killTree`: a job attached after start leaves a window,
  and the launcher assigns the job before the child's first instruction.
- **Working directory.** A plugin child runs in its plugin's folder: the
  launcher needs a directory.
- **The interface lives in core and the implementation in the host.**
  `src/core` imports nothing from `src/host`. The tests use fake trees, and
  the real job is tested on Windows only.

### Open points for the lead

1. **Amp's `error` action.** `amp_plugin-api.md:1978`: it "stops the thread
   worker", so in Amp the tool never runs. Under PLAN's mapping it is a
   failure, blocked only where the event is fail-closed. Under the M91b rule
   (fail-closed only for OpenCode `tool.execute.before`), the tool would run
   here, which is weaker than Amp. A related citation issue: the quote
   "logged and otherwise ignored" is at `:656`, and it describes `onDispose`
   callbacks, not event handlers. The saved docs do not say what a throwing
   `tool.call` handler does in Amp.
2. **Amp `agent.end` continue.** The child answers blocked and sets
   `stopReason` as well. `dispatchHooks` reads a `stopReason` as "stop", so
   the turn would stop where the mapping says it continues. This is fixed
   with the dispatch in M91b.
3. **Job preparation failures.** The M50 launcher's preparation
   (`mcpJobExecutable`) caches a failure for the window: there is no
   #118-style retry. Until a reload, plugin hooks on that machine fail by
   their fail-closed rule.
4. **P2 12 (memory).** A Windows job memory limit means adding
   `JobMemoryLimit` to the shared `MuseSparkMcpJob.cs` `Run`, which MCP
   servers also use. That goes to M91b with the rest of P2 12.
