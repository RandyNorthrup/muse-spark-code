## GitHub's documentation, read 2026-10-17

- "Authorizing OAuth apps", device flow
  (docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps):
  `POST https://github.com/login/device/code` (`client_id`, `scope`) →
  `device_code`, `user_code` (eight characters with a hyphen),
  `verification_uri`, `expires_in` (900), `interval` (5); JSON with
  `Accept: application/json`; the user enters the code at
  `https://github.com/login/device`; polling
  `POST https://github.com/login/oauth/access_token` with
  `grant_type=urn:ietf:params:oauth:grant-type:device_code`; errors
  `authorization_pending`, `slow_down` ("5 extra seconds are added to the
  minimum interval", the reply carries the new interval),
  `expired_token` (the text says `token_expired`), `unsupported_grant_type`,
  `incorrect_client_credentials` ("The client_secret is not needed for the
  device flow"), `incorrect_device_code`, `access_denied`,
  `device_flow_disabled`. The parser's shapes match; it now reads both
  expiry words (`deviceFlow.ts` `ERROR_REASONS`).
- "Refreshing user access tokens" (GitHub Apps page): `client_secret`
  "Required unless the user access token was generated using the device
  flow"; `grant_type=refresh_token`; the reply's `expires_in` 28800 and
  `refresh_token_expires_in` 15897600. No error word for a spent or expired
  refresh token is documented. So a renewal answered with any word but
  `bad_refresh_token` once made every **Sign In** fail before it could
  start a new sign-in, after the access token had expired; `ask` now
  starts a new sign-in then (`deviceFlowSource.ts` `credential`), a silent
  read still fails and Cancel still stops.
- Not captured: no reply of GitHub's device flow has been recorded. The
  first sign-in below records them.

## Residuals

- Lane A's cross-process windows (PLAN.md M123, "one logout barrier"):
  without a compare-and-swap in the keychain, a refusal racing another
  process's store can lose a pair (the user signs in again); none serves a
  token issued before a finished sign-out.
- VS Code's own session (a) cannot be signed out from the panel (VS Code's
  Accounts menu owns it); `gh`'s login is `gh`'s.
- In VS Code the device-flow token lives in VS Code's secret storage; the
  terminal's in the OS credential store under the same account name. The
  two are separate sign-ins.
- The native route's pull request Create asks twice (the push's own
  confirmation, then the pull request's), where VS Code's route treats the
  form as the confirmation.
