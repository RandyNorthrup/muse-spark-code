## Thonny API evidence (read, not guessed)

`thonny-5.0.0-py3-none-any.whl` was downloaded from PyPI and its sources
inspected read-only (the wheel was deleted afterwards; it never entered
the repository). Findings, each cited in the code:

- Plugins are modules under `thonnycontrib.__path__` exposing
  `load_plugin()` (`thonny/workbench.py`, `_load_plugins`).
- `thonny.get_workbench()`, `thonny.get_runner()` (may be `None`)
  (`thonny/__init__.py`).
- `workbench.add_command(command_id, menu_name, command_label, handler,
tester=None, ..., image=None, caption=None, include_in_toolbar=False,
...)`; the `tools` menu exists; `image=None` is safe; a toolbar button
  needs only `caption`.
- `runner.send_command(InlineCommand(name, **fields))` is async and shows
  no UI; backend `InlineResponse` events arrive on the workbench bus and
  match by `response.command_id == cmd["id"]`.
- **Correction to the research citation:** `send_command_and_wait(cmd,
dialog_title)` (5.0.0, two arguments) pops a modal `InlineCommandDialog`
  per call — it is not a silent programmatic call. The bridge never uses
  it; it sends with `send_command` and matches `InlineResponse` itself,
  so no per-action Tk dialog double-prompts the user.
- Backend `read_file` takes `path` and answers `content_bytes` + `path`;
  `write_file` additionally requires `content_bytes` and
  `make_shebang_scripts_executable` (`thonny/backend.py`). The bridge
  sends both fields.

The whole package imports without Thonny installed (`thonny` is imported
lazily only); `test_package_import_needs_no_thonny` pins that.

## Reuse and scope decisions

- No new npm dependency; no new Python dependency (standard library
  only). `thonny` itself is the host and provides its own package.
- Runtime commands reuse the plan's names: `muse-spark-code-acp panel`
  (D84) to start, `muse-spark-code-acp stop-machine` (D83.16) for the
  out-of-band stop.
- MIT license text is byte-identical to the repository `LICENSE`.
- Workflows follow `release.yml` conventions (SHA-pinned actions,
  `persist-credentials: false`, secret-gated publish, `environment`).
- Owner rulings (2026-10-04): this lane has no paid surface and no model
  choice, so there is nothing to gate — enhancements/paid/single-model
  behaviour is unchanged by the plugin. Recorded here so the question is
  visibly considered, not overlooked.
- **Strings (original lane, superseded by FIXM103T below):** no keys were added to `src/shared/l10n/en.ts`, the 14
  `l10n/ui.*.json` tables or `package.nls*.json`. Those tables carry
  strings the TypeScript UI reads; the plugin's two menu labels live in

  keys, so `package.nls*.json` must stay untouched while lane W owns
  `package.json`. `node scripts/check-l10n.mjs` reports 0 problems on the
  finished tree (see gates below).

### Remaining corrections and final evidence

Findings 4, 5, 7, 8 and 12 are fixed. Plugin Open clicks and controller
starts are serialized separately; shutdown marks the plugin permanently
closed, increments the controller generation, closes a published connecting
client, cancels queued work and joins Open/provider workers. A late spawn is
terminated and cannot reconnect or mark the plugin running. Stop machine
keeps its independent worker and direct CLI call, with no approval/runtime
prerequisite. No pump or notice is scheduled after closure.

Windows tree ownership uses a small C# launcher built by the bundled .NET
Framework compiler in a private temporary directory. It owns a kill-on-close
job before creating the suspended target, which inherits the job atomically.
Only then does it resume the target. Thus shutdown during startup cannot
leave an unowned suspended child. A live or exited runtime's descendants
are released with the job; the controller waits after both terminate and
kill. Standard handles preserve the private stdout pipe, including command
shims and paths with spaces. POSIX creates a new session and signals its
process group. Python imports no ctypes/device stack; the original structural
gate remains unchanged. The native source ships in both wheel and sdist.

One bounded startup queue and one reader cover the runtime's whole lifetime;
post-start stdout is discarded and never logged. Startup requires all three
announcement kinds, in any order, and RuntimeInfo construction remains inside
the cleanup/error-normalization block. Tests cover all six orders, incomplete
and malformed announcements, blocked startup and 2 MiB of post-start output.

Gettext ships 14 real PO/MO catalogues covering all 11 menu/caption/failure
messages. Stop uses each extension table's stopTitle translation. The host's
general.language preference is read at action/notice time; country codes and
Chinese script aliases resolve, and unsupported languages use English.
Only fixed translated messages reach the plugin's notices; unchecked peer
or process text is not displayed. PO/MO equality and catalogue completeness
are owning pytest gates, so Python text is checked even though the TS l10n
gate does not scan it. The standard-library compiler is included in the
sdist and its new README command was run successfully (14 catalogues).

## REDM103T — redesign after round two (2026-10-05, Windows 11)

This record supersedes the write-admission claims above. RVM103T2 proved
that Thonny's own postponed queue could bypass them. The approved redesign
removes the complete command/write path; it does not try another admission
callback. No device command factory, sender, response binding, payload decoder
or write approval exists in the plugin. A structural AST regression and
behavioural approved/busy/switched/empty-write cases enforce that absence.

The plugin supplies only the last 4,096 characters already displayed in the
Thonny shell and an honest connected/read-only probe, read on the Tk thread.
Explicit hand-over destroys the backend (the public API also clears Thonny's
postponed commands) before a runtime port-acquire request. Explicit give-back
requires serial-close/lease-release acknowledgement before restarting the
same configured runner/interpreter/port. Failures, Open, provider frames and
shutdown never reconnect automatically. `auto` and WebREPL are refused;
the user chooses a concrete configured serial port. Device approvals, bounded
serial reads, lease enforcement and out-of-band Stop belong to runtime lane P.

The incompatible v2 interface is specified in integrations/thonny/README.md.
This base has no R/P implementation: the tests use a fake runtime serial
session/lease over the production socket. Installed-runtime compatibility,
actual cross-process lane-P lease enforcement and its approval UI are **not
certified** here. R/P must freeze the contract and provide those receipts;
M103T-WIRE-FREEZE remains open. This is the smallest lane-T implementation;
no runtime lane, TS model request, paid feature or device stack was added.
