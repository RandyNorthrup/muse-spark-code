## Where Muse Code keeps memory

Muse Code 1.3.0 has no MSP method for memory (`memory/list` answers
`methodNotFound`, M43's inventory) and no CLI subcommand for it (the saved
`--help` output has none). Its memory is Markdown files, so they were looked
for on disk, by name only (no note, lock or credential file was read):

- The note the M43 capture wrote for `C:\muse-live-m43` was at
  `%USERPROFILE%\.local\share\muse\memory\projects\C--muse-live-m43-7bdb42d98a06c29b\palette.md`,
  beside a `.muse-memory.lock`. `%USERPROFILE%\.config\muse` holds no memory.
- The folder name's second half is the FNV-1a 64-bit hash of
  `\\?\C:\muse-live-m43`, the path as Rust's `canonicalize` spells it on
  Windows (found by trying the usual digests of the usual spellings; only
  this one matched).
- The binary's strings gave the tools' schemas and descriptions, the
  scopes' meanings (its `migrate` skill), and Muse Code's refusals, such as
  "memory path traversal is not allowed", "hidden memory path components
  are not allowed", "memory path contains a symlink" and "ambiguous
  old_str". `XDG_DATA_HOME` is among the variables it reads.

## Existing-note concurrency audit, 2026-09-25

Read-only local evidence: one `.muse-memory.lock` in the existing project
memory folder contained `pid=40696`; that process was no longer running.
The lock file persists beyond ownership, so its presence or PID cannot be
used as a cross-process mutex. Muse Code 1.3.0's installed binary places
`.muse-memory.lock` beside `pid=`, `memory lock busy: a native write holds
the view` and `memory lock failed:`. It imports Windows `LockFileEx` and
`UnlockFileEx`. Node 24.20's `node:fs` exports no lock operation. These
facts support native locking but did not establish the memory writer's
specific lock calls, hold lifetime, or the corresponding POSIX protocol.

A second read-only audit examined the installed
`muse-bin-1.3.0-R3401.1.exe` (415,378,168 bytes; SHA-256
`E0A7CFEF0755A6C7D249AD66A4D3CCCDC52671563C8F1FF3A66881CDB11A6BBA`).
It has no symbol table or bundled source. Its generic locking helpers call
`LockFileEx` at RVAs `0x9189081` with flags `1` and `0x9189d31` with flags
`3`; another call at `0x9188bff` takes flags from its caller. The visible
calls pass reserved `0`, low and high range lengths `0xffffffff`, and an
`OVERLAPPED` buffer initialized to zero. [Microsoft's API reference](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)
defines flags `1` as fail immediately and `2` as exclusive, so the fixed
calls request shared and exclusive try-locks over a zero-based
`0xffffffffffffffff`-byte range. This establishes the generic Windows
helper's arguments. It does **not** establish that Muse Code's memory
writer calls that helper, when it acquires/releases the guard around a
read-modify-write operation, or what macOS/Linux use. The [official memory
guide](https://dev.meta.ai/docs/muse-code/configuration) documents scopes
and Markdown notes but no lock protocol; the public SDK exposes no memory
management or file-lock interface.

`MemoryStore.add` and `edit` read an existing note and then call
`MemoryIo.writeFile`; the host replaces that file atomically. Atomic
replacement prevents a torn note, but it cannot prevent two independent
read-modify-write operations from overwriting one another. An in-process
mutex would not coordinate with `muse serve`; an `wx` lock on the persistent
PID file would be incompatible. No cross-process lock was added from this
evidence. The existing-note lost-update risk remains, accurately stated in
README and PLAN §9. A safe fix requires a verified memory-writer call path,
acquisition/hold protocol, and portable equivalent before implementation.
The seven focused memory test files passed 67/67 after this documentation
audit. No new behavior or test gate was introduced, so no red drill is
claimed for the unresolved lock gap. Full quality and integration remain
pending on the final milestone base.

## Native lock boundary and complete new-note publication, 2026-09-26

The exact M47-base staged tree before this work was
`a3e550e163b3e5ef6e2abe2a1492a1360375a2a7`, preserved as immutable stash
`10911e9b831a4d434d217844003a5adcfa9508d7` at
`refs/codex-backups/m49-pre-lock-progress-20260926`. No original Claude
worktree, global configuration or global stash index was touched.

This pass targeted Muse Code's **actual memory writer** rather than repeating
the generic Windows LockFileEx inventory above. Installed Muse Code 1.3.0
exposes no no-model memory-write command in `muse --help` or `muse config
--help`. The [Meta memory guide](https://dev.meta.ai/docs/muse-code/configuration#local-memory)
documents scopes, Markdown notes and the index but not the native writer's
lock call path, acquisition point or hold lifetime; the public SDK offers no
memory-writer API. The binary lacks symbols as recorded above. No permitted
free operation was found that invokes `add_memory`/`edit_memory` with a
controlled hold. Therefore compatibility with `.muse-memory.lock` remains
**unproved**. No native writer, model or paid attempt ran in this pass.

The narrower bug was real: `open(target, 'wx')` reserved a new note's final
name **before** writing it, so another process could read an empty or partial
file. `createMemoryIo` now writes and syncs a hidden stage beside the target
(mode `0600` where honored), closes it, then publishes it with
`fs.link(stage, target)` and removes
the stage. [Node's `fsPromises.link`](https://nodejs.org/api/fs.html#fspromiseslinkexistingpath-newpath)
uses the system hard-link operation. [POSIX `link(2)`](https://man7.org/linux/man-pages/man2/link.2.html)
refuses an existing target with `EEXIST`; [Windows CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw)
is documented for NTFS. A filesystem that does not support hard links now
fails the create explicitly; there is no overwriting rename or visible-copy
fallback. A cleanup failure after publication is logged without suppressing
the completed note's index update. A crash may leave a hidden stage, which
the memory listing ignores. Existing-note append/edit and `MEMORY.md` index
read-modify-write paths still lack Muse Code's native cross-process lock and
can lose an update.

The real-filesystem publication test held the hard-link step: it saw complete
bytes in the hidden stage, no final note and no new index line. Releasing it
published the full note and index line, with no stage left. A simulated
unsupported link refused both direct and store creates and left no target,
stage or index. Seven memory
suites passed 69/69. The red drill temporarily used the final name as the
stage; the publication test failed with `expected complete note to be
undefined` before release (exit 1). Restoring the hidden stage passed the
same selected test (1/1) and all seven suites (69/69).

A separate bounded process drill compiled the actual `memoryIo.ts` into a
disposable Node bundle under `%TEMP%/m49-atomic-create-probe-20260926`.
Two independent Node processes staged different 1,000,000-character notes
and waited at publication; the final target was absent while both stages
were complete. On release, one returned `created`, the other `EEXIST`; the
winner's full 1,000,000 bytes remained, and no stage remained. Its first
orchestration script failed to parse before any child launched; the corrected
script produced the reported result. A post-run process audit found zero
probe-owned Node processes. This tests extension writers on local Windows
storage, **not** Muse Code's native writer lock. Full quality, browser,
hosted review and native existing-note/index concurrency remain open.
