## First piece

The terminal parses `schedule add --draft <JSON>`, `list`, `remove`,
`run-now`, `pause`, `resume`, `timeline --hours 24|168`, `fire`, `run-due`,
and `background off|status`, with `--json`. Workspace commands accept
`--cwd`; global wake/background commands do not. Drafts and control results
use lane 0's strict schemas. Drafts cannot set creator, consent or other
host authority. Each invocation closes its control after settled work,
including failure. Text output reads the installed locale at use time;
all seven new runtime strings have real translations in all 14 tables.

ACP intercepts `/schedule` locally before starting a model turn. Its add
form takes the complete draft JSON directly after `add`, preserving spaces
and Unicode. ACP forbids `--cwd` and `run-due`. A missing binding returns an
explicit capability refusal and starts no model turn. A held ACP session
acquires the runtime's workspace lease and releases it when replaced or
closed; a failed release cannot prevent the existing Stop/dispose path.

`RuntimeScheduleHost` provides independent wall/monotonic clocks and
reference-counted workspace ownership. Delivery forwards the validated
unattended context unchanged, waits for final settlement, verifies its
identity/target/occurrence/delivery, and keeps refusals, cost, certainty and
retained liability. It never admits a turn or manufactures a free success.

## Runtime, shared surfaces and background entries

`ScheduleRuntime` binds each CLI/ACP control to the shared `ScheduleSurface`,
holds S's persisted due workspaces before `runDue`, waits for settlement, and
attempts every lease release even if one fails. Engine teardown precedes OS
maintenance. A control or watcher finishing after close is cleaned up instead
of adopted. ACP's failed schedule lease release cannot prevent Stop/dispose;
a late lease on an already closed adopting session is released immediately.

`ScheduleSurface.message` is the same strict version-1 envelope for the
companion/panel, JCEF, WebView2, SWT, TUI and desktop. Their fake JSON bridges
retain request IDs and versions. Requests stay within the trusted workspace;
list/audit responses cannot return another schedule's data; mutation IDs,
history trigger/range and response kinds must match. CAS revisions pass
through unchanged. A committed creation keeps its accepted ID even if the
optional background question, registration or notification fails: retrying
must not silently create a duplicate.

`ScheduleBackgroundCoordinator` asks at the first accepted creation while
holding the injected durable consent lock. Yes registers only the next wake;
Not now/Never are remembered without another question. Settings and uninstall
use the same removal operation as `schedule background off`. Restrictions
are persisted before native removal, so a failed OS deletion cannot become
permission to register again. No next fire removes the entry.

`NativeScheduleBackground`, `backgroundRegistration` and `nodeBackgroundFiles`
provide the native manifests and checked create/status/rearm/remove operations:

- Windows: current kernel user SID, InteractiveToken, LeastPrivilege,
  IgnoreNew, one TimeTrigger, fixed quoted `schedule run-due --json`, UTF-16
  XML with BOM. Task Scheduler initially rejected UTF-8 XML with "unable to
  switch encoding"; the real rig check and X86's BOM mutation caught it.
- macOS: per-user `gui/<uid>` launchd calendar, minute rounded upward, no
  KeepAlive or RunAtLoad. **Automatic wake self-rearm/removal is incomplete:**
  reloading its own launchd job can kill the wake. The trusted `isWakeProcess`
  flag makes both mutations refuse before touching a file or OS job. An
  independent after-exit maintenance helper and a macmini receipt remain
  required. Calendar entries are not claimed to be inherently nonrepeating;
  maintenance must replace/remove them after the wake.
- Linux: per-user systemd oneshot service and absolute UTC timer, second
  rounded upward, Persistent=true, no periodic interval; rearm restarts the
  changed timer. Specifier, dollar and quote characters in trusted paths are
  escaped. Real systemd user-manager receipts remain for a Linux rig.

Native helper children use argument arrays, bounded output/deadlines and a
credential-free environment. State is bounded, strict JSON; writes use an
owner-only temporary file, sync and atomic rename. Removal touches only the
known registration/state files. Failed/unknown OS queries or mutations never
return an empty success. A crash orphan reports registered without inventing
a next wake.
OS executables use fixed system locations: WindowsPowerShell/v1.0 and
schtasks under the validated startup SystemRoot, `/bin/launchctl`, and
`/usr/bin/systemctl`. A real replacement powershell.exe on the test PATH
cannot take over the system command. Missing/relative/control-character
SystemRoot values refuse before launch. The first pinned-path trial used
the wrong PowerShell directory; the actual rig failure and `Get-Command`
capture identified WindowsPowerShell/v1.0, and the corrected tests passed.
