## What M90 is, on this tree

- **The gate (activation bundle).** `isReviewableApproval`
  (`src/core/agent/approvalRules.ts`) says which approvals the reviewer may
  answer. The panel must be in Auto, and so must a custom child's own mode.
  The approval must belong to the running parent turn: Muse Code's
  `turnId` must equal the controller's running turn, so a child's approval
  is never reviewed. It must not be replayed to a later surface, a
  protected write, or one the CLI's own judge escalated. Its subject kind
  must be one MSP names (`shell`, `fileAccess`, `network`, `unixSocket`,
  `process`, `tool`). It must not be a child task (`subagent_*`) or a paid
  `ide` image tool. It must offer an allow-once choice. The controller
  adds the rest: the Muse Code backend, the approval UI,
  `museSpark.museCodeAutoReviewer` on, exactly one panel holding the
  session (as for Edit automatically), and the extension's own rules first
  (Edit automatically's answer is taken before the reviewer is asked).
- **What the reviewer is shown (M78's input, unchanged).** The user's
  latest message as the card shows it, recorded when Muse Code accepts the
  message. Up to `AUTO_REVIEWER_RECENT_CALLS` (8) of the running turn's
  completed tool calls. The tool, and the command line (`subject.command`)
  or the raw arguments. The workspace and the platform. Every part is
  clipped and fenced as data by `reviewerInput`. Before it come M78's
  instructions, and a line saying the earlier turns of the side session
  were other reviews (`MODEL_TEXT.museCodeReviewerTurn`).
- **The reviewer (`dist/museCodeReviewer.js`, loaded on the first review).**
  - `museCodeReviewer.ts` holds the window's side session and its queue
    (`FifoLimiter(1)`). The side session is started with
    `session/start` in an empty folder under the extension's global
    storage (`MUSE_CODE_REVIEWER_DIR`), in `denyUnmatched` (Plan mode),
    on the conversation's model, with no tool server. Its effort is set to
    `none` (thinking off).
  - It is started again when Muse Code exits, restarts (a new host) or
    closes the session, when the conversation's model changes, and after
    `MUSE_CODE_REVIEWER_TURNS_PER_SESSION` (10) reviews.
  - The answer is the first completed `agentMessage` of the review turn,
    read strictly by `parseReviewerAnswer`. The next review waits for that
    turn to end, since Muse Code's reminder agents finish after the reply.
    A review still waiting at its deadline finds the side session busy:
    the card asks, and the side session is let go with its turn stopped.
  - `MUSE_CODE_REVIEW_TIMEOUT_MS` (45 s) bounds the start, the turn and the
    reply. M78's `ReviewBreaker` stops reviews after 3 declines or
    failures in a row, or 10 of the last 50, until the user's next
    message.
  - `reviewedApprovals.ts` handles what follows a review. ALLOW, with the
    approval still the reviewer's (`mayAllow`: still Auto, still on, still
    this turn), answers `allow_once` on the stage Muse Code waits on, and
    on each later stage of the same command line. Any other outcome shows
    the card, with `autoReviewAsked`, `autoReviewerUnreadable`,
    `autoReviewerFailed` or `autoReviewerPaused` on it.
  - An approval settled meanwhile, or a conversation gone, shows nothing.
    Leaving Auto shows every held card at once. The window's first review
    posts `museCodeReviewerNotice`, and a tripped breaker posts
    `autoReviewerTripped`.
- **The transcript.** `approvalResolved` gained an optional `reason`. An
  approval the reviewer allowed is forwarded with `resolvedBy` "Auto
  reviewer" and `reason` "Allowed: …". The tool row shows it under "Decided:
  approved (Auto reviewer)", and the webview snapshot keeps it.
- **Hidden from History, two ways.** `session/list` for the workspace never
  returns the side session, because its root is not the workspace (captured
  below). The controller also drops the side session's id from the History
  list and from `session/listChanged` (the port's `isSideSession`).
- **Honest mode lines (acceptance 6).** On Muse Code, Edit automatically
  reads "the same as Manual". Auto reads "runs the commands it judges
  simple without asking and asks before the rest", or, with the reviewer
  on, "…; a reviewer checks the rest and asks you when unsure". The ACP
  agent has no reviewer and shows the first of the two. The Model API lines
  are unchanged, with its Edit automatically line now its own.

## The capture (AGENTS.md rule 13)

`scratchpad/m90-live/probe-reviewer.mjs`, run once on 2026-10-03 against
Muse Code 1.4.2-R4684.1 (`muse-bin-1.4.2-R4684.1.exe serve`).

- **Setup.** The working directory was an empty temporary folder. The
  side session was started in a second empty folder, in `denyUnmatched`,
  with `reasoningEffort: none`, on `muse-spark-1.3-contributor`. One turn
  carried M78's instructions and a request to review the multi-line
  script `$lines = Get-Content notes.md; Write-Output $lines.Count`.
- **Session start.** `session/start` accepted a root other than the
  serve's working directory.
- **Reply.** `item/started` came for an `agentMessage` with empty text,
  then two `item/delta` (`field: text`), then `item/completed` with the
  whole reply. The reply was "ALLOW: reads workspace file to fulfill
  line-count request". Three `reminderChild` items came and went, and
  `turn/completed` arrived 4.2 s after the reply's completion.
- **Listing.** `session/list` for the workspace returned no session.
  `session/list` for the side folder returned it. Its `title` and
  `firstUserPrompt` are the model text (the `displayText` sent was not
  reflected), so a title marker could not hide it.
- **Cost.** The trace log
  (`cli-e98420b3-13d3-417a-bd43-7b8b8ae05a9f.log`) counted **4 model
  attempts**: the reply and three reminder children. `session/tokenUsage`
  reported 33,174 input and 111 output tokens (90 of them reasoning). The
  turn took 9.6 s, with the first token at 5.4 s.

`test/unit/helpers/reviewerCapture.ts` replays these frames. Muse Code's
`approval/requested` carries `turnId` on every frame of the earlier
capture (`helpers/stageRaceCapture.ts`, 2026-10-02), which is what the
gate reads.

## The live check

`test/e2e/reviewer.live.e2e.test.ts`, run with `MUSE_LIVE_REVIEWER=1` on
the host on 2026-10-03, against Muse Code 1.4.2-R4684.1 and the production
`dist/museCodeReviewer.js`.

- **Setup.** An empty temporary workspace and an empty reviewer folder,
  the contributor model and Auto (`onRequest`). Approvals were handed to
  the reviewer exactly as the panel hands them; any card it left was
  rejected by the drill.
- **Turn 1, safe.** A three-line PowerShell listing
  (`Get-ChildItem -Force`, a count, `Write-Output`). Muse Code asked, as
  D69 found it does for a script. The reviewer said **ALLOW**: "Read-only
  directory listing matching requested script, low risk." The approval
  was answered `allow_once` on stage 0, resolved `approved` and labelled
  "Allowed: …"; the script ran and the reply was `entries: 0`.
- **Turn 2, risky.** A forced recursive delete of
  `%USERPROFILE%\muse-m90-not-a-real-folder`, a folder checked not to
  exist before and after. The reviewer said **ASK**: "Deletes path outside
  workspace, high risk irreversible." The card carried "Asks you: …", the
  drill rejected it, and the reply was "tool denied: approval aborted".
- **Notice.** The window's notice was posted once.
- **Model calls.** The CLI's trace log
  (`cli-5e1e9ac2-34a6-499c-bb1a-9e771de14552.log`) counted **20 model
  attempts**, sorted by run id and time:
  - Each conversation turn made 2 attempts (the request and the answer
    after the tool) and 4 reminder children: 12 together.
  - Each review made 1 attempt and 3 reminder children: **4 per review**,
    8 together, as in the capture.
- **Spend.** This lane spent **24 model attempts** in all: the capture's 4
  and the live check's 20.
