## What M90 is, on this tree

- **The gate (activation bundle).** `isReviewableApproval`
  (`src/core/agent/approvalRules.ts`) says which approvals the reviewer may
  answer. The panel must be in Auto, and so must a custom child's own mode.
  The approval must belong to the running parent turn: Muse Code's
  `turnId` must equal the controller's running turn, so a child's approval
  is never reviewed. It must not be replayed to a later surface, a
  protected write, or one the CLI's own judge escalated. Its subject kind
  must be one MSP names (`shell`, `fileAccess`, `network`, `unixSocket`,
  `process`, `tool`). It must not be a child task (`subagent_*`) or a paid
  `ide` image tool. It must offer an allow-once choice. The controller
  adds the rest: the Muse Code backend, the approval UI,
  `museSpark.museCodeAutoReviewer` on, exactly one panel holding the
  session (as for Edit automatically), and the extension's own rules first
  (Edit automatically's answer is taken before the reviewer is asked).
- **What the reviewer is shown (M78's input, unchanged).** The user's
  latest message as the card shows it, recorded when Muse Code accepts the
  message. Up to `AUTO_REVIEWER_RECENT_CALLS` (8) of the running turn's
  completed tool calls. The tool, and the command line (`subject.command`)
  or the raw arguments. The workspace and the platform. Every part is
  clipped and fenced as data by `reviewerInput`. Before it come M78's
  instructions, and a line saying the earlier turns of the side session
  were other reviews (`MODEL_TEXT.museCodeReviewerTurn`).
- **The reviewer (`dist/museCodeReviewer.js`, loaded on the first review).**
  - `museCodeReviewer.ts` holds the window's side session and its queue
    (`FifoLimiter(1)`). The side session is started with
    `session/start` in an empty folder under the extension's global
    storage (`MUSE_CODE_REVIEWER_DIR`), in `denyUnmatched` (Plan mode),
    on the conversation's model, with no tool server. Its effort is set to
    `none` (thinking off).
    This does not disable native tools: SDK `SessionConfig` only configures
    `mcpServers`. Any item other than an agent message or reasoning cancels
    the review turn, shows the generic failure card and recreates the side
    session. A command covered by the user's always-allow rule could run
    in the empty folder before the cancel lands. Only workspace files,
    rules and skills were excluded by the captured setup; CLI-global
    context is not excluded.
  - It is started again when Muse Code exits, restarts (a new host) or
    closes the session, when the conversation's model changes, and after
    `MUSE_CODE_REVIEWER_TURNS_PER_SESSION` (10) reviews.
  - The answer is the first successfully completed `agentMessage` of a
    successfully completed review turn, read by `parseReviewerAnswer`.
    The verdict now waits for the turn's end; the captured reminder items
    below trigger the new fail-closed guard rather than carrying an ALLOW.
    A review still waiting at its deadline finds the side session busy:
    the card asks, and the side session is let go with its turn stopped.
  - `MUSE_CODE_REVIEW_TIMEOUT_MS` (45 s) bounds the start, the turn and the
    reply, including reasoning-effort setup and cancellation. M78's `ReviewBreaker` stops reviews after 3 declines or
    failures in a row, or 10 of the last 50, until the user's next
    message.
  - `reviewedApprovals.ts` handles what follows a review. ALLOW, with the
    approval still the reviewer's (`mayAllow`: still Auto, still on, still
    this turn), answers `allow_once` on the stage Muse Code waits on, and
    on each later stage of the same subject. A changed kind, command, path,
    host or tool name invalidates it. Any other outcome shows
    the card, with `autoReviewAsked`, `autoReviewerUnreadable`,
    `autoReviewerFailed` or `autoReviewerPaused` on it.
  - An approval settled meanwhile, or a conversation gone, shows nothing.
    Leaving Auto shows every held card at once. An accepted message or
    steer also releases held reviews and drops old allowances. Queued jobs
    recheck the breaker when their slot starts. The window's first review
    posts `museCodeReviewerNotice`, and a tripped breaker posts
    `autoReviewerTripped`.
- **The transcript.** `approvalResolved` gained an optional `reason`. An
  approval the reviewer allowed is forwarded with `resolvedBy` "Auto
  reviewer" and `reason` "Allowed: …". The tool row shows it under "Decided:
  approved (Auto reviewer)", and the webview snapshot keeps it. Resolutions
  arriving before their tool row are kept for the newest 50 item ids and
  applied when the row arrives.
- **Hidden from History, two ways.** `session/list` for the workspace never
  returns the side session, because its root is not the workspace (captured
  below). The controller also drops the side session's id from the History
  list and from `session/listChanged` (the port's `isSideSession`).
- **Honest mode lines (acceptance 6).** On Muse Code, Edit automatically
  reads "the same as Manual". Auto reads "runs the commands it judges
  simple without asking and asks before the rest", or, with the reviewer
  on, "…; a reviewer checks the rest and asks you when unsure". The ACP
  agent has no reviewer and shows the first of the two. The Model API lines
  are unchanged, with its Edit automatically line now its own.
