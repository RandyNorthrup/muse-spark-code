## The request

PLAN.md §6 M82: the user knows what happened and what it cost.

- A notification when a long turn ends or waits for approval while the VS
  Code window is unfocused, and never while it is focused.
- Tokens and cost per reply, optional.
- A session budget cap on the Model API, machine-scoped, kept by
  reservation: each request's input estimated high, `max_output_tokens` set
  so input plus output at list price fits what is left, a request that
  cannot fit not sent and the turn saying why, the only overrun the
  estimate's error (named in the setting), and the turn's cost shown against
  the cap afterwards.
- Cache savings in Account & usage, on the Model API only.

## How it was made

A Muse Code instance (Muse Spark, contributor tier) drafted the milestone
and left it uncommitted. Its sandbox blocked the production build,
`npm`/`npm audit`, Semgrep and `gitleaks git`, so those never ran on the
draft; its record said the milestone was certified anyway. Claude reviewed
the draft against PLAN.md and AGENTS.md and finished it. This record
replaces the draft's.

What the review found and changed:

- **The estimate was not high.** The draft counted what was added since the
  last request at four characters a token (below the real rate for code and
  for CJK text), counted only replay items (the instructions and the tools,
  about 11 KB, never entered the first request's estimate), missed child
  results drained while the body was built, and moved its base on every
  reservation, so a retry after a dropped stream was estimated at the old
  base with nothing added. `sessionBudget.ts` now estimates from the body
  sent: the last reported input plus every part (instructions, tools, each
  input item, as JSON) the reported request did not carry, at one token per
  UTF-8 byte, matched by SHA-256; removals never subtract. The base moves
  only when a response reports usage; it resets on a model change and after
  a compaction, where Meta's count of the new context replaces it.
- **Spend that was never reported was never counted.** A Stop or a dropped
  stream after the response began spent money the cap never saw. Such a
  request now counts at its whole reservation; one refused before its
  response began counts nothing.
- **An unpriced model was priced as standard.** The cap now refuses a model
  without a verified price (`modelApiPaidTier`) instead of guessing.
- **Child tasks' spend was left out** of the conversation's, although their
  tokens count in its totals and its goal budget. It now counts as it
  reports; child tasks are still not reserved (each is priced and asked for
  on its own, D48). The setting's description names them as the second way
  past the cap.
- **The reply line showed only the last request of a multi-step turn.** It
  now carries every request since the previous line in that turn, so a
  turn's lines add up to its cost; a failed turn's usage does not leak
  into the next turn's line.
- **A reply cut short by the budget said nothing.** A response that used
  every output token the budget left is now marked in the transcript.
- **"OS notification" was claimed, but VS Code gives extensions none.** The
  notice is VS Code's own `showInformationMessage`; the docs say so, and the
  OS-level toast is an open question for the owner (PLAN.md §3 Q10).
- **Two panels on one conversation both notified.** One `BackgroundNotifier`
  per window raises each notice once by key; a failed turn now says it
  failed instead of "finished responding".
- **`notifyOnBackgroundTurn` was machine-scoped**, though it chooses nothing
  that runs or is billed (D15's rule for that list); it is now an ordinary
  setting. The budget stays machine-scoped.
- **Smaller fixes.** A JSDoc sat on the wrong method in `ModelApiHost.ts`;
  German used colloquial "rein/raus" and called a turn an "Antwort"; French
  used straight apostrophes where its tables use ’; the draft had no
  harness scenario for the reply line.

## Second review

Grok Build reviewed `17cca2f4` against its base: two P1 findings, four P2.
Each was checked in the code. Five were real and are fixed, with every
sibling of their class. One is answered below.

- **P1: spend was not saved while a call waited, and closing did not wait
  for it.** Real. `persist` skips a snapshot with a call that has no output
  yet (so a crash cannot leave one), and the spend was only added in memory.
  Now each reported usage saves the session (`touch` in `noteUsage`), and
  while a call waits `persistSpend` writes the token totals and the spend
  onto the session's last saved snapshot. `close()` waits for every
  session's running turns and compactions (`settled()`, tracked by
  `track`) up to `MODEL_API_CLOSE_SETTLE_MS` before it awaits the save
  queue, so a turn the close stops charges and saves first. Tests: a reload
  while a call waits for approval cannot send what the real balance does
  not cover; a command stopped by the close ends a moment later and its
  turn is saved whole before `close()` returns.
- **P1: a model switched during a request repriced it and restored the old
  base.** Real. The request's model is stamped when it is sent
  (`sendingModelId`, and `modelId` on the reservation); its usage is priced
  at that model, and it becomes the base only if the session still uses
  it. The same applies to a child's usage report.
- **P2: a replayed question was not marked.** Real for a second surface:
  `MuseSession.onEvent` marked only approvals. It now marks both
  (`isPendingPrompt`), the schema carries `isReplayed` on
  `questionRequested`, the controller strips it before the panel sees it,
  and `attentionNotice` skips it. The `approval/listPending` path the
  review also named delivers into a new session's backlog, which the same
  marking covers (the resume test asserts both prompts arrive replayed); a
  flag there as well would be a guard no test can fire, so there is none.
- **P2: negative counts.** Real. A response usage with a negative count is
  now no report (`isCountedUsage`; a reserved request then counts at its
  reservation), a negative count of the compacted context fails its schema
  (so it is no base), and a stored negative spend fails the session file's
  schema. Non-finite numbers were already refused: zod 4's `z.number()`
  rejects `Infinity` and `NaN` (checked).
- **P2: the token count's failure logs network text.** Deferred in this
  earlier review because the line predated M82. The authorized 2026-09-29
  resume fixes it: compacted-context counting logs `HTTP <status>` for a
  `ModelApiError`, or fixed words for another failure. The envelope's
  message, kind and code are omitted from that log. The regression uses
  private-message markers and checks both the exact status line and their
  absence.
- **P2: the docs overclaimed, and H10/N4 missed these paths.** Real. The
  setting's description, the README, CHANGELOG and PLAN now name the third
  way past the cap: a request Meta never answered at all (no response
  within the stall timeout), which may still have run. A request the user
  stops after it was sent now counts at its reservation too (`isSent`, set
  by the attempt guard when the request goes out with the key). New drills
  cover the saved spend, the close, the model switch, negative counts and
  replayed questions.

## Windows resume, 2026-09-29

The resume starts from `49056306` and retains the earlier fixes rather than

The reservation preflight publishes its own durable row in a scoped shared
budget journal, then awaits the existing strict save queue before fetch.
It saves only the spend and totals onto the last safe snapshot when
an unanswered call prevents replay persistence. Final admission remains
synchronous after the actual key is read, checking the captured account,
model and goal revisions, trust, MCP state and whether a requested web
search is still allowed. Storage failure or no store refuses the capped
request. A nonsent request releases its liability with an awaited write
under its original account, including after the key changed. Actual usage
replaces the held reservation. HTTP/MSP fields and request call arguments
are unchanged; the paid consent flow is retained. An owned optional
attempt observer is described below.
The journal is a narrow session-store responsibility: a one-time
account-owned seed and permanent UUID claim intents, no locks, ownership
takeover, winner election, row deletion or live compaction. Failed original
publication may refund only its own proven nonsent row; it still rejects
the reservation, and another failure retains blocking intent or liability.
Old session saves project the journal and cannot lower its spending.
