## 1. Who can redeem a ticket

The delegated ticket is bound to the feeder's pid, the OS start time, and the
envelope digest (`state.ts` `delegate` / `redeemDelegated`). The delegation is
deleted at the start of `redeemDelegated`, before `verifyFeeder` returns, so a
second attempt sees no delegation. The ticket lives only in the broker's
memory: a restart drops it. `operationReason` refuses an item whose
`dates.expiresAt` has passed, and the headless session refuses a ticket whose
`expiresAt` is already past. The wire `redeem` on the requester socket is
always denied (`channel.ts`). Material leaves only as a private `execMaterial`
frame on the feeder connection.

`verifyFeeder` (`brokerBindings.ts`) re-reads the live identity and requires
the same start time, user id and executable as the connection-time peer, then
walks parents with the helper's `parent` mode until the registered requester,
checking that process's start time and user id. A cycle or a missing parent
returns false. The peer is authenticated once per connection
(`authenticatedPeer` in `channel.ts`) and reused for every frame.

Measured on this rig, with a throwaway Unix socket under the worktree `temp/`
and the kernel `SO_PEERCRED` (not the product helper):

- After another process inherited the connected socket, the peer pid stayed
  the process that called connect. An inherited fd would be treated as the
  original feeder.
- A child started the way the product starts the feeder (`stdio` ignore, pipe,
  pipe, pipe) did not receive that socket. A pipe-stdio child of the connector
  did not receive it either.
- `ptrace_scope` is 1. A different uid was not given the product socket. The
  runtime directory `/run/user/1000` is mode 0700, and `sudo -n -u nobody
/usr/bin/test -r` on it exits 1. The product socket directory is created mode
  0700 before bind (`vaultPrivateDirectory`). The socket file itself was mode
  0775 in the moment after `listen` and 0600 after the following `chmod`
  (`channel.ts`). Another user cannot traverse the directory during that
  window. A same-user process can.

The real broker and feeder suite (`test/unit/vault/vaultExecDelegated.test.ts`)
passed 3 of 3 after the fix in section 5, and again on the final tree (4865 ms
of tests, file anchor): ceiling
refusals in words, environment and stdin runs whose stdout carries the value's
length and a redacted echo, a foreign-identity delegation refused, a tainted
use refused, redemption on the requester socket refused, and a lock ending the
running command.

Not proven with a process: pid reuse of a dead parent inside the helper's
two-step `parent` lookup, a container whose pid namespace differs from the
broker's, and a second redeem of one ticket after a crash between the deletion
and the material write. The deletion is in memory only, so the crash loses the
ticket rather than leaving a second redeem. The helper was not changed.

## 2. Provenance and the ceiling

`reportProvenance` is accepted only on the connection that registered, and
`combineVaultTaint` only sets the tainted bit, never clears it. `requestUse`
refuses when that connection has not reported. The headless requester is built
by the host, not from tool arguments. The person's ceiling is read at
registration (`vault policy`); the default is none, and the suite's first case
shows that refusal in words, including a ceiling written for a different
workspace.

A same-uid process can still replace the regular `vault-policy.json` and the
next registration will honor it. That file is the person's setting and has to
exist before a broker does. Headless use still needs a grant. Section 5 stops
the case where the file is a link, is readable by another account, or has a
second name. It does not try to hide the file from its owner.

The headless service starts a taint session with `beginRequest([], true)` and
never calls `observe` (`vaultExecHost.ts`). A tainted report is denied, which
the suite shows. Nothing in this increment feeds later tool observations into
that session, so taint does not accumulate across commands. Recorded, not
changed: there is no observation source to invent.

## 3. Where a secret can land

The value is not on the host path. The suite's environment run asserts the
stdout does not contain the value and does contain the redacted mark. The
feeder wipes lease buffers and removes the environment keys in `finally`. The
host discards feeder stderr bytes. Refusal text is the fixed no-access
sentence. The policy file holds ceilings, not secret values.

Measured residuals, not fixed:

- A same-uid sibling read `/proc/<pid>/environ` of a dumpable Node process
  while `ptrace_scope` was 1 (`ENVIRON=ok`). Yama's relational scope restricts
  attach, not that read. The command that receives an environment secret is
  readable by any other process of the same user for as long as it runs. The
  parent can read it too. The product does not call `PR_SET_DUMPABLE`. A
  follow-up would set dumpable off in the command process itself before it
  runs; this lane did not add a native mode to do that.
- This process's core soft limit is 0 (hard limit unlimited), and a child
  inherited 0. `spawnGuarded` does not set `RLIMIT_CORE`. The confine helper's
  `setrlimit` does not wrap this spawn. A person who raises the core limit
  would get the secret in a core of the command. Not changed.
- The broker, helper and SSH sockets are `chmod` 0600 after `listen`, not
  created owner-only. The containing directory is 0700 first, which is what
  stops other users. A process-global umask around `listen` was not added.
- JavaScript strings that held JSON or base64 cannot be wiped. The owned
  buffers are filled with 0.

## 4. Fail closed

A malformed channel frame closes the socket and the refusal carries no private
text (`channel.ts`). A damaged, linked, shared, second-named or oversize policy
becomes ceiling `none` and writes `vault-policy-refused` (section 5). Before
the oversize fix, a file past the frame was read whole and then thrown as a raw
`No access`, which the ceiling did not treat as a policy refusal. The
delegation is spent before verification, and tickets are not stored on disk, so
a crash or a broker restart does not leave a redeemable ticket. `execFinish`
closes only the lease map of that connection.

The Linux feeder was failing closed for the wrong reason until section 5: it
refused the real broker socket, so the use never ran.

## 5. Fixes

### 5.1 The person policy file

`readVaultPolicy` / `writeVaultPolicy` used `readFile` and `writeFile` of a
fixed `vault-policy.json.next`. On this rig (umask 0002):

- A symlink at `vault-policy.json` pointing at a wider policy was honored
  (`ask` instead of `none`).
- A symlink at `vault-policy.json.next` was truncated to the new policy body
  when the policy was saved.
- A mode `0644` file and a second hard link were honored.
- A file one byte past the frame was loaded and then thrown as `No access`,
  which escaped the ceiling's refusal.

POSIX now reads through `readVaultFile` (no follow, owner-only, one link, size
before the buffer) and writes through `writeVaultFile` (exclusive random
temporary). A hostile file becomes `VaultError`, which the existing ceiling
path turns into `none` and `vault-policy-refused`. Windows cannot use those
helpers (`O_NOFOLLOW` is 0 and the mode check would refuse a normal file); its
write creates an exclusive random temporary and renames it over the target.
No new sentence was added.

`test/unit/vault/vaultPersonPolicy.test.ts` with the vulnerable file restored:
7 tests, 5 failed, exit 1. After the fix, and again after the red drill below:
7 passed, exit 0. Repository timeout, `--maxWorkers=2`, no `--testTimeout`.

Red drill: `git show HEAD:src/runtime/vault/vaultPolicy.ts` over the fixed
file, suite exit 1 (the same five failures), the fix copied back, suite exit 0.

### 5.2 The feeder's runtime directory

`spawnVaultFeeder` started the feeder with `vaultFenceEnvironment`, which drops
`XDG_RUNTIME_DIR` so a command cannot see the per-user runtime directory. On
Linux that directory is where the broker binds. The feeder then refused the
real socket. A temporary diagnostic, removed before the fix landed, printed the
broker socket
`/run/user/1000/muse-spark-vault-8cb87a26b7e9/broker.sock` against the bases the
feeder would accept, which were only the `TMPDIR` leaf and the home fallback.
The delegated suite was 1 passed and 2 failed (exit code null; `sleep 30` never
started). The refusal was fail closed: no value was released.

`feederProcessEnvironment` keeps an absolute `XDG_RUNTIME_DIR` for the feeder.
The command is fenced again from the feeder's environment
(`feeder.ts`), so the command still does not receive it, nor `GH_TOKEN`.

`test/unit/vault/feederRuntimeDir.test.ts`: a real Node child. With the restore
removed, exit 1 (`''` instead of `/run/user/1000`). Restored, exit 0.
`vaultExecDelegated.test.ts` then passed 3 of 3, exit 0.

## 6. What is sound

Different-user reach of the socket is closed by the 0700 directory and the
peer uid check, with the nobody probe on the runtime directory above. Double
redeem, expiry and restart fail closed in the broker state as section 1
describes. Provenance cannot be cleared on the wire, and a missing report
refuses the use. The person's ceiling, default none, is what the broker
evaluates; this lane did not add a ceiling of ours. Secret values stay off the
host result path in the real feeder run. Files the vault writes for the policy
are owner-only from the create flags on POSIX. The two defects above were the
breaks in that story, and both are fixed at the cause.
