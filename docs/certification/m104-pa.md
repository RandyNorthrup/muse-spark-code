## Implementation and controls

### Finding 1 — preparation/release quiescence

`RuntimeConversation` fences suspended composition and restore, disposes a
controller created during a reentrant release, rejects new work immediately,
and shares one release completion. Release cancels first, waits for preparation
and admitted handlers, stops the controller, disposes its session and performs
the final storage drain.

The original production code fails both suspended-composition/concurrent-release
and pending-replay controls. The restored runtime/controller/ACP registry batch
passes **14 tests in 3 files** on macmini. Host and unit typechecks pass.
Four source mutations fire: preparation fence, late controller disposal,
shared release completion and in-flight drain. Every mutation restores identical
source bytes/SHA-256; receipts are `m104-pa-drills.json`, logs under
`temp/m104-pa/`. The initial drain mutation passed an observation that checked
too early; its test now yields a full event-loop turn and the mutation fails.
No timeout, threshold or gate changed.

### Finding 2 — late cancelled/timeout replies

`PanelConnection` retains each cancelled ID with its request method. The
combined pending/retired count is bounded at the existing 128-message limit;
new calls refuse with `MHP_BACKPRESSURE` until a late reply frees a slot,
without closing the connection. A valid late success/failure is parsed with
the retained method and consumed exactly once. Unknown, duplicate and malformed
results retain fatal validation behavior. Cancellation cannot retire a reply
that already completed.

The original runtime fails four new cases (late success, cancelled failure,
timeout and bounded admission). The three restored correlation/delivery suites
pass **18 tests**. Host and unit typechecks pass. Three byte-exact mutations
fire: retention, consume-once and method validation (`m104-pa-drills.json`).
No new protocol vocabulary or larger cap is introduced.

### Finding 3 — one publication policy per record

Store instances use one resolved-path queue in this process. Cross-process
writers read the expected record revision, acquire an exclusive per-record
lock, compare the current revision and publish an fsynced temporary record
through atomic rename. Stale revisions are refused and reread, bounded to
eight attempts. Format 2 requires a revision; format 1 reads and migrates.
Activity/restoration (`lastSession`) keeps the greatest observation `at`;
equal timestamps use revision/publication order. A clear writes an activity
tombstone at its admission time, so an older observation cannot resurrect it.
Settings publications notify the other subscribed same-root stores, respecting
workspace/user scope; no credentials enter either record format.

The original code fails independent-store ordering, stale activity and peer
settings notifications. **15 storage tests pass**, including two actual separate
Node processes, explicit stale-CAS retry, migration and non-stealing lock deadline.
The runtime/controller/ACP composition batch passes **20 tests**. Four source
mutations fire (shared queue, CAS compare, newest activity and exclusive
publication), with byte-exact restoration recorded in `m104-pa-drills.json`.

A crashed publisher may leave its lock. The fixed five-second deadline returns
`MHP_STATE_LOCK_TIMEOUT`; this lane deliberately does not steal an abandoned
lock or claim automatic crash recovery. Recovery must remove that record's
lock only after all writers are stopped. Activity clocks are local-process
wall clocks; cross-machine synchronized state is outside this local store.
Windows/Linux peer execution remains with integration qualification.

## Frozen composition contract for B/C

No `src/runtime/features/**` or `core/presentation/**` exports exist at this
base. A consumes two optional lazy factories through `RunPanelDeps.factories`.
The following is the frozen authored contract, to be implemented in
`src/runtime/panel/runtimeFeatures.ts` before any B/C adapter is connected:

- Each factory receives `RuntimeConversationPorts` (runtime/backend, confined
  workspace root, live settings/trust, runtime-owned store, HostServices,
  current selection/documents, all controllers, logger), a selected-model
  capability lookup, and `openWorkspace(root)` for new worktree ownership.
- B returns engine ports (`runManualHook`, `rewriteMessage`, `ideMcpEndpoint`,
  `museCodeReviewer`, `judge`, `plans`, `isWorktreeHeld`, `bundledSkillsOffer`,
  `createGit`, `checkpoints`, `runBestOfNGit`), action handlers keyed by the
  existing `HostAction` union (rules/skills/memory/agents/bundled installers,
  worktree/backend actions), and an awaited cleanup callback.
- C returns presentation ports (`tasksTab`, `editReview`, `review`,
  `openDocument`, `dictation`, `exports`, `transferFiles`, `reports`,
  `usageInsights`), its existing `HostAction` handlers, optional auxiliary
  `PanelView` lookup by immutable MHP binding, and awaited cleanup.
- Duplicate action ownership refuses composition; missing handlers refuse
  `MHP_UNSUPPORTED_CAPABILITY`. Factories install the supplied caller table
  before reading UI text and register cleanup before publication. No fake
  capability, success result or placeholder feature is supplied.
- `RunPanelDeps.configureRuntime(options, settings, root)` is B's profile
  construction seam. A's main adapter supports the two existing backends;
  B owns provider catalog/configuration and backend capability records. The
  selected-model lookup identifies provider, model and a set of supported
  internal feature names. Factories must gate model-dependent operations on
  that record, never an editor or Meta-model name. An absent record refuses
  capability-dependent adapters; it does not imply universal support.

B/C must implement these consumed interfaces in their owning files, with fake
scenarios and lazy bundle readers. A's wiring is tested using injected typed
factories; this record does not claim the absent adapters are complete.
