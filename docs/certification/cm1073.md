## Binding and ownership

The existing lazy `createTeamRunnersRuntime` exposes `createResourceRouting`.
It registers cached approved-route availability, loads the existing window
resource host, and creates one `ResourceRunnerRouter` per conversation. It
uses that host's governor, settings, clock, event stream and durable journal;
it does not start another sampler or discover runners at activation.
`routeChecks` uses this binding through `CheckRoutingDeps.resources` when the
local governor reaches relocate/pause. Normal/throttle preserves ordinary
authorized routing. Disabled/off/headless/light work and absent or revoked
approval retain existing local admission without relocation probes.

CM96C1 must supply these production ports together:

- Cached `hasTarget` reports an active, user-approved SSH check route without
  probing. Route registration changes rebind the relocation target live on
  the existing resource host (`updateRelocationTarget`); active work, queued
  admissions and pressure/override state survive, and disposal of the last
  routing removes the registration.
- `isHeavy`, live `phase`, and `isApproved` use the scheduler's exact current
  check, repository/snapshot, command and runner grants. The router's shell
  guard runs before ownership, snapshots, health probes or dispatch. No port
  grants new tool authority or permits a model worker on SSH.
- `claim` acquires exclusive attempt ownership. `settle('kept')` releases the
  relocation attempt for the scheduler's ordinary local admission;
  `settle('admitted')` transfers ownership to the existing remote completion
  path; `settle('uncertain')` retains occupancy and forbids a local retry.
  The caller retains the remote run until its existing terminal proof.
- `ask` takes an AbortSignal and uses the existing interactive confirmation.
  `row` installs target, `reason: machineBusy`, level and the provided Keep
  here action before dispatch. `notice` reports once per conversation;
  `traffic` receives each admitted relocation event. All are required ports.
- The existing SSH `sample`/`remote` and local scheduler admission fill
  `CheckRoutingDeps`. The receiver's validated durable start receipt invokes
  `onAdmitted`; output/completion remains owned by its existing transport.
  Existing paid rules stay with the caller; SSH checks introduce no paid call.

Checks share a pending attempt through both remote completion and local
fallback, including pressure recovery; disposal remains closed at every level. Keep here withdraws unanswered Ask and pre-admission dispatch;
after durable admission it cannot cause a duplicate local run. Lost transport,
wrong completion identity and an exception after sending remain uncertain.
Only a proved busy/offline refusal returns to local admission. The receiver
rechecks load, valid core counts and available slots inside its allocation
lock before creating a relocated run. Linux/macOS use the existing POSIX
helper; Windows uses its existing PowerShell helper and job containment.

### Failure 1 — drill A `EBUSY` removing `runs\check-1\output`

The launch worked (run folder with an output file: the helper started
under the forced policy — the point of the case). The failure is after
settlement proof, in cleanup: Windows refuses to delete `output` while
a handle is open on it.

Hand-reasoned sequence. The `start` action spawns the detached job
process with the run's `output` file as its stdout/stderr
(`native/runner/runner-helper.ps1:224`, via `MuseRunnerJob::Start`,
which duplicates the log handle into the child at `:79`). The `start`
action then reports `running` and exits; the job process runs setup and
`execute`, drains its job object, writes `exit.json` atomically
(`exit.new` + `Move-Item`, `:259-260`), breaks out of the switch, and
only then does the process tear down and close its inherited stdout
handle. The test polls for `exit.json` every 250 ms, so cleanup can
land in the millisecond window between the atomic rename and process
teardown — or on a transient OS lock (Defender/indexer) on the just
released file. The healthy-load case won that race; drill A lost it.
Exit-record presence therefore does not by itself prove the handles are
closed, but it is still the run's own settle event, and it is what the
wait keys on.

Fix (test-only, the ruling implemented literally):
`awaitAdmittedSettlement` (`test/unit/resourceRunnerAdmission.test.ts`)
is the one shared waiter — it polls only the run's own exit record,
parses it, asserts `{runId, state:'ended'}`, never sleeps a fixed span
and never retries the delete. `expectAdmitted` — the single funnel
every admitting case (healthy load, drill A) goes through — calls it,
and `rm` runs once, only after it resolves. When the record never
arrives the helper throws with what it saw (the file names under
`runs/check-1`, or that the folder itself is missing), never silently;
the old bare `expect(hasSettled).toBe(true)` is gone. Refusal cases
admit no run and wait on nothing. A post-settle transient lock would
still surface as an `EBUSY` naming the file — loud and re-runnable,
not a silent pass.

Expected on the Windows rig: drill A prints
`{"runId":"check-1","state":"running"}`, the waiter observes and parses
`runs/check-1/exit.json` (`state:'ended'`), slots hold `0` →
`check-1`, then cleanup removes the folder with no handle open.

## Round 7 — "settled" means the run's processes are gone (lane CM1073R7, macmini rig)

Date: 2026-10-12. Worktree `/Users/randy/lanes/CM1073R2`, branch

### The contract

A run is settled when no process of the run exists any more and every
handle it held is closed. The exit record (`runs/<id>/exit.json`,
written atomically via `exit.new` + rename) is the announcement of
that state, so it must not be observable before the state is true.

### Who wrote the record before, and who writes it now

Before: the job supervisor — the `job` action process, itself a child
of the run's `start` spawn and running with the run's `output` file as
its own stdout/stderr — wrote the record, then exited and only then
released its inherited output handle at process teardown. On Windows
the record was therefore observable while a live process still held
`output`, and a reader that deleted the run folder in that window met
`EBUSY: resource busy or locked, unlink '...\runs\check-1\output'`
(the round-6 measurement: 1 run in 5 on the Windows rig).

Now: the same supervisor writes the record, but only after it has
observed the run's end AND closed its own output handle first. The
writer is the part of the helper that outlives the run's processes; it
is never a still-running member of the run's process set, and at the
moment the record becomes observable it holds no handle on any run
file. No sleep, no retry loop, no "wait a little" anywhere.

Before sequence (Windows, `native/runner/runner-helper.ps1` `job`):
`Run()` spawns `execute` in a job object, waits the child,
`TerminateJobObject`, loops to `active == 0` → `Remove-CacheLock` →
`WriteAllText(exit.new)` → `Move-Item` to `exit.json` → `break` →
supervisor exits (inherited stdout handle closes). Window: record
visible while the supervisor still lives and holds `output`.

After sequence (Windows): drain to `active == 0` → `Remove-CacheLock`
→ `[MuseRunnerJob]::ReleaseOutput()` (new C# method: `CloseHandle` on
`GetStdHandle(-11)`/`(-12)`, once when both name the same handle) →
write `exit.new` → rename → `break` → exit. The cache-busy early path
writes its record the same way (`Initialize-RunnerJob` first, then
`ReleaseOutput`, then the write). After `ReleaseOutput` the action
writes no console output.

Before sequence (POSIX, `native/runner/runner-helper.sh` `job`):
wait the group, kill the timer, `kill -KILL` the group, loop on
`kill -0` to group retirement → `release_cache_lock` → write
`exit.new` → rename, all while fd 1/2 (the `start` redirection onto
`output`) are still open. POSIX deletion tolerates open files, so the
race never bit there, but the contract is the same.

After sequence (POSIX): group retirement → `release_cache_lock` →
`exec 1>/dev/null 2>&1` → write `exit.new` → rename. Cache-busy path
likewise redirects before writing. Verified live on this rig: a real
`start` → `exit.json` `{state:'ended',exitCode:0}` → `status`/`output`
actions read back → run folder deletes cleanly.
