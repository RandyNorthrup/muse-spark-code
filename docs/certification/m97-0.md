## Lane-boundary decisions

- **Header-policy setting.** The lane table assigns lane 0 the
  "header-policy setting", which the plan (D76) defines as a workspace enum
  `required` / `optional` / `off`, default `optional`. Lane 0 therefore
  delivers the whole setting atomically: `LEGAL_HEADER_POLICIES` and the
  `SETTING_DEFAULTS.legalHeaderPolicy` default in `constants.ts`, the
  `museSpark.legalHeaderPolicy` manifest contribution (no `machine` scope,
  so a repository may set its own header style), its four
  `package.nls*.json` strings, and the `src/host/settings.ts` reader entry
  the settings tests require. No command contribution is added: the l10n
  gate fails an unused manifest key, so `/legal` palette/command titles
  arrive with lane B/I's contribution.
- **No `MODEL_TEXT` block.** Tool description text is model-read text and
  belongs to lanes B/S with their own block; a new block would also need a
  split-guard update (`npm run build` fails an unguarded new block), which
  is lane R/lead territory. Lane 0 adds no model text.
- **No CHANGELOG/README/docs edits.** Those files are lane I's.
- **Enum ids.** Severities use D76's own words (`blocker`, `should-fix`,
  `advice`). Categories map the brief's words to the repo's camelCase enum
  style: `license`, `copyrightHeader`, `spdxIdentifier`, `noticeFile`,
  `dependencyLicense`, `distribution`, `codeQualityHeader`.
- **Tool input shape.** `legalScanInputSchema` takes an optional explicit
  file subset (`paths`, at most `LEGAL_SCAN_PATHS_MAX`) and an optional
  per-scan header-policy override; empty input scans the whole workspace
  under the configured policy. Later lanes may add optional fields; no new
  required field may appear without a result-version review.
