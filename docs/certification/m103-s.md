## Installer

`src/host/skills/bundledSkillsInstall.ts` derives `first-party-skills` beside
`vendor/high-quality-projects-skill`, so existing callers need no new port.
Install copies the complete first-party tree inside the existing marked
package copy, then links its skills alongside the vendored skills. The one
marker governs both trees. The source remains unchanged, and no first-party
bytes are added to the pinned vendor tree. First-party ids have the same
precedence as the shared catalogue. User folders and outside links are left
alone. Remove requires the valid marker and only removes links into the
marked copy's two skill roots. An obsolete first-party link is removed on
update. The existing Windows junction / POSIX symlink selection applies.

The existing portable `fingerprint` helper supplies SHA-256, so the host API
record needs no new Node import. The installed tag includes the SHA-256 of
sorted first-party paths and bytes.
This makes old vendor-only installs, new skills, and topic edits eligible for
the existing Update offer without changing the vendor release. A package
without the first-party root retains the old tag and behavior. Linked roots,
linked skills/entries/topics, invalid ids and missing entries are refused
before installation writes. A failed first-party link install undoes its new
copy and links.

`bundledSkillsInstall.test.ts`: 41 tests passed, including ten new first-party
cases (the link refusal is parameterized over four locations). Real symlinks
and the actual lazy built bundle are used. Cross-platform link types are
checked on Kubuntu; a native Windows/macOS run remains integration evidence.
The shipped first-party pack is also installed through real links; every
entry and topic is compared byte-for-byte with its source, then removed.

## Skill pack

Nine entrypoints (each at most 64 lines) route to topics read on demand:

| Id                | Topics                                                             |
| ----------------- | ------------------------------------------------------------------ |
| maker_firmware    | PlatformIO; Arduino; ESP-IDF/ESPHome; Pico SDK/Zephyr              |
| maker_micropython | MicroPython and CircuitPython deployment/auto-reload               |
| maker_pi          | GPIO/power diagnosis; remote engine and local model placement      |
| maker_printers    | Protocol-specific status/stop; G-code and live limits              |
| maker_cnc         | GRBL/grblHAL/FluidNC status and stop; offline stock simulation     |
| maker_ros2        | Builds/tests and isolated Gazebo; physical robots status/stop only |
| maker_cad         | OpenSCAD and Python CAD exports; slicer handoff                    |
| maker_kicad       | ERC/DRC; electrical assumptions and logic captures                 |
| maker_simulation  | Local QEMU/Renode/virtual printers; explicit Wokwi cloud choice    |

Every entry carries host-only, per-action approval, no model-set confirmation,
physical stop, secret-file, unattended-worker and remote-port rules. Topics
repeat the relevant rules at the physical step. CNC/laser and real robot
motion remains refused; printer pause/cancel is actuation, not Stop. Printer
stops use the protocol's out-of-band path and state the physical switch caveat.
No shell monitor recipe is shipped: topics prefer bounded host serial access
and document PlatformIO's lack of timeout, Arduino's closed-stdin failure,
ESP-IDF reset-on-open, process-tree deadlines and port leases. Therefore no
monitor CLI invocation is claimed as certified on a socat pair.

`makerSkills.test.ts` uses the real portable loader, checks front matter/ids,
short entries, all local links and topic coverage, credential patterns,
scaffolds, recipe ids/commands/classes/evidence, host approval and stop rules,
and initial catalogue/body separation. The skill-creator helper's hyphen-only
naming convention conflicts with the requested `maker_*` ids; the project
parser and project ID pattern are the validators for these repository skills.

`m103-s-recipes.json` is the complete recipe-check list: 25 exact command
blocks, each with an action class and an honest evidence state. All 25 passed
`bash -n`. The two CMake commands ran successfully on a host C fixture and the
resulting program exited 0; this proves generic CMake syntax/build behavior,
not a Pico SDK build. The remaining 22 toolchain commands are explicitly
`pending-toolchain`, and the Wokwi command is `pending-user-cloud-opt-in`.
The PlatformIO, Arduino CLI, ESP-IDF, Zephyr, mpremote, OpenSCAD, KiCad,
CAMotics, Renode and ROS commands are absent on PATH on this rig. A Pico SDK
build was not run. The shared brief forbids network acquisition; no missing toolchain was replaced
by a fake production implementation or represented as a successful recipe.
Wokwi needs the user's explicit cloud choice and private token; it was not run.
