# M91: hooks from every popular agent

Recorded on branch `feature/m91-hooks-parity`, from main `1e93c67c`. PLAN.md
D70 and M91. The research is in `m91-research.md`, a copy of the research
report of 2026-10-04.

## Step 1 captures (2026-10-04)

AGENTS.md rule 13: no Interrupt, SessionFork, StopFailure or PostToolBatch
wiring is written from a guess. These runs are what lane R wires from.

### How they ran

- **The CLI.** Muse Code 1.4.2 (`1.4.2-R4684.1`), the same build in both
  places:
  - On the Windows host, `muse-bin-1.4.2-R4684.1.exe`: the binary that
    `muse.cmd`'s launcher runs and that the extension spawns directly
    (D25).
  - On the Kubuntu rig, `~/.local/bin/muse-bin-1.4.2-R4684.1`.
- **The driver.** `muse serve --provider echo --trust-workspace` (run 7 adds
  `--disable-sandbox`), spoken to over MSP through the SDK's
  `spawnMspConnection`, `initialize`, `session/start`, `turn/start`,
  `turn/cancel`, `turn/interrupt`, `session/fork` and `session/userShell`, as
  `src/core/backends/musecode` speaks them. Run 3 drove the interactive TUI
  instead (`muse --provider echo --workspace <workspace> --trust-workspace`)
  in a pseudo-terminal, typing `/fork`.
- **The hook.** One recording command for each of the 19 events, in
  `.muse/hooks.json` (`hooks.json` in each run's folder). It writes its stdin
  to `payloads/` and answers as a control file says, so one host can be
  asked several verdicts: `log` (exit 0, no output), `allow`, `refuse2` (exit
  2 with a reason on stderr), `refuseJson` (`{"decision":"block"}`),
  `refuseContinue` (`{"continue":false}`), `crash` (exit 1), `timeout` (15 s
  against a 2 s `timeout`), `sleep:<s>`. Interrupt is `async: true` and
  SessionFork `async: false`, the only forms Muse Code accepts (research run
  C).
- **Isolation.** Each run had a fresh workspace under the scratchpad holding
  only that file, and its own home: `HOME`, and `XDG_CONFIG_HOME`,
  `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` under the run.
  Neither the owner's settings nor his trace logs were read or written.
  Every `*_API_KEY`, `META_*` and token variable was removed from the
  child's environment.
  - No sign-in or sign-out ran.
  - The Model API key was never used.
  - No provider other than echo ran.
- **The count.** Before each run, the expected number of model calls was
  stated: 0. Afterwards it was counted from that run's own trace log
  (`<home>/data/muse/local-tracing/bootstrap/*.log`, the
  `event="model.attempt.lifecycle"` lines with `phase="admission"`).
  - The echo provider's local replies show there too, as `provider="echo"`.
  - So do the replies of Muse Code's own reminder agents: every echo turn
    ran SubagentStart and SubagentStop for them.

Run 3's TUI trace names the provider and model `unknown`. Three things

- The session was echo: the status line read `echo`, and so did the reply.

### (a) SessionFork: never run by 1.4.2

- **Payload.** None exists: in 21 forks the hook process never started.
- **Verdict effects.** None. Every mode left the fork to go ahead, or fail,
  exactly as with no hook: `log`, `allow`, `refuse2`, `refuseJson`,
  `refuseContinue`, `crash` and `timeout`.
  - **Run 1 (Windows).** All seven `session/fork` calls were refused before
    any hook: `forkBoundaryInvalid` (-32023), "invalid fork boundary …:
    WriteFailed". This is meta-models/muse-code-sdk#31, still open on 1.4.2.
  - **Run 2 (Linux, MSP).** All seven forks succeeded in about 155 ms each,
    whatever the hook would have said, `timeout` included (the hook's
    timeout was 2 s). The trace shows `hook.admission outcome="ready"
handlers=19 runnable=19`, so SessionFork was accepted. It also shows a
    `session.fork.materialization` task per fork, and no
    `hook.execution.terminal` for `session_fork`.
    - Each fork ran SessionEnd when the host closed (8 SessionEnd in all),
      but none ran SessionStart.
  - **Run 3 (Linux, TUI).** All seven `/fork`s printed "Fork created: <id> ·
    Source session stays active" (`screen-fork-lines.txt`). No SessionFork
    hook ran.
- **What it means.** The binary's example plugin (`hooks/session_fork.py`)
  documents an intent that 1.4.2 does not run on either fork path a client
  can reach.

### (b) Interrupt

The payload (`04-…/payloads/013-Interrupt-Interrupt-log.json`), the same in
every case:

```json
{
  "hook_event_name": "Interrupt",
  "session_id": "<id>",
  "turn_id": "<the cancelled turn>",
  "cwd": "<workspace>",
  "transcript_path": null,
  "model": "echo",
  "permission_mode": "default"
}
```

| Cause                                                                    | Turn's `turn/completed`                      | Interrupt | Run           |
| ------------------------------------------------------------------------ | -------------------------------------------- | --------- | ------------- |
| `turn/cancel` 2.5 s into a turn                                          | `cancelled`, "cancelled during model step"   | Fired     | 4             |
| `turn/cancel` 2.5 s into a turn held in a sleeping UserPromptSubmit hook | `cancelled`, "cancelled before model step"   | Fired     | 4             |
| `turn/interrupt` 2.5 s into a turn                                       | `cancelled`, "cancelled before model step"   | Fired     | 4             |
| A UserPromptSubmit hook exited 2                                         | `cancelled`, the hook's stderr as the reason | Fired     | 5             |
| The host closed while a UserPromptSubmit hook held the turn              | (none: the host closed)                      | Fired     | 6             |
| The host closed with no turn running                                     | —                                            | Not fired | 1, 2, 4, 5, 7 |

- **Stop and StopFailure** fired on none of the cancelled turns.
- **Timing.** The hook is async: on Windows it ran 1 to 2 s after the cancel
  was acknowledged (trace `hook_event="interrupt" status="completed"`).

### (c) StopFailure and PostToolBatch: neither fired

- **StopFailure: no.** Two turns failed without firing it (run 5):
  - A PreLLMCall hook that exited 2 failed its turn: `terminal: "failed"`,
    error `{"kind":"modelError","message":"m91 capture: refused by exit
2","retryable":true}`.
  - A PreLLMCall `{"decision":"block"}` did the same.

  Neither StopFailure nor Stop ran on either turn. This matches the 1.4.2
  trace schema's note that StopFailure is "production-dark".

- **PostToolBatch: no; it cannot be reached with 0 model calls.**
  - The echo provider plays back text and never calls a tool. Its only
    setting in the binary is `--echo-delay-ms`.
  - The one tool path without a model is a user shell command
    (`session/userShell`, the composer's `!` mode). It ran PreToolUse, then
    PostToolUse, or PostToolUseFailure (runs 5 and 7). It never ran
    PostToolBatch.
  - The tool payloads name `tool_name: "shell"`,
    `tool_use_id: "user_shell_<commandId>"` and `model: "unknown"`. They
    carry `tool_response: "m91\n"` on success, and on failure
    `error: "tool failed: exit status: 3"` and `is_interrupt: false`.
  - With the sandbox unavailable in the isolated home, the failure was
    "environment failure: managed shell sandbox is unavailable".
  - M91's live check (one contributor-model turn with a tool call) captures
    whether a model batch runs it.

### Also seen

- **SessionStart** fires when the first turn starts, not at `session/start`
  (runs 1 to 4).
- **`continue: false`** from PreLLMCall or UserPromptSubmit was ignored: the
  turn completed (run 5). This matches `STOP_EFFECT_EVENTS` in `hooks.ts`.
- **On Windows, SessionEnd at host close is cut short.** In run 1 the hook
  wrote its payload, but the trace says `status="cancelled"`. In run 4 it
  never ran.
- **User shell commands** on Muse Code run the PreToolUse and PostToolUse
  hooks, under `tool_name` `shell`.

### What changes for the lanes

- **Lane R, Interrupt.** Interrupt fires on every cancellation of a running
  turn: Stop, a UserPromptSubmit block, and closing the session while the
  turn runs. It never fires on an idle close. The approved draft said
  "never on dispose". The capture says Muse Code fires it on a dispose that
  cancels a running turn, so D70 and M91 follow the capture.
- **Lane R, SessionFork.** SessionFork's veto is not wired. It is accepted
  (sync only) and runs nothing on the Model API, as on Muse Code 1.4.2, until
  a release's capture shows it running. Its test becomes "an async
  SessionFork is refused, and a sync one runs nothing".
- **Lanes E and W, StopFailure.** StopFailure stays on the Model API. The
  Hooks picker and the README say that Muse Code 1.4.2 does not run it.
- **The live check.** It adds one Muse Code turn with a tool call, to
  capture PostToolBatch.

### Files

`m91-captures/<run>/` holds:

- `hooks.json`;
- every hook payload (`payloads/NNN-<event>-<label>-<mode>.json`);
- `hook-sequence.txt`, the order the hook ran in;
- `calls.jsonl`, the MSP calls and their answers;
- `turn-completed.jsonl`;
- `driver.log`;
- `trace-summary.json`: the attempt count by provider, model, phase and
  outcome, the credential status and the hook trace lines;
- `screen-fork-lines.txt` (run 3).

Scrubbing:

- Paths are scrubbed to `<workspace>`, `<home>` and `<scratch>`.
- The export fails if a user name or a home path is left.
- The driver scripts (`cap.mjs`, `hook.cjs`, `tui_fork.py`, `export.mjs`)
  stay in the lead's scratchpad (`m91-cap/`), because they carry that
  machine's paths.
