  `.muse/hooks.json` (`hooks.json` in each run's folder). It writes its stdin

  asked several verdicts: `log` (exit 0, no output), `allow`, `refuse2` (exit

  `refuseContinue` (`{"continue":false}`), `crash` (exit 1), `timeout` (15 s
  against a 2 s `timeout`), `sleep:<s>`. Interrupt is `async: true` and

- **Isolation.** Each run had a fresh workspace under the scratchpad holding
  only that file, and its own home: `HOME`, and `XDG_CONFIG_HOME`,
  `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` under the run.
  Neither the owner's settings nor his trace logs were read or written.
  Every `*_API_KEY`, `META_*` and token variable was removed from the
  child's environment.
  - No sign-in or sign-out ran.
  - The Model API key was never used.
  - No provider other than echo ran.
- **The count.** Before each run, the expected number of model calls was
  stated: 0. Afterwards it was counted from that run's own trace log
  (`<home>/data/muse/local-tracing/bootstrap/*.log`, the
  `event="model.attempt.lifecycle"` lines with `phase="admission"`).
  - The echo provider's local replies show there too, as `provider="echo"`.
  - So do the replies of Muse Code's own reminder agents: every echo turn
    ran SubagentStart and SubagentStop for them. Their payloads carry only
    the child session id, with no parent session or turn. This is filed as

### (a) SessionFork: never run by 1.4.2

- **Payload.** None exists: in 21 forks the hook process never started.
- **Verdict effects.** None. Every mode left the fork to go ahead, or fail,
  exactly as with no hook: `log`, `allow`, `refuse2`, `refuseJson`,
  `refuseContinue`, `crash` and `timeout`.
  - **Run 1 (Windows).** All seven `session/fork` calls were refused before
    any hook: `forkBoundaryInvalid` (-32023), "invalid fork boundary …:

  - **Run 2 (Linux, MSP).** All seven forks succeeded in about 155 ms each,
    whatever the hook would have said, `timeout` included (the hook's

    `runnable=19`, so SessionFork was accepted. It also shows a
    `session.fork.materialization` task per fork, and no
    `hook.execution.terminal` for `session_fork`.
    - Each fork ran SessionEnd when the host closed (8 SessionEnd in all),

  - **Run 3 (Linux, TUI).** All seven `/fork`s printed "Fork created: <id> ·

### What runs an imported hook

Lane I writes each hook from another agent as one `spark-hooks.json` group
with its import record (`m91-i.md`). Lane P's adapters read that record
(`m91-p.md`). Lane W connects the two:

- **Loading.** `loadForeignHookDefinitions` (hooks.ts) reads both
  spark-hooks.json files under M51's gates: a trusted workspace, the
  `museSpark.modelApiHooks` opt-in, the project file confined to the
  workspace, and the per-session snapshot. Each group carrying `format` is
  checked field by field:
  - `format` is one of `HOOK_FORMATS`, and `flavor` names a contract of that
    format;
  - `pathPattern` is Kiro's only, and `commandPattern` and `failClosed` are
    Cursor's only;
  - `loop_limit` is Cursor's, on Stop and SubagentStop only;
  - a regex compiles under the bounded deadline;
  - the handler's `cwd` is relative and inside the workspace by its text.

  The handler and the matcher are then parsed by the native rules, so an
  imported hook has a native hook's bounds. Muse Code's own
  `.muse/hooks.json` still refuses a `format` group.

- **Dispatch.** `dispatchHooks` hands each imported hook to the
  `ForeignHookAdapter` its caller gives. Without one, the hook is skipped
  with a warning and never runs natively. The process runs through the same
  host-wide cap, allowlisted environment, timeout and tree kill as a native
  hook. The ending is reported as an exit, a timeout, a crash or a refusal.
  Any grant an adapter returned is stripped, and a failure never becomes
  PostToolUse feedback.
- **The adapters' bundle.** `foreignHooksEntry.ts` is the entry of
  `dist/foreignHooks.js` (64.9 KiB when split out, 68.0 KiB with lane X's
  Cline contract; budget 75 KiB). A session loads it the
  first time it runs a hook while holding an imported one. The entry decides,
  by each source's own rules:
  - **Whether the source would run the hook at all.**
    - Cursor's `commandPattern` is tested against the command (CH:745). A
      clipped preview, or a pattern the bounded matcher cannot finish, runs
      the guard: running more often is never weaker.
    - Kiro's `PostFileCreate` runs on a call that created its file and
      `PostFileSave` on one that changed it. `fileOperationOf` reads the
      call's own patch document. `PostFileDelete` never runs: no tool here
      deletes.
  - **The directory.** A definition's `cwd` is confined once links and
    junctions resolve (`confineWorkspacePath`), and the hook runs in the
    canonical directory. A Cursor user hook runs from `~/.cursor`, as Cursor
    runs it (CH:653), so its relative script paths resolve.
  - **The shell on Windows.** Copilot CLI runs `powershell` there, and the
    `command` it copies to it (C:124,128); Windsurf runs both through
    `powershell -Command`; Cline runs `<HookName>.ps1` with PowerShell. Here
    hooks run through cmd.exe, as Muse Code's do, so these are handed to
    `powershell.exe` as an encoded command, with UTF-8 output. A line longer
    than cmd's 8191 characters is refused, never cut.
  - **Timeout against crash.** Copilot lets a timed-out hook through on
    every event (C:854). The others read a timeout as a crash (exit null),
    so Cursor's `failClosed` blocks on it (CH:707). A guard that could not
    start, or whose stdin could not be translated, fails as its source
    fails. Both endings add a notice that names the format
    (`hookAdapterFailClosed`, `hookAdapterUnreadable`).
  - **Loop limits.** Cursor's `loop_limit` bounds a stop or subagentStop
    script's follow-ups in the conversation: 5 by default, and `null`
    leaves only this window's cap of 8. `loop_count` goes on its stdin.
- **Replacements before packing (SoL-Pi rule 2).** A documented output
  replacement (Cursor `updated_mcp_tool_output` for MCP tools, Copilot
  `modifiedResult`) replaces the call's replay output before the next
  request is built. So ObservationPack archives what the model saw, and
  `recall_output` returns those bytes. The row keeps the real output, and a
  notice says the model saw the hook's (`hookOutputReplaced`). A Copilot
  subagentStop `modifiedResponse` becomes the reply the parent reads.
- **The Hooks picker** lists `.muse/hooks.json` and `.muse/spark-hooks.json`
  for the project, and the settings `hooks` block and the user's
  `spark-hooks.json`, with the backend that runs each. A spark-hooks.json
  row names its imported formats and says they run on the Model API backend
  only. The notes for StopFailure and SessionFork, and for an event in the
  wrong file, come from lane 0's strings.
- **The MessageDisplay marker.** The panel marks an assistant reply whose
  `displayText` differs from its text: above the reply, outside the
  Markdown the hook wrote, so no hook can hide it. The original is one click
  away, and copy always takes the original. Lane E fires the event and sets
  the field; this branch carries the same field lines.

### semgrep: prototype pollution in lane P's engine

semgrep's `prototype-pollution-loop` flagged `engine.ts:38`, the dotted-path
walk of the contract tables. The paths come from the tables, never from a
hook's output, but the walk read inherited keys and the writer would have
walked `__proto__`. Fixed at the cause, no suppression:

- a path segment named `__proto__`, `constructor` or `prototype` reads
  nothing, and the writer refuses the whole path (the build then refuses,
  failing closed on a blocking row);
- reads take the record's own keys only (`Object.hasOwn`);
- the records built for a hook's stdin have a null prototype.

`hookFormatsEngine.test.ts` (6 tests) holds it, with a `__proto__` key in a
hook's parsed output (drills W16 and W17).
