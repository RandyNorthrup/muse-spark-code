#### What changed beyond the findings' own lines

- **Kill-on-close without new native code.** `MuseSparkJob.Join` does not
  set the limit and decision 3 allows no new C#, so the helper sets it on
  the handle it holds, through the loaded type's own Win32 binding (its
  private `held` field and its `SetInformationJobObject`). A type without
  them fails before any pipe exists; a check on every OS reads the shipped
  source for both, so a rename there fails here. Measured on the owner's
  machine: a contained process was gone 33 ms after its helper was killed.
- **The POSIX supervisor was redesigned, not patched.** The first fix had
  the supervisor report its child's process group to its caller on a pipe.
  On the Linux rig a call that kills its supervisor at once did so before
  the report was written, every time, so the caller knew no group exactly
  when it needed one. Now the caller starts the supervisor as the leader of
  its own group and the call is born into that group, so the supervisor's
  pid is all the caller needs. The supervisor can no longer signal "the
  child's group" without ending itself, so its walk of the process table
  takes a member of its own group as the call's whoever its parent is by
  now, and the native sweep of the whole group is the caller's, after every
  call.
- **This relies on an undocumented option, and the reviewer should weigh
  it.** `spawnSync` is given `detached: true`. The documented options of
  `child_process.spawnSync` and its types do not list `detached`; Node's
  code honours it there as it does for `spawn`. The two places, as read:
  `lib/child_process.js`, `normalizeSpawnArguments`, whose returned object
  carries `detached: !!options.detached` and which `spawnSync` spreads into
  its options (`...normalizeSpawnArguments(file, args, options)`); and
  `src/spawn_sync.cc`, `SyncProcessRunner::ParseOptions`, which reads
  `detached` and sets `uv_process_options_.flags |= UV_PROCESS_DETACHED`.
  The JavaScript was read from the host's own Node (v24.20.0) and at tag
  v22.0.0, the C++ at tags v20.18.0, v22.0.0 and v24.20.0 (fetched pages,
  summarised by a tool; the quoted lines are as it returned them). The
  options carry a declared type for the extra property, no cast and no
  escape hatch. The policy has passed the same option through this same
  synchronous spawn since `2636f8d63c` (2026-10-06,
  `outcomes.ts`: `detached: process.platform !== 'win32'`), though nothing
  depended on it then.
- **What stands if the option is ever ignored.** The supervisor checks, in
  the process table, that it leads its own group before it starts the call,
  and refuses otherwise. "refuses the call and starts nothing under a
  runtime that ignores detached" runs the real supervisor through a spawn
  that drops the option: exit 1, the refusal on its error stream, the
  command never started.
- **Which runtimes the pin ran on.** "starts each call in a new process
  group that its supervisor leads" asks the call itself for its group and
  its parent and compares both with the pid `spawnSync` returned. It ran on
  Node v24.18.0 (Linux rig) and v24.21.0 (macOS rig); a standalone probe of
  bare `spawnSync` with and without the option gave the same on both. Those
  are the only Node runtimes on the two rigs: no Node 22 (the floor in
  `engines`) and no VS Code (whose extension host is the window's runtime)
  is installed on either, and this lane installs nothing. Hosted CI pins
  Node 22 (`.github/workflows/build.yml`), so the floor runs it there, on
  the first push. **Owed:** that run, and the pin under VS Code's own
  runtime on macOS or Linux; until then the check above is what stands.
- **What ending the group can reach.** The group is new with each call and
  is the supervisor's alone. A pid is not handed out again while a process
  group still carries it, and a supervisor that did not come to lead a
  group leaves no group under its pid, so the signal goes to the call's own
  processes or to nobody. It is never the caller's group: the caller's
  group id is the pid of an older process, and an id of 1 or less is
  refused outright. Two tests keep a process of the caller's own, in the
  caller's group, beside a call (one whose supervisor is lost, one under
  the runtime that ignores the option) and find it running afterwards. The
  one window left is the classic one, unchanged from the supervisor's own
  group sweep before this commit: the group empties, its number wraps all
  the way round, and a new process comes to lead a group under it, in the
  microseconds between the supervisor's end and the signal.
- **`src/host/processTree.ts` is shared.** The CLI's and the ACP agent's
  playbook use the same supervisor on macOS and Linux. Their suites ran
  with it on both rigs (below).
- **Seen and not changed here: the supervisor's own start inside VS Code on
  macOS and Linux.** It is started as `process.execPath -e …`, which in an
  extension host is VS Code's own binary, and that runs as Node only while
  the environment it is given carries `ELECTRON_RUN_AS_NODE` (the
  extension host's does, as far as this lane knows: it is one of the
  variables VS Code's terminal strips from it, `toolIo.ts`). No rig has a
  VS Code to try it in, so it is not verified, and the commands the
  supervisor starts inherit the variable. Setting it for the supervisor
  alone, and not for the call, belongs with commit 4, the first to run the
  governor from a real window.
- **`GOVERNED_ROUND_TIMEOUT_MS` is 180 s, from 60 s.** The governor's tests
  are synchronous calls with no timer in them and the window's poll for the
  decision itself, so the bound is a ceiling on real work and nothing waits
