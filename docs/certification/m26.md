## macOS: what an ad-hoc signed helper means for users

Probed read-only on the Mac mini; nothing was installed or changed there.

- **Quarantine and Gatekeeper.** The Marketplace-installed 0.5.4 helper
  carries `com.apple.provenance` only, no `com.apple.quarantine`; so do the
  native binaries of Claude Code 2.1.278 and Ruff installed the same way.
  VS Code's Info.plist has no `LSFileQuarantineEnabled`, and its zip
  extractor writes no extended attributes. Gatekeeper assesses quarantined
  files ("running a quarantined app always invokes Gatekeeper", Apple
  forums 706442; Unix unzip tools "don't propagate quarantine"), so the
  ad-hoc binary runs: executed from SSH it started, answered with its
  refusal line and exited 2; `codesign --verify` says "valid on disk".
  `spctl --assess` rejects it, as it rejects any code that is not notarised,
  which matters only for a quarantined launch.
- **Whose permission it is.** tccd attributes the helper's requests to the
  process responsible for it: over SSH it logged
  `responsible=… sshd-keygen-wrapper, requesting=… dev.randynorthrup.muse-spark-code.dictate`
  and "Policy disallows prompt". From the panel the responsible process is
  Visual Studio Code: the extension host is an Electron utility process and
  VS Code's `utilityProcess.fork` passes no `disclaim` (Electron's option,
  default false), so the grant belongs to VS Code and covers everything VS
  Code starts. The owner's TCC database shows VS Code allowed the
  microphone (2026-07-23) and has no speech-recognition row; Terminal has
  both (the M9 runs).
- **The likely failure.** VS Code 1.138.0's Info.plist declares
  `NSMicrophoneUsageDescription` but not `NSSpeechRecognitionUsageDescription`
  (read on the mini; microsoft/vscode `build/darwin/sign.ts`, which writes
  those keys, adds none for speech). microsoft/vscode#307364 (open,
  backlog; a maintainer: "we cannot keep adding all the usage
  descriptions") reports speech recognition silently denied for processes
  VS Code starts, "Policy disallows prompt for Sub:{com.microsoft.VSCode}".
  Terminal declares no usage strings at all and macOS still prompted for
  it in M9, so the rule is Apple's per app, not a general one; for VS Code
  the report above is the evidence. So on macOS, dictation from the
  panel most likely ends at the speech-recognition step with no prompt,
  for every user, until VS Code declares the key. Not observed end to end:
  that needs a person at a Mac pressing the microphone in VS Code, which
  would also put a permission prompt on the owner's screen.
- **What the user now reads.** Over SSH with `--app-name "Visual Studio Code"`
  the rebuilt helper wrote: "macOS did not allow speech recognition for
  Visual Studio Code, the app that started the dictation helper. If Visual
  Studio Code is listed in System Settings > Privacy & Security > Speech
  Recognition, turn it on and try again. If it is not listed, macOS refused
  without asking, which it does for Visual Studio Code because Visual Studio
  Code does not declare speech recognition (microsoft/vscode#307364);
  dictation cannot work there until it does." with `step: asking macOS for
speech recognition for Visual Studio Code` on stderr, exit 2. A helper
  that macOS ends at a request, or refuses to start, is reported with the
  last step and the early-exit hint.
- **Signing** would change none of this: it matters only to Gatekeeper,
  which never sees an unquarantined helper, and TCC's attribution is by the
  responsible app either way. The one route to a working prompt without VS
  Code's key is for the helper to disclaim responsibility and re-launch
  itself (`responsibility_spawnattrs_setdisclaim`, the private call
  Chromium, Qt and Electron's `disclaim` option use), so that macOS asks
  for `muse-dictate` itself with its embedded strings; an ad-hoc signature
  would then tie each grant to one build. Not built: it rests on a private
  interface and needs a person at a Mac to verify; it is the owner's call.

## Findings recorded during the milestone

- A live child that closes its stdin does not fail the parent's next write
  on Windows (both `process.stdin.destroy()` and `fs.closeSync(0)` were
  tried: the writes succeeded and the child exited normally 3 s later), so
  the broken-pipe test uses a real `Writable` that fails like a dead pipe.
- VS Code's `remoteName` is set in both extension hosts of a remote window;
  only the extension's kind says which side it runs on.
- `npm ci` with this repository's lockfile runs three install scripts
  (`esbuild`, `@vscode/vsce-sign`, and `fsevents` on macOS) plus husky's
  `prepare`; `vsce publish --packagePath` of an unsigned package never
  touches `@vscode/vsce-sign`'s binary (publish.js signs only with
  `--signTool` or a signature manifest).
- `actionlint` could not be run: the npm package of that name is a 2022
  WebAssembly library with no command (maintainer `hops-release`), and the
  real tool needs Go or Docker, neither of which was installed for this.
  The workflows were parsed with the `yaml` package already in the tree and
  reviewed by hand; `build.yml` runs in this pull request's CI, `release.yml`
  first runs on the next tag.
