## What this lane built

`hooks.ts` (events and parsing):

- `HOOK_EVENTS` (and `WIRED_EVENTS`) gain `Interrupt` and `SessionFork`, in
  the binary's order. In Muse Code 1.4.2 both are accepted from
  `.muse/hooks.json` (capture run C: `runnable=19`).
- Interrupt is async-only: a sync Interrupt handler is refused at parse
  (`Interrupt must be asynchronous`). Research run C: Muse Code accepts
  Interrupt only as `async: true`.
- SessionFork is sync-only: an async SessionFork handler is refused at parse
  (`SessionFork cannot be asynchronous`). Research run C: the fork waits on
  its verdict. A SessionFork matcher is accepted and ignored (no match
  dimension), like `PostToolBatch`.
- `parseHookAnswer` accepts `updatedInput` on `PostToolUseFailure` (the 1.4.0
  changelog's corrected call). Every other non-PreToolUse event still refuses
  it. Interrupt stays out of `BLOCKABLE_EVENTS`: an exit-2 Interrupt fails
  instead of blocking (observation only).

`ModelApiHost.ts` (cancel, dispose, forkSession, tool-failure regions):

- Interrupt fires exactly where the captures show Muse Code firing it
  (`m91.md` §b, runs 4–6): `cancel()` while a turn or a compaction runs
  (covers Stop, `turn/interrupt`, disposal and host close through the same
  entry), a UserPromptSubmit exit-2 block, and never on an idle close. It is
  async observation owned by the session lifetime, so a turn unwind cannot
  suppress it; async answers apply nothing. Repeated cancellation is deduped
  by the running work's controller, and terminal finalization is excluded.
  Queued and running Interrupt handlers are tracked and aborted on disposal.
- A UserPromptSubmit exit-2 block now ends the turn `cancelled` with the
  hook's reason (capture run 5, `turn/completed` terminal `cancelled`), via a
  new `HookCancelledError` mapped in `runTurn`'s catch. Every other hook stop
  (PreLLMCall block, SessionStart `continue: false`, …) still fails the turn,
  as the captures show. This changes the pre-M91 `failed` terminal asserted by
  `modelApiHost.test.ts`'s `blocks a prompt…` test; the assertion is updated
  with a capture citation (contract change per the binding lead decision).
- `forkSession` is unchanged: SessionFork parses but fires nothing until
  upstream [meta-models/muse-code-sdk#84](https://github.com/meta-models/muse-code-sdk/issues/84)
  is answered (21 forks in runs 1–3 never started the hook).
- PostToolUseFailure `updatedInput` runs the same tool again as a new call
  through PreToolUse, policy, path confinement and approval, bounded by
  `HOOK_ON_FAILURE_MAX_DEPTH` (3). Refusals name their reason for the model
  (`hookCorrectionRefused` + one of the lane-0 reasons) and the original
  failure stands:
  - a `tool_name` naming another tool → refused (`hookCorrectionOtherTool`);
    a restated same-tool name is stripped as envelope, not tool input;
  - a `path` outside the workspace → refused (`hookCorrectionOutside`),
    checked with the same `editTarget` confinement the call would run under
    (memory tools exempt: their paths live under scope roots);
  - past the depth bound → refused (`hookCorrectionTooDeep`).
  - A stop (`continue: false`) still stops: no corrected call runs after it.
    A backgrounded call is still running and is never corrected.
  - The superseded attempt keeps its transcript row, but its
    `function_call_output` and trailing attempt contexts/feedback leave the
    replay so one `call_id` answers once, before replacement contexts (with
    its queued media and unread files dropped).
  - The same bounded correction applies to `then_run` and configured check
    commands through `runVerifyCommand`. The corrected shell command gets a
    new PreToolUse dispatch and full admission/approval, preserving the
    original edit guard and without repeating the edit. Invalid corrections
    explain their refusal in replay using the existing localized reasons.
- Backend failure semantics (pre-existing, M51): a non-zero shell exit is
  model data, not a failure (`shellOutcome` sets `failureReason` only on
  timeout/cancel). The correction rides on the backend's existing failure
  notion — wherever `PostToolUseFailure` already fires (rejections, thrown
  errors, timeouts) — not on shell exit codes.
