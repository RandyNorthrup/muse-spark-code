## Findings recorded during the milestone

- The SDK's `spawnMspConnection` takes no `windowsHide` and spawns without
  it; no console window appears because the extension host's own console
  is hidden and inherited. Every spawn the extension makes passes it.
- On Windows a background child started by a test command held the test's
  temporary folder open after the command returned, so its removal failed
  with `EBUSY`; the drill now starts that child in another folder.
- An earlier run showed why "the pipes closed" is the wrong end of a
  command: with `ping` left running by `Start-Process -NoNewWindow`, the old
  runner waited the full 30 seconds.

## 0.10.1: a slow start, and one card per failed start (2026-10-02)

**The report.** On the owner's machine, starved of CPU (VS Code's
activation took 211 s), `muse serve` missed the 30 s handshake deadline
and was killed, and every caller waiting on that one start posted its own
red card, "That did not work (the Muse Spark log has the details): Muse
Code did not finish starting within 30 s": six skill listings (the palette
and the slash menu ask each time they open) plus the warm-up's notice.

**The change** (PLAN.md D25, the new row):

- `withSlowDeadline` (`src/core/timeouts.ts`): past the first deadline, a
  start whose process still runs (`handshake.exited` has not settled) gets
  one longer wait, `MSP_SLOW_HANDSHAKE_TIMEOUT_MS` (120 s) in all, logged
  as "muse serve is still starting after 30 s and its process runs; waiting
  up to 120 s in all". 120 s is four times the first deadline; a healthy
  start connects in a second or two. A process that exits fails the
  handshake at once, as before; one still silent at 120 s is ended. The
  text keeps the MCP pool's phrasing ("did not finish starting within
  N s"); no new user-visible text, so no table changed.
- `ConversationController`: every waiter on one start gets the same
  rejected error, so a failure is shown once per panel (`shownFailures`):
  a message's own failed card always (it must give the composer back its
  text), another action's card only if nothing showed it yet, and the
  warm-up's notice last, after a turn of the event loop, only if nothing
  else did. Skill listings log "The skills were not listed: …" and never
  show a card. The shared start is forgotten once it fails, so the next
  action starts afresh.

**Tests.** `timeouts.test.ts` (fake timers, the real constants): a start
answering at 45 s connects and says it waits once; one whose process
stopped fails at 30 s; a running one that never answers ends at 120 s and
not before; a rejection at 40 s fails at once. `conversationController.test.ts`
"one card for one failed start": six skill listings and the warm-up show
one warning; a message, a listing and a compaction show only the message's
card; two compactions show one card and the next listing starts the
session. `museCode.e2e.test.ts` against the fake CLI (new `slow` and
`dying` start modes): a slow start answering at 1.5 s past a 0.5 s first
deadline connects; a silent host ends at the 2 s total with the log line; a
process exiting during the longer wait fails at once.
