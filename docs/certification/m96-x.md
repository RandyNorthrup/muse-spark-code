# M96 lane X (C-M96-3): the team host service and its VS Code binding

Branch `c/m96-3` from `82d50d5e4` (v0.17.0). Host lane (Claude), 2026-10-10.

## What this lane adds

- **The interface** every surface binds to: `src/core/team/teamHostService.ts`
  (`TeamHostService`, `TeamHostSeams`, `TeamHostServiceDeps` and the ports
  `TeamStatePort`, `TeamSettingsPort`, `TeamOrchestratorPort`,
  `TeamWorkerPort`, `TeamMergePort`, `TeamPaidPort`, with `TeamTaskSpec`,
  `TeamWorkerOutcome`, `TeamMergeOutcome`, `TeamWaitingChoice`,
  `TeamMergeDecision`, `TeamSnapshotReader`). Types only, no `vscode`.
- **The implementation**, `src/core/team/teamHost.ts` (`createTeamHostService`,
  `readStoredTeam`), exported from dist/team.js as `createTeamHost`:
  - the decision source a conversation reads at its first request, from the
    stored team (`museSpark.team.config`), the settings, the worker port's
    `canRun` and the setup probes' results; the conversation passes its own
    model, so Default and `sameModel` compare against the real orchestrator;
  - the roster (stable part from the stored roles, live part from the tasks);
  - the runner: `preview` (dry run), `delegate` (trust, per-entry
    concurrency and `tasks` caps, `museSpark.teamMaxWorkers`' computed
    default, one D48 popup per call for key tasks, Default resolved to the
    orchestrator slot's model), `collect` (no wait: the bound is 0 until the
    Muse Code capture), `cancel`, and `merge` (refused in Plan mode; "not
    reviewed", so it asks on the tree's card in every other mode);
  - the Agent map's tree (undefined while the workspace is single-model:
    today's map) and the actions Stop, Stop all, Merge, Discard and Reset.
- **The window binding**, `src/host/teamHostBinding.ts` (`TeamHostBinding`,
  `TeamSurfacePort`, `TeamSurfaceMessage`): kept outside `src/host/team/` like
  `teamViewBundle.ts`, because the activation-graph gate
  (`teamActivationGraph.test.ts`) refuses team runtime modules in
  dist/extension.js; it imports only types from the team modules and loads
  dist/team.js only for a workspace that stores a team, with `museSpark.team`
  on.
- **VS Code wiring**: `extension.ts` builds the binding over VS Code's ports;
  `ModelApiBackendManager` passes its seams to the window's host only (never
  a best-of-N attempt host); `ConversationController` answers
  `stopTeamTask`, `stopAllTeamTasks`, `decideTeamMerge`, `answerTeamWaiting`,
  `resetTeamEntry`, `openTeamRoles`, `openTeamTaskTranscript` and
  `reviewTeamDiff` through it and shows the tree (`showTeamTree`); a chat
  surface's opening runs the declared setup probes.
- **Switch** `museSpark.team` (D75's, on unless set `false`): not contributed
  to the manifest, not in the README or the Help reference, and no CHANGELOG
  entry until a user can save a team in Roles and run it (lead, 2026-10-10).
  The runtime reads it directly, so an explicit `false` still turns the team
  off.

## What a user can do in VS Code (round 2, after the lead's decisions)

Round 1 shipped the service with no worker; round 2 adds the engine worker
and merge ports, so a stored team now runs end to end on the Model API
backend:

1. A team is stored in `museSpark.team.config` (the Roles section, C-M96-2,
   writes it and calls `TeamHostBinding.reload()`; nothing else does yet).
2. When a chat surface opens, the setup probe lists the engine's models; a
   custom engine entry whose model is listed and differs from the
   conversation's model makes new Model API conversations team
   conversations. Default entries run on the conversation's own model.
3. The orchestrator's `delegate` starts each task in its own shared clone on
   `agents/<role>/<task-id>` (or a detached scratch copy for `read-only`
   roles) as a Model API conversation with the file tools only, billed as the
   paid feature `teamWorkers` after one popup per call. The extension commits
   the branch and publishes the `agents/` ref; a read-only copy that changed
   fails its task.
4. Every entry at its limits asks with the "waiting for you" card (Queue,
   Do it myself, Raise, Cancel) unless the role's policy is `queue` or `self`.
   Queued tasks start in order when headroom returns, or fail after
   `TEAM_QUEUE_MAX_WAIT_MS`.
5. `collect` waits up to 60 s for a task to change; `continue` reopens a
   finished, unmerged task on its own copy and branch with its report as
   handoff data.
6. `merge` shows the merge card (not reviewed, files and protected paths) and
   waits for the user's Merge or Discard there or on the tree; it is refused
   in Plan. The three-way merge writes the working tree only, keeps the user's
   uncommitted changes, returns conflicts as `rework`, and then removes the
   copy and the ref. Review diff opens the branch's diff; Stop, Stop all,
   Discard and Reset work from the tree.

Not yet in VS Code (named handoffs below): roles beyond the seven built-ins,
`in-place` (refused at planning), Muse Code and external agents, the worker
shell, a worker transcript (refused with its reason), the ledger and history,
and the orchestrator override pill.
