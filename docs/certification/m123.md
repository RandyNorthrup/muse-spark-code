### Threat boundary (the lead's decision, also in PLAN.md D104)

- **In scope, enforced:** untrusted repository content (configuration,
  hooks, attributes, filters, remotes, credential helpers, submodules,
  links inside the tree); stale state (a plan, stamp or confirmation that
  no longer matches what will run); cancellation and session or owner
  changes; secrets (no credential, model key or provider key reaches any
  Git child, terminal, log, error or the model unless that operation needs
  that credential); confinement of every read made on the model's behalf
  to the bound repository.
- **Out of scope, a residual, never claimed:** a same-user process
  renaming, swapping or replacing directories inside the user's own
  workspace between a check and the operating system acting on a path. It
  holds the user's authority already, and path-based APIs cannot close
  that race. Every guard still fails closed on any change it detects.

### The pipeline

1. **Plan:** M71's push plan plus what binds it (every push URL from
   `git remote get-url --push --all`, the branch's commit, the
   configuration files git read); or the commit form's stamp.
2. **Confirmation:** the push modal (those URLs masked) or the form's press.
3. **Admission:** the repository's transaction lock file in git's common
   directory (`transaction.ts`), shared by every editor and runtime
   process, then the host's admission (M72).
4. **Final revalidation:** the state git reads sealed (HEAD, index, refs,
   reftable list, configuration files), then the whole plan or stamp read
   again and compared with what was confirmed.
5. **Spawn:** the runner's synchronous `beforeRun` after its own admission
   and the Windows job's preparation, and again at the Windows helper's
   READY before GO: arguments, signal, owner, trust, the root a real
   directory with its bound identity, the lock held, the seal intact.

### What landed

- **P2-1, attempts forgot the watch** (`storeLock.ts`). What a process has
  watched of each lock (the instance and when it was first seen, on the
  monotonic clock) lives in one watch book per process, shared by its
  acquisitions; 10 s attempts add up to the 30 s lease, and the third
  attempt takes the lock over. A changed instance starts its watch again;
  whether its owner is gone is asked once per attempt. The rule stays:
  takeover only after watching the same instance for the lease. The book
  comes in through `StoreLockEnv`, so the module stays self-contained.
- **P2-2, the hour takeover could strand a materialized checkout**
  (`checkout.ts`). A checkout confirms it still holds its reservation
  before its folder is claimed (own: added) and right after. Displaced, it
  removes its own claim (own: its just-added worktree, through the new
  `removeOwnWorktree`) and reports the change; the record's owner, finding
  that folder in its way while it still holds the reservation, claims
  again once it is gone (`CHECKOUT_FOLDER_CLAIM_ATTEMPTS` 3,
  `CHECKOUT_FOLDER_CLAIM_RETRY_MS` 250). Every interleaving settles to one
  owner with its record.
- **P2-3, Linux births moved with the clock** (`processOwner.ts`). On Linux
  a birth is the kernel's start time in clock ticks since boot
  (`/proc/<pid>/stat` field 22) plus the boot id
  (`/proc/sys/kernel/random/boot_id`), compared exactly, never converted
  through btime; another boot means gone. Windows and macOS keep the
  creation time the kernel recorded (a later clock step does not move it;
  macOS's `ps` now prints it in UTC, so a timezone change does not either);
  their 1 s tolerance cannot tell two births within it apart.
  `LINUX_CLOCK_TICKS_PER_SECOND` is gone.
- **Found on the native Linux run: inode reuse** (`storeLock.ts`,
  `checkout.ts`). Linux handed the stale lock's freed inode number to the
  fresh lock, so the move-aside check matched a live lock by file id alone
  and deleted it (takeover and release); a folder removed and made again
  got the same inode, so a stale trust ticket still matched. A lock
  instance is now its file id, birth time and note id together; a folder's
  identity (the ticket's and the claim's) carries its birth time.
- Tests: worktree-list assertions compare paths through `isSamePath` (the
  Win11 VM spells its temp folder `C:/Users/randy`, git prints the real
  `Randy`; a case-sensitive `not.toContain` would also have passed
  vacuously). The property race now forces one takeover mid-write on any
  machine: the first window holds its first publish until the eager
  window has taken the lock over and published that very generation (at
  most 2 s), so the fence must refuse it. On the loaded Win11 VM the
  timing-only race had produced no conflict.

### Design

- **LOCKLIB** (`src/core/locks/fileLease.ts`, `nodeLeasePort.ts`;
  `processOwner.ts` moved to `src/core/locks/`). One cross-process lease on
  a file, pure over an injected port (file operations, wall and monotonic
  clocks, the owner probe, the watch book). `acquireFileLease()` returns a
  lease with its `fence` (an exclusively created `<lock>.fences/<n>`,
  strictly above every earlier one and above any floor the caller's data
  carries), `isHeldSync()` (the lease runs on the holder's monotonic clock,
  the lock file is this instance, the highest fence is this one),
  `renew()` (rewrites the holder's own note in place, bound to the open
  file's identity) and `release()` (retires only its own instance).
  Takeover follows the watch book: only the same instance (file id, birth
  time, note id, renewal), watched unchanged for its holder's lease on the
  waiter's monotonic clock. Takeover moves it aside and proves it; unproven
  for any reason (a read error, a mismatch) it is linked back while the
  name is free and the waiter waits on; when it cannot go back the waiter
  ends busy and the file stays aside, never removed. `storeLock.ts` is gone.
- **Fenced registry** (`recordGenerations.ts`, `records.ts`). The store
  runs over a `RecordRegistry`: each hold takes the lease, reads the head
  and publishes at most once, by compare-and-swap (refused while the head's
  fence is not below the hold's, refused once `isHeldSync()` fails just
  before the link, and the exclusive link of generation N+1). Every record
  written carries its hold's fence; a reservation is a checkout id and that
  fence. `claim`, `complete` and `discard` compare-and-swap on it;
  `supersede` on the version read, with the folder checked absent under the
  same hold. `claim` publishes the claimed record, then makes the folder
  under the same hold. A memory registry (one window) and the file registry
  share the store code; deleting the fences is recovered (holds go above the
  records' fence).
- **Dispatch gate** (`checkout.ts`). Every git the module starts goes
  through `runGit` or `startGitBatch`: the gate, then the process, in one
  synchronous turn (`nodeGitProcesses`, injectable as `processes`). The
  checkout's gate: trusted, not cancelled, `holdsSync(reservation)`; the
  cleanup's gate: trusted (refused, the folder is removed without git and
  the registration left to git's prune); file writes: trust and Cancel. The
  protocol moved into `PullRequestCheckoutProtocol`: reserve, claim (the
  folder made under the hold), git through the gate, complete by
  compare-and-swap; refused or not known, remove exactly what was made,
  then discard the own reservation. The confirm/retry machinery of rounds
  5–6 (`CHECKOUT_FOLDER_CLAIM_*`, `removeOwnWorktree`) is gone; own and held
  checkouts claim their folder the same way.
- **Found while building it.** The pending owner's schema dropped `bootId`
  (zod strips unknown keys), so a Linux pending owner could never be judged
  gone by its birth (only the hour applied); it now keeps it. The
  interleaving test found one more order: a checkout that never made its
  folder kept its reservation when another window's (stale) folder stood
  there; a failed checkout's record now goes once nothing _it made_ is
  left, whatever else is at the path. `hasAdded` is set only once git's add
  succeeded, so a refused add never removes content it did not make.

### Residuals (also in PLAN.md M123)

- **Overlap, another process.** A Serve whose last generation read the
  store answered before another process's Sign out wrote its generation
  can return its bearer after that Sign out returned: its check came
  first. A store with no lock or notification cannot close it; in one
  source the Sign-out count does (D7).
- **Windows of two store calls in another process** (no compare-and-swap):
  Publish's checks and its write; a take-back's compare and its delete;
  Refuse's compare and its delete; Sign out's write and its delete. Each
  loses a pair (that process signs in again); none serves a pair issued
  before a Sign out.
- **A crash** after Sign out's generation write, or between a write and
  its take-back, leaves an unreadable pair until the next sign-in
  overwrites it or the next Sign out deletes it.
- **A refresh whose last caller cancels** after GitHub rotated the pair
  loses the rotation (the user signs in again), as before.
