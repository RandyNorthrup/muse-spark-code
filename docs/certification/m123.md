### What landed

- **P1, stale trust restore (RVM123P2 finding 1).** The record store is now
  versioned: every record carries a per-folder `revision`
  (`src/core/worktreeConversations.ts`), and every mutation is validate →
  act → persist against the fresh state. `reserve` never replaces — a
  second checkout of a folder in flight refuses with what is there. File
  mutations hold a cross-window lock folder (`worktree-records.lock`,
  `mkdir`-atomic, stale-takeover past `WORKTREE_RECORD_LOCK_STALE_MS`,
  loud failure past `WORKTREE_RECORD_LOCK_TIMEOUT_MS`) while they
  validate and persist, so two windows never interleave a
  read-modify-write. The unconditional last-write fallback is gone: a
  mutation that cannot persist throws instead of writing over a state it
  did not read. A stale writer detects it lost (version mismatch) and
  re-reads. `release` never marks a pending checkout trusted.
  (`src/runtime/panel/pullRequests/records.ts`.)
- **P2, cross-window stranded pending (finding 2).** Checkout open is now
  claim → act → settle over the versioned store (`checkout.ts`:
  `claimAndCheckout`, `finishCheckout`, `settleComplete`,
  `offerExistingCheckout`): reserve the folder, run git, complete or roll
  back exactly the reserved version. A reserve that finds another
  checkout there follows what is there — in flight: honest
  `gitOperationChanged` refusal; finished with folder: reopen offer;
  finished without folder: `supersede` at exactly the version read. A
  complete that lost re-reads: a reserved record found ready is success.
  The per-instance folder queue stays for same-window opens.
- **P2, batch surviving its deadline and Cancel (finding 3).** The batch
  child runs detached in its own process group (POSIX) with its own
  deadline (`runBatchChild`, exported for tests). The deadline kills the
  tree (`killBatchTree`: group SIGKILL on POSIX, root SIGKILL on
  Windows), destroys the pipe ends so the reader cannot hang on a helper
  holding them, observes the exit for `GIT_BATCH_KILL_GRACE_MS`, then
  settles anyway. An already-aborted signal refuses before spawn; Cancel
  mid-batch settles through the same path. Whole-tree retirement on
  Windows converges on lane G's governed runner (documented at the kill
  site); the operation settles on every platform.
- No new command, setting, UI string or bundle. The three refusals reuse
  `UI_TEXT.gitOperationChanged`; `l10n/` is untouched. New tunables in
  `src/shared/constants.ts`: `WORKTREE_RECORD_LOCK_TIMEOUT_MS`,
  `WORKTREE_RECORD_LOCK_POLL_MS`, `WORKTREE_RECORD_LOCK_STALE_MS`,
  `GIT_BATCH_KILL_GRACE_MS`; `WORKTREE_RECORD_SAVE_ATTEMPTS` now bounds
  merge retries before a loud failure. The state machine is documented in

### What landed

- **Lock** (`storeLock.ts`): one lock file created with O_EXCL; its note
  names host, process id, process start time, a random id and a 30 s lease.
  Expired = lease over (capped at the file's last write plus the lease), or
  owner provably gone (this host: no such process, or this process id with
  another start time), or a missing/torn note on a file older than
  `WORKTREE_RECORD_LOCK_UNREADABLE_MS` (2 s). Takeover and release move the
  exact instance aside with one rename and compare `dev:ino` with the
  instance judged; a newer lock moved by mistake is linked back while the
  name is free. A lock is held for one mutation only.
- **Fence** (`recordGenerations.ts`): the records are numbered generation
  files; a write stages, flushes and hard-links generation N+1, which fails
  while N+1 exists, so a writer that lost the lock without knowing it lands
  nothing and re-applies its transition to the new head. Parent write ids
  expose a publish into a number the sweep freed. The newest 8 generations
  are kept; a crash's stages and retired locks are swept after 60 s.
- **Records** (`records.ts`): every mutation names `{ checkoutId, revision }`.
  `release` takes a single-use `TrustTicket` (checkout id, revision, head
  SHA, folder `dev:ino`); `supersede` carries no trust or identity over;
  `discard` replaces `remove` and never restores a displaced record.
  `src/core/worktreeConversations.ts` gains the optional `checkoutId`,
  `folderIdentity` and `pendingOwner` fields.
- **Checkout** (`checkout.ts`): `trustTicket(folder)` is what the card shows;
  `releaseHold(ticket)` re-checks the folder's identity. A failed checkout's
  record is discarded only once its folder is gone, else it stays pending
  (held, never offered or trusted). `HeldWriters` gives the held batch one
  invalidation every publisher checks before each disk step and a drain: a
  failure invalidates first, kills the tree, waits for the writer in flight
  (`HELD_WRITER_DRAIN_GRACE_MS`), then cleans up; past the grace it rejects
  as `CleanupPendingError`, whose cleanup runs when the writer stops, the
  record staying pending until then. Cleanup (`worktree remove --force`
  with the untrusted-lane options and its own timeout, then the folder)
  runs after Cancel too. A pending record whose process is provably gone
  and whose folder is gone is taken over (crash recovery). The batch's
  stdin gets an error handler (the reviewer's inherited early-`EPIPE`
  crash; hardening without a regression test, which would need a git that
  exits before reading its input).

### Design

- **LOCKLIB** (`src/core/locks/fileLease.ts`, `nodeLeasePort.ts`;
  `processOwner.ts` moved to `src/core/locks/`). One cross-process lease on
  a file, pure over an injected port (file operations, wall and monotonic
  clocks, the owner probe, the watch book). `acquireFileLease()` returns a
  lease with its `fence` (an exclusively created `<lock>.fences/<n>`,
  strictly above every earlier one and above any floor the caller's data
  carries), `isHeldSync()` (the lease runs on the holder's monotonic clock,
  the lock file is this instance, the highest fence is this one),
  `renew()` (rewrites the holder's own note in place, bound to the open
  file's identity) and `release()` (retires only its own instance).
  Takeover follows the watch book: only the same instance (file id, birth
  time, note id, renewal), watched unchanged for its holder's lease on the
  waiter's monotonic clock. Takeover moves it aside and proves it; unproven
  for any reason (a read error, a mismatch) it is linked back while the
  name is free and the waiter waits on; when it cannot go back the waiter
  ends busy and the file stays aside, never removed. `storeLock.ts` is gone.
- **Fenced registry** (`recordGenerations.ts`, `records.ts`). The store
  runs over a `RecordRegistry`: each hold takes the lease, reads the head
  and publishes at most once, by compare-and-swap (refused while the head's
  fence is not below the hold's, refused once `isHeldSync()` fails just
  before the link, and the exclusive link of generation N+1). Every record
  written carries its hold's fence; a reservation is a checkout id and that
  fence. `claim`, `complete` and `discard` compare-and-swap on it;
  `supersede` on the version read, with the folder checked absent under the
  same hold. `claim` publishes the claimed record, then makes the folder
  under the same hold. A memory registry (one window) and the file registry
  share the store code; deleting the fences is recovered (holds go above the
  records' fence).
- **Dispatch gate** (`checkout.ts`). Every git the module starts goes
  through `runGit` or `startGitBatch`: the gate, then the process, in one
  synchronous turn (`nodeGitProcesses`, injectable as `processes`). The
  checkout's gate: trusted, not cancelled, `holdsSync(reservation)`; the
  cleanup's gate: trusted (refused, the folder is removed without git and
  the registration left to git's prune); file writes: trust and Cancel. The
  protocol moved into `PullRequestCheckoutProtocol`: reserve, claim (the
  folder made under the hold), git through the gate, complete by
  compare-and-swap; refused or not known, remove exactly what was made,
  then discard the own reservation. The confirm/retry machinery of rounds
  5–6 (`CHECKOUT_FOLDER_CLAIM_*`, `removeOwnWorktree`) is gone; own and held
  checkouts claim their folder the same way.

  left, whatever else is at the path. `hasAdded` is set only once git's add
  succeeded, so a refused add never removes content it did not make.

### Interleavings (`runtimePullRequestInterleavings.test.ts`)

The real `PullRequestCheckoutProtocol` and store logic for one folder, over
a registry that models the lease and generations (a hold takes the lock and
the next fence and reads the head; a publish checks the head's fence and the
hold's currency, then, as a separate step, lands only on the head it read).

link, make, dispatch, remove; events are a hold's lease running out while
it is paused inside its hold (before or after its checks, or while making
the folder), trust revoked, and a window's wall clock stepped an hour
forward. A depth-first search replays each order from the start; a state
reached again with the same shared state and the same per-window history
(every value shared state handed each window) is explored once, and a hold
that can no longer run out, while no stale hold is still inside its own,
reads, checks and links in one step (everything else that can run in
between commutes with it). A first version of that last rule also merged
while a stale hold was still inside; the completion guard's red drill
caught the lost order, and the rule now stops every hold while a stale one
is inside. Checked at the end of every order: at most one window succeeds;
a folder that exists is named by its maker's finished record and its maker

### Lane G

LOCKLIB is shaped for lane G's git transaction lock (`469cc9018`'s
`transaction.ts`, unchanged here): `acquireRepositoryLock` becomes
`acquireFileLease(<common dir>/<lock file>, env)` with lane G's
`GIT_TRANSACTION_LOCK_STALE_MS` as the lease; `RepositoryLock.isHeld()`
becomes `isHeldSync()` (instance, highest fence and lease, synchronously),
checked beside the seal at each spawn with no await between; the 50 ms
presence poll that put a removed file back becomes a `renew()` timer (a
third of the lease), and a lock that is gone or taken is lost, never
re-made; the 250 ms newcomer wait goes, because a newcomer only gets the
lock by O_EXCL or by LOCKLIB's watched, proven takeover, and the fence
orders the holds; `takeOver` becomes LOCKLIB's retire (prove the moved
instance, put back what it cannot prove, busy when that fails).
