### GitHub documentation (dated)

- **Not re-read in this lane.** The WebFetch of
  `docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps`
  was refused in this session (2026-10-09, permission not granted); no
  workaround was tried. The shapes below are from the lane's knowledge of
  that page (Claude Opus 5.5, knowledge to June 2026) and match lane 0's
  fixtures:
  - `POST https://github.com/login/device/code`: `client_id`, `scope`; reply
    `device_code`, `user_code`, `verification_uri`, `expires_in` (900),
    `interval` (5).
  - `POST https://github.com/login/oauth/access_token`: `client_id`,
    `device_code`, `grant_type=urn:ietf:params:oauth:grant-type:device_code`;
    no client secret for the device flow.
  - Errors: `authorization_pending`, `slow_down` (adds 5 s; the reply
    carries the new `interval`), `expired_token`,
    `unsupported_grant_type`, `incorrect_client_credentials`,
    `incorrect_device_code`, `access_denied`, `device_flow_disabled`.
  - Revocation: `DELETE /applications/{client_id}/token` (and `/grant`)
    authenticate with Basic `client_id:client_secret`; a public client
    cannot call them. Hence Sign out = delete locally + the app's page
    `https://github.com/settings/connections/applications/<client id>`.
  - **Unsure: refresh without a secret.** GitHub's "Refreshing user access
    tokens" page lists `client_secret` as required for GitHub Apps. D104
    states a device-flow token refreshes without it; this lane did not
    confirm that. The code sends `client_id`, `grant_type=refresh_token`,
    `refresh_token` only; if GitHub refuses, the pair is dropped and the
    user signs in again (tested), so nothing breaks beyond a sign-in after
    eight hours. **The lead re-reads both pages and dates them; the first
    live sign-in (PLAN.md M123, the optional check) settles refresh.**
