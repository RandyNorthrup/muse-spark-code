### Threat boundary (the lead's decision, also in PLAN.md D104)

- **In scope, enforced:** untrusted repository content (configuration,
  hooks, attributes, filters, remotes, credential helpers, submodules,
  links inside the tree); stale state (a plan, stamp or confirmation that
  no longer matches what will run); cancellation and session or owner
  changes; secrets (no credential, model key or provider key reaches any
  Git child, terminal, log, error or the model unless that operation needs
  that credential); confinement of every read made on the model's behalf
  to the bound repository.
- **Out of scope, a residual, never claimed:** a same-user process
  renaming, swapping or replacing directories inside the user's own
  workspace between a check and the operating system acting on a path. It
  holds the user's authority already, and path-based APIs cannot close
  that race. Every guard still fails closed on any change it detects.

### The pipeline

1. **Plan:** M71's push plan plus what binds it (every push URL from
   `git remote get-url --push --all`, the branch's commit, the
   configuration files git read); or the commit form's stamp.
2. **Confirmation:** the push modal (those URLs masked) or the form's press.
3. **Admission:** the repository's transaction lock file in git's common
   directory (`transaction.ts`), shared by every editor and runtime
   process, then the host's admission (M72).
4. **Final revalidation:** the state git reads sealed (HEAD, index, refs,
   reftable list, configuration files), then the whole plan or stamp read
   again and compared with what was confirmed.
5. **Spawn:** the runner's synchronous `beforeRun` after its own admission
   and the Windows job's preparation, and again at the Windows helper's
   READY before GO: arguments, signal, owner, trust, the root a real
   directory with its bound identity, the lock held, the seal intact.
