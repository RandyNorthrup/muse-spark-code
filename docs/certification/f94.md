# F94: a restarted Muse Code backend keeps its sign-in

Lane F94FIX, branch `fix/muse-restart-signin`. Worktree on the `macbook`
rig. All captures below are 2026-10-17, `muse-bin 1.4.10-R6427.1`
(`muse --version`: `Muse Code 1.4.10 (1.4.10-R6427.1)`), macOS, throwaway
homes under the lane's `$TMPDIR`, dead proxy (`127.0.0.1:9`), dummy
credential values, 0 model attempts in every trace. No credential value
was read, printed or stored; the owner's real `~/.config/muse/auth.json`
was never opened (only the install layout around it was listed).

## The incident (from the brief)

Jobs on our app 0.18.2, Muse Code backend, CLI 1.4.7, died mid-turn
with `missing meta credentials: run muse login or set META_API_KEY`.
Order in the agent log: (1) the start line `muse serve credentials:
the CLI's own (credential file unrecognized, META_API_KEY in the
environment absent)` on every job, healthy ones included; (2) `Muse
Code reported session <id>'s event log failed (internal (MSP error
-32603))`; (3) `muse serve exited as asked (Muse Code failed with an
unhandled error (exit code 1))`, `The museCode backend stopped`;
(4) after the restart, the next turn failed on missing credentials.
Healthy jobs showed `storeFaults: 0`, failed ones `storeFaults: 3`.
The sign-in itself was valid (other jobs on the same machine kept
working). `storeFaults` is not our vocabulary (no match in `src/`);
it is CLI-side session-store evidence.

## Research: the code paths

- Spawn/restart/env: `MuseCodeBackendManager.spawn`
  (`src/host/backend/museCodeBackendManager.ts`) builds the child env
  from `childEnvironment()` on EVERY start; nothing differs between a
  first start and a restart by construction. In the ACP/headless
  runtime the env is `museCodeEnvironment` (allowlist: HOME, PATH,
  XDG_*, proxies stay; every `*_API_KEY` is stripped at agent start
  per D61). The credential path comes from `XDG_CONFIG_HOME` (else
  `~/.config`) plus `MUSE_CREDENTIAL_FILE_SEGMENTS`; `MUSE_AUTH_PATH`
  is honoured only by the POSIX launcher and is deliberately not in
  the allowlist.
- The POSIX launcher (`~/.local/bin/muse`, launcher v3) resolves its
  own credential default the same way
  (`${MUSE_AUTH_PATH:-$credential_default}`) and its
  `read_credential` expects `providers.meta` with `mechanism:
"oauth"` and a non-empty string `access_token` (plus optional
  numeric `expires_at`). The launcher never writes the file.
- The reader (`credentialFile.ts` + `cliAccount.ts`): structure only,
  values replaced by `true`. `unrecognized` means "only the CLI can
  say"; the passive estimate counts it as signed in. On macOS a
  version-1 file holding the credential was ALREADY `unrecognized`
  by design (never captured on mac).
- The event-log fault: `MuseSession.noteLogFault` matches
  `MUSE_EVENT_LOG_FAULT` (`'event log failed'`) in an `MspError`;
  the panel marks the session damaged and refuses new messages
  (`refuseDamaged`, `UI_TEXT.sessionLogDamaged`). The ACP agent had
  NO damaged-session handling and mapped a failed turn's
  `errorKind: authRequired` to a generic `internalError`
  (`AcpSession.settle`).
- Exit 3 (`MUSE_EXIT_PERSISTENT_CODES`) is the CLI's credential
  refusal: unsupported schema, unreadable Keychain item, and — new
  in this lane — a malformed file. The old exit-3 meaning text
  pointed only at settings/environment variables.

Rule, from the CLI's own mouth: **`api_key` is required in every
meta shape 1.4.10 starts with**; `access_token` without it is
fatal. The CLI never rewrote any synthetic file (no refresh with
dummy tokens and a dead proxy).

- `account/read` without `experimentalApi` (the chat host's
  posture, `noexp-probe.mjs`): refused —
  `account/read requires experimentalApi capability`. A post-restart
  re-verification through the main host is therefore impossible
  without widening its capability set (not done).
- Concurrency (`concurrent.mjs`): two `muse serve --provider echo`
  on ONE home, two sessions, two concurrent echo turns — both
  accepted, no fault. Echo provider is local-only (dead proxy
  proves it); no Meta call in any probe.
- Crash (`kill-probe.mjs`): raw-spawned serve, `session/start`,
  `turn/start`, SIGKILL 300 ms later, new host, `session/resume`,
  second turn — resume ok, second turn accepted, no `-32603`.
- `model/list` with a synthetic file + dead proxy: `{"providerId":
"meta", "source": "bundledCatalog", "models": []}` with
  `startup model-catalog fetch failed … no cached default` on
  stderr. The catalog needs a real sign-in; session setup through
  the packed agent cannot pass model selection without one (same
  wall the RESTARTMODEL lane hit).
- Packed product (`drill-acp.mjs`, packed `dist/acp.js` 0.18.2,
  uniquely named binary copy so the kill could hit nothing else):
  `initialize` ok → `session/new` refused (`no model this agent may
use`, expected — see above) with the host UP → SIGKILL the serve
  → `session/new` again → RESPAWNED, and the log shows the new
  warn line: `The previous run Muse Code was stopped by SIGKILL;
the replacement starts with the CLI's own credentials, as logged
above`. The drill's start line reads `credential file
unrecognized` because the rig is macOS (by design, see below).
  No prompt was ever sent.

## Findings and fixes (commit SHAs below)

F1. A restarted `muse serve` gets EXACTLY the first one's
environment, home and file path — there is no restart-only env
difference in our code (VS Code manager or ACP runtime). The
credentials the restart lost were lost CLI-side (its file/refresh
state), not by our spawn. Fix: the replacement host now carries
why the previous run went away on its own
(`AgentHost.takeRestartCause`, read once; recorded by
`MuseCodeBackendManager` from unexpected exits, cleared by a
requested stop and by the restart that carries it), and the
manager warns at respawn. A turn that runs to completion clears
the cause, so a later natural expiry never blames an old crash.

F2. Our reader called 1.4.7's file "unrecognized" because newer
CLIs write shapes the 1.4.0-era reader does not know (a `storage`
lane, as in the third-party macOS pointer and my `storageFull`
probe which 1.4.10 accepts as `accountLogin`; or a key set
without `api_key`). Separately, the reader OVER-claimed: an
`access_token` without `api_key` read `inline`, but 1.4.10 exits
3 on it. Fix (`credentialFile.ts`): `inline` now needs no
`storage` lane AND an `api_key` — exactly the shapes measured to
start on 1.4.10. Everything else stays `unrecognized`: the CLI is
asked (win/linux probe; macOS passive estimate), so a working
sign-in still works, one probe slower at most. On macOS even a
perfect file reads `unrecognized` — pre-existing design (never
captured there), unchanged.

F3. The `-32603` event-log failure under several concurrent jobs
did NOT reproduce on 1.4.10 (concurrent echo turns; SIGKILL
mid-turn + resume + second turn — all clean). It is a CLI-side
session-store fault (`museHome` is per-user, shared by every job
of the machine; `storeFaults` is CLI vocabulary). Not fixed in
the CLI (not ours to fix); our side already refuses damaged
sessions in the panel, and now says the sign-in loss loudly
(F4). Full concurrency proof needs the lead's multi-job run.

F4. Never silent. ACP mapped an `authRequired` turn to a generic
`internalError` — just another failed turn. Now
(`src/acp/signInLoss.ts` + `settle`): with a restart cause behind
it, the prompt answers `authRequired` with
`museSignInLostOnRestart` (the cause, the turn's reason, the
remedy: `muse login` or `META_API_KEY`), and the log warns the
same line. The panel (`conversationController.ts`) puts the same
loud text in the sign-in detail `markAuthRequired` publishes.
Without a restart behind it, today's paths are byte-identical.

F5. An exit-3 over credentials logged as a bare line length.
`stderrForLog` now names the CLI's captured words (`the
credential file is malformed (…)`), never the path.
