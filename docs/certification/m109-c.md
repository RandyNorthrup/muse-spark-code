## Format and integration bindings

The project-owned v1 format uses AES-256-GCM, fresh 96-bit nonces,
HKDF-SHA256 separated by vault, item, kind and format, and authenticated
generation numbers. Names, labels, policies and bindings live in the
encrypted index. Private material is encoded as raw length-prefixed bytes
beside a JSON descriptor; secret bytes never become base64 plaintext strings.
Slot wrapping authenticates stable slot identity and KDF parameters. Mutable
generation/audit fields are authenticated by the slot document under the
vault key.

The default Node file adapter verifies POSIX owner/mode (directory 0700,
files 0600), rejects symlinks, compares opened-file identity, bounds reads,
and uses synced exclusive staging plus rename-over-existing. A cross-process
`writer.lock` is created exclusively. Stale locks require explicit recovery;
there is no timeout that can steal a live writer's lock.

Publication prepares an authenticated ciphertext-only `pending.v1`, then
advances the independent generation anchor, publishes `slots.v1` and
`vault.v1`, and removes the pending record. Opening recovers a fully
authenticated pending transaction at the anchor's generation or its immediate
successor, including every item, before exposing the store. Failed publication
locks and erases the current store key. Invalid, stale, skipped-generation or
inconsistent-audit pending records fail closed without replacing the files.
No operation observes a partially published pair through this port. A failed
write may finish during recovery, so callers must not interpret its exception
as proof of an aborted transaction.

Restoring both data files to an older generation fails against the anchor;
the audit generation and head must also match on open. Restoring all rollback
state together is the D89 V11 residual unless the anchor is independently
protected. Backup restore authenticates the index and every item, checks the
current destination and anchor before preparing any record, and publishes a
fresh generation. Older backups cannot silently roll back an existing device.

Argon2id uses RFC 9106's second option (64 MiB, t=3, p=4), feature-detected
at runtime. Scrypt uses N=2^17, r=8, p=1. Both use a fresh 128-bit salt and
a 256-bit result. Recovery codes contain 160 random bits, returned as an
owned Buffer for the setup surface to display once and erase. The passphrase
supplier is invoked for every wrap/unwrap; transferred input is erased. An
unavailable stored Argon2 slot is refused rather than downgraded. Backup slots
are portable passphrase/recovery slots; backups never export a plaintext key.
Backups are chunked authenticated ciphertext, binding their portable slot,
generation, payload length, chunk count and position as additional data.

### Required integration bindings (P/B/M/W)

- P/B bind `VaultGenerationPort.minimum/advance` to durable monotonic state
  outside the replaceable data files. `advance` must reject regression of
  generation or audit state and inconsistent equal-generation values. The
  test implementation is confined to `test/**`; there is no production stub.
- P supplies `VaultFileSecurityPort.protect/verify` for owner-only Windows
  DACLs. `NodeVaultFiles` refuses Windows construction without this port.
  Other native file adapters can implement `VaultFilePort` for native lock,
  identity and durability requirements. `maxBytes` is a required injected
  limit, including the full prepared record, not an unbounded default.
- B owns the unlocked store lifecycle, fresh per-use presence, and durable
  anchor/audit binding. `setSlots`, `commitAudit`, `exportSnapshot` and the
  static create/open/restore/slot-hint methods supplement lane 0's
  `VaultStorePort`. Unlock hints are explicitly unauthenticated until a key
  opens the store. `lock` zeros the owned root key; B erases returned material.
- M retains its old secret mirror until a prepared migration is durably
  resolved. A write exception can leave a recoverable prepared transaction.
- W's backup/setup surface wraps the same root key into the supplied portable
  slot before `createEncryptedBackup`; the function proves the encryption key
  belongs to the store, but cannot prove a slot's wrapping key without its
  passphrase/recovery input. W displays/erases the owned recovery-code buffer
  and supplies the backup byte limit. W owns the lazy bundles, integration
  docs, PLAN/CHANGELOG and featureCatalog/reference entries. No new command,
  setting, surface or network call is introduced in this lane.

## Memory limits

Owned secret Buffers and derivation/plaintext scratch are unpooled and erased
on completion, failure and lock. Callers retain ownership of input bytes and
must erase returned material after use. Node/OpenSSL internals, immutable JSON
metadata strings, copies made by other code, swap and debugger reads cannot
be zeroized or prevented here; Node provides no mlock/MADV_DONTDUMP promise.
