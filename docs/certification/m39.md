# M39 certification — logging and performance you can see (PLAN.md M39)

Recorded 2026-09-24.

The owner asked, on 2026-09-24: "as far as o11y for errors etc we are good?
… really i mean logging and performance everywhere". A read-only audit of
the code that day found:

- The CLI process layer was well logged, with every line redacted.
- The conversation layer showed failures in the panel but did not log them.
- Webview errors never reached the host.
- Nothing measured time at runtime.
- Two resources were unbounded.

## Logging

- **Nothing fails unseen.**
  - `ConversationController.handle` catches, logs the message type with
    the stack, and says so in the panel.
  - Every command runs through `registerLoggedCommand`, which logs a
    failure and shows it once.
  - Each fire-and-forget call has `logRejection`: session restore, sandbox
    offers, skill refresh, Bypass revocation and backend restarts.
- **What the user was told is in the log.** A warning or an error
  `notice()` writes the same line. So do the worktree and skills popups,
  through `loggedPopups`.
- **Webview errors reach the host** (`webviewError`, capped in the zod
  schema). The sources are:
  - the error boundary;
  - `window` `error` and `unhandledrejection`;
  - a reducer that throws on a host message, which used to lose the message
    silently outside React's boundary;
  - a malformed host message.

  An image that cannot be read now says so in the banner, and its error
  reaches the log. The host logs at most 10 errors a minute per panel, then
  says once that it stopped.

- **The session's story, with ids:**
  - sign-in state changes and the backend they chose;
  - the backend conversations run on, when it changes;
  - each session started, resumed, forked or continued after a restart;
  - each turn's start, then its end with the result, duration and time to
    first output;
  - approvals, asked for (the tool) and answered (the choice, never the
    feedback);
  - a restart and its reason;
  - a retried MSP command.
- **Less noise:**
  - an invalid setting warns once per value, per logger;
  - an ignored Model API stream event type is logged once, not once per
    frame.
- **No content in the log:**
  - an unparsed dictation-helper line is logged by its length;
  - the skills CLI's stderr is clipped (`clipForLog`, shared with
    `muse serve`'s);
  - a malformed stream frame is named by its length, not a preview of
    model output.
- **Swallows that hid a cause:**
  - `readTextFile` treats only "not found" as absent, so a rewind blocked
    by permissions says why;
  - the CLI lookup names a path it could not read;
  - the git facts say why they are missing.
- **Trace level:** each MSP command's time, and each Model API request's.

## Performance

- **Measured:**
  - activation time;
  - `muse serve` spawn to handshake;
  - turn duration and time to first output, on both backends;
  - the git facts, now three calls in parallel instead of in sequence.
- **Bounded:**
  - A reply stream that sends nothing for 5 minutes, headers or frames,
    ends with a clear reason, and its request is aborted.
  - The file tools refuse a file over 10 MiB before loading it.
  - Open output documents are held to 20, and to 32 million characters
    together.
- **Webview:**
  - Streamed text is posted at most once every 16 ms. Consecutive deltas of
    one item join, and any other message posts them first, so the order
    holds.
  - The once-a-second state save waits while a reply streams.
- **Smaller:**
  - The editor selection is read once it settles, and at send time, not on
    every arrow key.
  - Previews are clipped at 2,000 characters as well as 12 lines.
  - The IDE tool server starts when a session first needs it.

## The review of pull request #20

The Codex review found two gaps; both were fixed on the branch.

| Finding                                                                                                                                                                                                                         | Fix                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P2: the reply stream's frames came from a manually driven iterator, which an early end (a malformed frame, the caller stopping) no longer closed, as `for await` had. The parser stayed suspended with the response body locked | The loop runs in `try`/`finally`, and the `finally` closes the parser. That releases the body. It is not awaited, because after a stall the last read may never settle |
| P2: a turn ended in the extension (a restart, a crash, the session closing) sent its own `turnCompleted` without the turn clock's bookkeeping, so it got no end line and its clock stayed for the controller's life             | That end goes through the same `endTurnClock` as one the host ended. When the session drops, any clock left is logged as "ended with its session" and cleared          |
