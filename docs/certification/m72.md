### Lane MEM: memory writes keep checkpoint copies (`cfe57534`, `80b768f4`)

**Defects.** Activation built Muse Code's memory over the raw tool I/O while
the guarded fixture composed a checkpointed one:

- a replacement of an ignored project note or of its `MEMORY.md` took no
  checkpoint copy;
- an exclusive creation, which has no ToolIo call, took none either;
- the Memory view's creation and trash held no restore lease, so they could
  overlap another window's restore;
- a conversation export the user places inside the workspace was written with
  a raw `vscode.workspace.fs.writeFile` (found by the sibling sweep);
- `MemoryStore.create` shadowed `isTaken(error)` (a compile defect), and four
  controller expectations predated the required `checkpointState` row.

**Fix.**

- `createCheckpointedMemory` (`src/host/backend/checkpointedMemory.ts`) is the
  one place activation builds the store, and the regression tests build it
  too. Replacements go through `withCheckpointCopies` with the original guard;
  an exclusive creation awaits the same `beforeToolWrite` copy (new
  `beforeCreate` option of `createMemoryIo`), then publishes no-clobber with
  the guard.
- The view's creation, trash and index line run under the pure edit lease
  (new `withCheckpointEditAt`) until their native promises settle. One guard
  (`backend.workspaceActionGuard`) is captured when the action starts and
  handed through `Store.create` and `Store.forget` to the atomic publication
  callbacks. A note is copied before the trash, and the guard speaks last,
  right before `vscode.fs.delete`, which has no callback seam.
- A scope takes the lease by its folder, not its name: only notes under the
  workspace folder do. A personal scope outside the workspace takes no project
  lease (tested both ways, including a personal scope below the workspace).
  There is still no trust gate, so the view works in Restricted Mode (tested).
- A published note stays when the index guard refuses, and a trashed note
  stays trashed (the existing partial-success rule, tested).
- A conversation export saved inside the workspace goes through the new
  `CliFeatureDeps.editFile`, which holds the same lease.
- The compile defect (`isPresent` replaces the shadowing local), the stale
  import and two redundant types are gone. The controller and App fixtures keep
  their complete strict order and add the real `checkpointState` row and its
  `legacyTurnIds`; nothing is filtered or weakened.
- `80b768f4` (verifier finding): the activation wiring test now pins the exact
  guard expressions (see the verifier table).

### Lane SHELL: the user's `!` command and a shell that never started (`e593ebe4`, `1fd98aaf`)

**Defects.**

- The user's own `!` command (`ModelApiSession.runUserShellCommand`, M46)
  passed no sixth `runShell` argument. After its initial Restricted Mode check,
  the checkpoint activity mark and the native adapter's awaited Windows
  assembly could end with nothing asking the current trust, the session or the
  Host's closing state at the command's real entry.
- A shell that could not start at all (no interpreter on `PATH`, a missing
  PowerShell, a spawn that failed with no pid, the hook shell) reached the
  checkpoint wrapper as a possible process, which left a false sticky native
  uncertainty and kept Restore and Redo closed.
- Several fake shell fixtures ignored the final callback.

**Fix.**

- `e593ebe4`: the `!` command passes its own final admission: the user's own
  stop, session disposal, the Host closing and the current trust. It is not the
  model's rule: the running turn, its Stop and the permission mode (Plan
  included) do not decide an explicit `!`, and a started command keeps its
  outcome. A refused entry ran nothing: its row reads "The command did not
  run" and the model is told nothing.
- `unstartedShell()` (`src/core/shellResult.ts`) carries
  `isWorkspaceShutdownProven` only for a known zero-launch result: no
  interpreter on `PATH`, the hook shell, and a spawn that failed while
  `child.pid` is still undefined. The failure itself is unchanged. A launched
  command, an error after launch and a normal exit never carry the proof.
- The memory, held and do-nothing fixtures, and the ad hoc `runShell` fakes of
  three checkpoint suites, ask the final admission at their entry
  (`refusedAtEntry`, `enteringShell` in `test/unit/helpers/fakeToolIo.ts`).
- `1fd98aaf` (two verifier findings): `spawn()` can throw inside the
  executor of `runCommand` (a command line past the operating system's limit,
  a NUL in the command); the spawn is guarded (`startProcess`) and the failure
  returns as an unstarted shell. A failure before entry (the checkpoint
  activity mark cannot be made) is now a `ShellEntryError`, which the user
  shell path refuses like any no-entry outcome; a failure after the command ran
  stays a plain `Error` and is still told to the model.

### Lane NATIVE: git's path limits in the checkpoint store (`62c856d8`)

**Defect.** Measured with Git 2.52.0.windows.1: `core.longpaths` is read only
after git has opened the repository, so the repository's own path must fit
PATH_MAX as written. The store's `git init` also ran without the scoped
option. Eleven tests in three suites failed under a 124-character TEMP: ten
whose independent git reads lacked the scoped option, and the Location test.
The frozen `90ff` host run had failed its one hashed-namespace capture at 242
characters (storage 185, repository 195, the old initializer folder 242).

**Correction to the previous diagnosis.** The earlier owner's diagnosis of the
ten fixture failures was right. It was only partly right about the eleventh:
adding `-c core.longpaths=true` to the old `git init` alone fixes the frozen
Location test (proved with the old code plus only that flag), but the real
limits were wider than the owner measured, and the option alone does not fix
paths over 258, repositories of 221 to 251 (which need the relative spelling)
or over 251 (unusable by any spelling).

**Measured limits** (Windows 11, Node 24.20, Git 2.52.0.windows.1; scripts,
outputs and SHA-256 prefixes in `scratchpad/evidence`, summary
`native-captures-summary.json`; exp1 `c9f601fc...` / `13d565db...`, exp2
`639996fe...` / `2b9339e6...`, exp3 `0ded855d...` / `ef8449b3...`, exp4
`a84668e2...` / `f4c1da28...`, exp5 `73ff598f...` / `2330f6a8...`):

| What                                                  | Result                                                                                                                                                             |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Absolute `GIT_DIR`                                    | 220 characters ok; 221 fails (`'$GIT_DIR' too big`, PATH_MAX - 40)                                                                                                 |
| Relative `GIT_DIR`                                    | Works while `<git dir>/objects` fits: repository 251 ok; 252 fails (`not a git repository` or `unable to access .../config: Filename too long`); 253 and more fail |
| `git init` with the scoped option, a name git creates | 258 ok; 259 fails (`cannot chdir`)                                                                                                                                 |
| `git init` without the option                         | Fails from 235; `cannot mkdir` from 248                                                                                                                            |
| Work tree                                             | 258 ok; 259 fails (`must be run in a work tree`)                                                                                                                   |
| A short junction to a 256-character canonical target  | Works: git sees only the string it is given                                                                                                                        |

No other spelling reaches further: relative path, another working directory, a
gitfile, the scoped option and a junction all fail past these.

**Fix.**

- `ShadowGit` makes the repository in a short unique folder in the storage
  folder itself (`.i-` plus 12 hex digits of the sha256 of the window's
  instance), with the scoped `core.longpaths`, and publishes it by one Node
  rename (the same folder, so the same volume, through links and junctions and
  with storage on C: and the workspace on D:). A `finally` removes the folder
  whether init failed, was cancelled or lost the publication race; a folder a
  dead window left is swept once older than `CHECKPOINT_STALE_LOCK_MS`.
- `run()` keeps the absolute `GIT_DIR` and the work tree as the working
  directory while the repository path is PATH_MAX - 40 or shorter. Beyond that
  it names `shadow.git` relative, with the storage folder as the working
  directory; `GIT_WORK_TREE` and `GIT_INDEX_FILE` stay absolute, and
  `hash-object`'s file argument is named in full (a sibling defect the
  equivalence drill found).
- A repository over PATH_MAX - 9 or a work tree over PATH_MAX - 2 is refused
  before any file or git, as the capture refusal `pathTooLong`, with the text
  `checkpointPathTooLong` in all 14 translated tables (machine-made). It shows
  as "No file checkpoint for this turn: ..." and as the restore-failure
  reason. PATH_MAX is the platform's (260 on Windows, 1024 on macOS, 4096
  elsewhere) unless a test lowers it through the optional `gitPathMax` dep.
- The shared test helper `shadowGit()` scopes `core.longpaths` for every
  independent shadow read in the suites. The legacy reader runs the same
  checks. No store made by an earlier build is affected (storage of 177
  characters or less), and the hashed namespace is unchanged.

**Tests.** `checkpointLongPaths.test.ts`, new: 24 passed at the normal TEMP on
Windows with a second volume (D:): capture, record, end, restore and redo
(an ignored-file preimage included) at three edges (longest absolute
repository path, shortest that must be relative, longest git opens) with the
platform's own limits (Windows only) and with a lowered limit (any platform);
the refusals; init failure after the repository was made, a real window close
mid-init, an unpublishable repository, two windows initializing at once and a
stale initializer; a short link to a too-long folder, a workspace on another
volume, a storage link to another volume, the legacy reader and the helper
reading refs past 260 characters. Also `checkpointStoreBundle.test.ts` (the
built CommonJS factory captures in the relative spelling and refuses a
too-long path; 7 passed) and `conversationCheckpoints.test.ts` (`pathTooLong`
said once per reason and named in a restore failure; 15 passed).

- The three originally failing suites under a 124-character TEMP: 11 failed, 43
  passed, 2 skipped before; 54 passed, 2 skipped after. Old production plus the

### Known limits

- Hooks have no final admission, by design: SessionEnd hooks run while the Host
  closes, and hook settings are user-global and not workspace-trust gated. Stop
  is honoured through the signal, and the wrapper's activity mark still fences
  Restore. A hook-specific admission would be a separate design decision.
- The Muse Code `!` (MSP `session/userShell`) runs in the CLI's own process, so
  the extension has no `ToolIo` entry to admit at: its guards are the
  controller's Restricted Mode check and the native startup fence and unsafe
  marker.
- A throw from `assertWorkspaceCurrent` stays unproven and conservative (the
  wrapper treats a throw from its work as a possible process). Only the ACP
  runtime composes it, and the ACP runtime has no checkpoint wrapper, so no false
  sticky state is reachable today.
- `git worktree add` and the workspace-cwd metadata runners (and
  `globalExcludesFile`) still cannot use a workspace over 258 characters: they
  pass it to git as a directory. In the checkpoint flow the work-tree fit check
  now runs before the first of them.
- Window presence files (`storage/windows`) are written before the path check,
  so a refused, too-long storage still gets that (small, Node-written) folder.
- The 14 translations of `checkpointPathTooLong` are machine-made (the
  repository's convention) and unreviewed by a native speaker.
- A storage folder over 240 characters, or a workspace over 258, is unusable by
  any spelling of the path; the store refuses it with a clear message instead
  of moving the repository (which would change the hashed namespace). Real users
  meet the path refusal only with a global storage path of about 180 characters
  or more.
- The git limits were measured only on Git 2.52.0.windows.1. A newer git may
  accept more paths; the store would then only be conservative.
- The lanes used only the Windows host: the Mac mini, the Windows VM (Git 2.55)
  and Kubuntu were not used. Nothing ran on Linux or macOS; the lowered-limit
  tests drive the relative spelling and the short initializer with real git on
  any platform, but only ran on Windows. The platform-limit tests are
  Windows-only by design, and the cross-volume tests skip with a named reason
  when no second writable volume exists (macOS will skip).
- No activation-level proof inside real VS Code for the memory wiring:
  `src/extension.ts` has no unit run, and the wiring test holds its source
  shape. The lead's integration and platform gates still need to run it.
- `test/unit/checkpointModelApiStop.test.ts` still builds its memory fixture by
  hand (`createMemoryIo` over the checkpointed I/O, without `beforeCreate`); it
  stays as the verified owner-repair proof, and `checkpointMemory.test.ts`
  covers the real composition.
- Explicit user edits that hold the lease but keep no preimage copy, by the
  existing design: the review revert write and delete and Create AGENTS.md. The
  ACP runtime's memory I/O (`src/runtime/backends.ts`) is an independent process
  outside the VS Code checkpoint guarantee (PLAN D51). The diagnostics command
  `muse config status` runs as a process with the workspace as its directory,
  without the workspace command start; it is a process, not a file write.
- `checkpointLongPaths.test.ts` adds about 90 to 135 seconds on the Windows host
  (real git, no file parallelism there).

### The Theia check's refused first message: cause found and fixed (2026-10-01)

The hosted Eclipse Theia check failed again on `a5a4b1ac` with the refusal recorded as intermittent in the first
round ("this window could not tell other windows on this folder that a turn is starting"). The cause had to be
found before the release. A diagnostic branch (deleted afterwards) captured the extension's own log from the
page and traced every git call, and ran the Theia job 20 times: 7 failed.

- **Cause: a race in the checkpoint store, on every host.** A window's first message starts both a read of the
  conversation's checkpoints (through the store's queue) and the running mark (`markTurn` → `open()`, which skips
  the queue by design). `open()` cached only a finished setup, so on a fresh storage folder both ran their own:
  two `git init --bare` in this window's one initializer folder, and the first to finish moved the folder to
  `shadow.git` while the second was still writing. When the second was the mark's, the message was refused.
  Theia shows it most because its session start, read and mark land within about 70 ms. The log of a failing
  run: `A running turn was not published: GitExitError`; the trace: two `git init` on `.i-<id>`, the second
  `could not lock config file … No such file or directory`.
- **Fix (`18f3c5ad`).** `open()` keeps the setup's promise and every caller shares it; a setup that fails is
  forgotten before any caller hears of it, so the next one tries again. Refusing to send when a mark truly fails
  is unchanged.
- **Proof.** `checkpointStoreGuards.test.ts`, "sets the repository up once when a running mark meets the first
  read" (a real store, both calls together, `git init` exactly once); it fails on `a5a4b1ac` with the same
  `GitExitError`. Drill: a fresh setup per caller back (`=` for `??=`) fails it; restored to `049bb2ce…`. With the
  fix, the Theia job passed 20 of 20 repeated runs (run 36894882359); without it 7 of 20 failed (run 36892812826).

## The mechanism (D51)

A bare shadow repository under the extension profile's global storage
(`checkpoints/<canonical-root-key>/shadow.git`) whose work tree is the workspace, or
the repository top when the workspace is a folder of one (so its
`.gitignore` files apply; every path is kept to the workspace's prefix).

- **Isolation.** The host's `GIT_*` variables are removed; the system config
  is off, the global config is an empty file, `HOME` is a folder in storage,
  system attributes are off, optional locks are off, `core.hooksPath` is an
  empty folder, fsmonitor and the untracked cache are off. The shadow's
  `info/attributes` unsets `text`, `eol`, `filter`, `ident` and
  `working-tree-encoding` for every path, so bytes are copied as they are.
  The workspace's `info/exclude` and the user's global excludes file are
  read as ignore patterns only. git is found by absolute path (D24).
- **No alternates.** The shadow keeps its own objects; nothing is written or
  freshened in `.git`, and the user's `gc` cannot break a checkpoint.
- **Captures.** `git status --porcelain=v1 -z --ignored=matching
--untracked-files=all` over an index that does not exist lists every file
  outside the ignore rules, the nested repositories and the ignored files
  and folders. A private index (stat cache) is brought up to date with
  `update-index`, and `write-tree` gives the capture. Each window has its
  own index. Each record's JSON, trees and copies share one `mktree` tree
  under `refs/muse-spark/record/<id>`, parsed with zod and updated by CAS.
  A restore reserves a shared CAS ref that also keeps its source trees
  alive while file work runs.
- **Ignored files.** A bounded stat scan at each turn's start and end, and a
  copy before each write of the Model API's tools and the image tools
  (`withCheckpointCopies`).
- **Restore** (`planRestore`, pure): the chosen turn's start capture against
  a capture now, less every path changed between the conversation's turns
  or after the last; ignored files by the turns' recorded changes with a
  stat continuity check. Writes are atomic and confined by canonical path;
  deletions touch regular files only. **Redo** records what was replaced and
  what was left, and puts back only files still as the restore left them.

Probe before building (`scratchpad/probe-shadow.sh`, git 2.52.0.windows.1,
no model calls): in a repository with `core.autocrlf=true` and
`* text=auto` plus `*.bin filter=lfs`, the shadow listed the files and
ignored entries as expected, kept a CRLF file's bytes, answered
`cat-file --batch` in the documented format, and left the repository's
object count (9) and refs (1) unchanged.

## PR #55: the Codex review

  archived-conversation queue (`forgotten.json`) is gone: archiving in

  set, never cached), the refs, the shadow's `info/` files (written at

## The Grok review of `4c43fb11`: one policy for the lock

- **What never waits.** A turn, and a message about to start one, is
  published as running in the window's presence file (replaced whole, no

- **What is told.** A capture, a record, a restore and a redo refused by
  the lock say so in the panel. A turn is open here only once its record is

- **What waits, in memory at once.** A turn's end, an archive, letting go

  recorded with its end time and no end capture, so its changes are named

## The Grok review of `2fa6c1ae`

Grok reviewed `2fa6c1ae` (the lock policy): 3 P1, 6 P2, all fixed in the
next commit; the policy stands and these close its gaps.

- **P1, a mark that could not be written.** `beforeTurn` logged and sent
  the message anyway. Now a message whose running mark cannot be written is
  not sent (the send fails with the reason), and its mark is dropped.
- **P1, tool copies before the record.** A tool's copy was taken only for a
  turn whose record was saved. Now it is taken whenever a turn or its
  message is published as running, and kept until that mark ends (then
  trimmed).
- **P1, a presence file removed.** The heartbeat only refreshed the file's
  time, so a presence removed by a window that thought this one gone stayed
  gone. Now every heartbeat writes the presence file again from memory, so
  a removed file or a failed write (an end that was not unpublished)
  heals within one beat.
- **P2, letting go of the lock.** It read the lock, then deleted it, so a
  lock taken over in between could be deleted. Now the lock is moved aside
  under a unique name and the moved file is checked; another window's is
  put back. An own leftover lock taken back gets a fresh time.
- **P2, a takeover's moved lock.** A fixed name for the moved lock could
  collide with a leftover; each move now has a unique name, and a lock in
  use is tried again later instead of failing the operation.
- **P2, records work at window open.** `maintain` returned before doing a
  Restricted Mode archive the lock had refused when no shadow repository
  existed yet; it now writes it.
- **P2, a silent retry.** A retry that failed before the put-off work ran
  logged nothing; it now logs, then tries again.
- **P2, wording.** README and CHANGELOG said a restore waits while a turn
  runs; it is refused until the turn ends, and they now say so.
