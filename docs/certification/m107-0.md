## Contracts and ownership

`src/shared/resources.ts` defines strict zod/mini contracts and inferred
types for samples, settings, levels, kinds, classes, local tickets/process
identity, tree usage, events, status, device headroom, resource journal
records and the new exec resource event. It has no OS/editor imports and
starts no sampler. Production sampling, process registry, actuation,
governor, queue, routing and UI remain their lanes' work.

The machine settings reader uses inspected `globalValue`, then
`defaultValue`, never workspace/folder values. Explicit false and optional
null are retained; invalid machine values fail validation. The memory floor
is the lesser of the requested GiB and 15% of total RAM. Each unknown reading
is null independently; a real zero remains zero. The contracts do not claim
that parsing a sample implements the unknown-reading state-machine rule.

Private tickets have process ids/start identities and local scope handles.
Status, headroom, events, records and exec resource events carry none of
those fields. Strict nested schemas reject privacy canaries instead of
silently stripping them. Records require exactly one minute or event, and
hold only numerical work totals by kind. Device resource status is exactly
`{level, headroom}`; it supplies no offer/permission authority.

The injected seams are `ResourceSampler`, `ResourceClock`,
`ResourceTreeReader`, `ResourceLinkedDevice` and `ResourceSettingsReader`.
Their implementations here exist only under `test/unit/helpers/resources`.
The sampler refuses exhaustion, the clock supports deterministic ordering
and cancellation, the tree can recycle child or root ids, and the device
can revoke an offer or change level between selection and admission.

Contract choices where D87 names no value: optional GPU/disk thresholds
range 1–100%; opaque local ids are bounded to 256 characters; the Windows
job CPU rate target is 50%. The last is a proposed actuator tunable, not a
certified platform capability or a cap applied here. Tree CPU accounting
uses cumulative CPU-seconds and aggregate current resident bytes; history
holds peak bytes, calculated by lane J.

## Integration boundaries

This base has no `src/shared/devices.ts`, `usageJournal.ts` or `hostApi/**`.
Lane 0 defines only its resource portions in the named central contract:
M100 composes `deviceResourceSchema` as the offer's `resource` field;
M102 composes `resourceRecordSchema` into its journal; M104 carries
`resourceStatusSchema` through its existing status-item bridge. No absent
parent wire protocol is guessed.

H owns `execProtocol.ts` and its live writer; W owns the schema generator
and manifest contributions. The resource event is explicitly envelope v2,
with the existing result payload staying v1. Adoption and generation of
the complete v2 union remain H/W's integration steps; lane 0 does not alter
v1 or falsely label the running CLI as v2.

Settings/command manifest contributions require W's `package.json` region.
The unused-NLS gate requires every manifest string to have a contribution,
so unattached keys cannot be added to `package.nls*.json` while preserving
the zero-problem requirement. The lane does not cross that ownership
boundary. README/CHANGELOG/PLAN, the English fallback region/split wiring,
and the shared validation entry also belong to W. W must expose zod/mini's
`_default` when this contract first ships, and wire the new English strings
into a lazy region. No gate/ignore is weakened here.

The new exports are staged dependency contracts, exercised by tests rather
than production consumers. W must join the dependent lanes, verify every
production reference and delete unused contracts; no Knip ignore is added.
