### Self-review repairs (same day, before the lead's reviews)

One pass by class (security, failure paths, lifecycle) after `66fe14d4d`:

- **Recovery code reaches a person.** `vault setup` and `vault recover`
  require a terminal on standard input and standard output. A redirected
  stdout would have written the recovery code into a file.
- **Recovered key on a failed unlock.** If the broker refuses the unlock, the
  recovered key is erased instead of waiting for the next unlock. A
  regression in `vaultManagement` covers it.
- **Watch retries.** A `watch` stream the broker keeps closing is reopened at
  `VAULT_WATCH_RETRY_MS`, never in a tight loop.
- **CLI and ACP status.** `vault status` and `/vault status` read the
  management view, so they report `uncreated` and `setupPending`; the
  broker alone reports neither.
- **Residual for lane (b).** When the OS store wraps the key but the vault
  write then fails, setup stays pending, and each retry wraps again under a
  new slot id. Lane (b)'s OS-store slot removes an unused entry, or names
  the leftover.

### Import and Reset Vault (lead decisions, 2026-10-10)

The lead decided two open points; both are built on `c/m109-1`, with
regressions in `test/unit/vault/importReset.test.ts` and drills in
[`m109-import-reset-drills.json`](m109-import-reset-drills.json).

**The encrypted batch writer and import, end to end.**

- `VaultStore.writeBatch` checks every item is new by id and name, seals
  them at one generation and stages them with an encrypted receipt.
- The importer's decrypt-and-verify reads the staged items back. Only then
  does one `publish` commit them, with the caller's authority checked at the
  physical commit: all items or none.
- A clean refusal at the commit (a cancelled requester, a retired grant)
  writes nothing and no longer locks the vault for everyone. Other failures
  still lock.
- Receipts (`readReceipt`, `forgetReceipt`) live in the encrypted index.
- `VaultManagement.importFile` accepts only a file the ambient discovery
  listed in the home folder. It decodes with the existing parsers
  (`prepareImport.ts`). Imported items are hidden from agents until the
  person reviews them, since a parser's targets are private review hints.
- The report carries names and kinds only; then the person chooses Keep or
  Delete (the importer's verified source deletion). A requester whose
  connection closed has cancelled, and the commit check refuses it.
- Protocol: `import` answers `imported` (receipt plus metadata); there are
  new `importKeep` and `importDelete` kinds.
- Surfaces:
  - CLI `vault import <path>` prints the names and asks Keep or Delete.
  - The panel's Import shows the same native question.
  - The ACP agent runs the same terminal command.

**Reset Vault.**

- It is offered only when this user's anchor names a vault whose slot
  records are missing or unreadable (`VaultStore.isLost`); a busy writer or
  an I/O error is never a loss. The status shows `unavailable` with reason
  `vaultLost`, and the Vault section shows **Reset Vault**.
- `resetBegin` returns a challenge and the fixed word `RESET`.
  `resetConfirm` needs that challenge (which one wrong word spends) and the
  exact word.
- `VaultStore.resetLost` re-checks, under the writer lock, that no slot or
  intent opens the vault. It appends a value-free line (`vaultReset`, time,
  previous vault id) to `reset.v1`, keeps the displaced document aside
  (quarantine) and removes the files.
- The anchor is then cleared by compare-and-delete. Rollback protection
  restarts with the next setup's new anchor, and the old vault's files never
  open again.
- Surfaces:
  - The panel asks in two native steps: the statement with Continue, then the
    typed word.
  - CLI `vault reset` asks Continue, then the hidden typed word, and refuses
    without a terminal.
  - The ACP agent runs the same terminal command.
- All new strings are in the 14 tables. The CLI reference now lists `reset`.

### RVCM1091A2 (Grok review, 2026-10-10)

Regressions are in `test/unit/vault/rvcm1091a2.test.ts`; drills are in
[`m109-rvcm1091a2-drills.json`](m109-rvcm1091a2-drills.json) (kubuntu).

**P2: a Lock during I Saved It still created and unlocked the vault.** The
class is any pending operation that finishes into an unlocked state after a
Lock. `VaultManagement` now keeps a lock generation that every Lock raises
(`noteLocked`), and management checks it across confirm, recover, reset and
import (`assertSameLock`):

- **Confirm:** checked after the OS-store wrap, so nothing is created and
  the key is erased. Checked again after the write, before `broker.unlock`,
  so the vault stays locked.
- **Setup:** checked before a pending setup is kept.
- **Recover:** checked after the status read and after the slot records, so
  no recovery key is offered.
- **Reset:** a Lock withdraws the challenge. Management re-checks before
  issuing the challenge and clearing the anchor; the audit publication
  checks the generation at its physical commit (CM1091A3).
- **Import and source deletion:** the commit-time check refuses a commit a
  Lock overtook, so nothing is written.

**P3: a headless open ignored cancellation after connecting.**
`openHeadlessVault` now closes the connection as soon as the signal aborts,
and re-checks the signal after registration. A run cancelled meanwhile gets
no session.
