### Registry/storage corrections (findings 2, 3, 4 and 6)

- **2:** Each in-flight deferral records its request IDs. A re-ask dispatches
  fresh IDs at its own deadline before waiting for preceding acknowledgements;
  each batch clears only its own registration. An older pending command cannot
  consume the new timer or resend IDs already covered by an earlier batch.
- **3:** Publication derives the retained snapshot first and invokes exactly
  one atomic store save (the existing write-temp/sync/rename adapter). Terminal
  deletion is the durable answer mark; there is no fallible cleanup save before
  delivery. If notification throws after a successful save, the serialized
  operation restores the durable snapshot and republishes its restored state.
- **4:** Coalesced live requests run through `Promise.allSettled`; each has
  its own result, and each uncertain failure invokes the existing failure port.
  A successful or already-settled request never inherits another request's
  uncertainty. The aggregate result is uncertain if any attempt is uncertain.
  A presentation-only reservation retains the waiting card until every reply
  finishes; the raw registry and disk already hold the same durable deletion
  mark. The regression checks those durable snapshots, holds the second reply,
  and injects an early first-request settlement. Card retirement needs no
  second disk write and cannot prevent a remaining request's dispatch.
- **6:** Removal sweeps all `<session>.json.*.tmp` names in the private store
  directory, including leftovers when the committed file is already absent.
  Similar session prefixes, unrelated files and symlink targets are preserved.

## Portable registry and private storage

The holding process owns arrival-time deadlines and one serialized registry
per session. Settings are machine-only, 60 seconds by default, 0 disables
interactive deferral, 1–9 clamps to 10, and scheduled callers may request
immediate deferral. Waiting reloads as open; only explicit Stop cancels.
Matching question keys coalesce live requests and re-asks, keeping original
card IDs/text while rebinding the answer to fresh request IDs and labels.
Open questions are capped at 20. Reminders are oldest first, once per turn,
limited to two per question and suppressed while an approval waits.

Marks are saved before delivery; only proof of non-admission restores them.
Uncertain acknowledgements never retry. Failed saves restore the in-memory
state before any dispatch. Dismissals persist lazily and join a running
steer or the next real user message; they never start a turn of their own.
Only live questions and queued dismissal notes persist; terminal records
are published and retired. The registry writes no logs and has no export
path, mode change or approval grant.

Host and runtime share the filesystem adapter: private data directory,
0700 directory/0600 file on POSIX, strict zod session envelope, validated
file names, refusal of linked directories/files, exclusive temporary
creation, sync and atomic rename. Corrupt storage rejects with fixed text;
JSON parser errors cannot quote question content into an exception. Windows
uses the existing private data directory's ACL; POSIX permission drills were
run on Kubuntu. No dependency or gate was added or weakened.

## Controller delivery and session deletion

One registry belongs to the shared AgentSession handle. Attaching or
reattaching a surface replays its snapshot; changes reach every attached
surface. Strict storage takes an explicit field whitelist from the parsed
question event, so the event's type/replay flags cannot enter the file.

Late answers use the established submit path: running steer, one fresh turn
only after proven refusal, or an idle turn with the localized display text.
The current session, auth, restart epoch, autosave and checkpoint guards
apply. No mode, approval or grant is changed. Errors on the new paths show
fixed UI text and log no question content. Legacy waiting answers retain
their user-visible error detail, without logging it. A failed registry
attachment drops its partial session and admits a later retry.

Deletion and retention remove the question store before the session file;
a cleanup failure preserves the session, including its History visibility.
The same store must be bound at backend construction (handoff above).
