# M36 certification — rewind finds a hunk that only moved (PLAN.md M36, D31)

Recorded 2026-09-24.

## The change

`revertHunks` (`src/core/patchApply.ts`) looks for each hunk's "new" side
(its context lines and the lines the edit added):

1. **The first look:** where the edit recorded it, shifted by how far the
   previous hunk moved.
2. **If it is not there:** anywhere after the previous hunk. It is taken
   only when it occurs exactly once, compared line for line, character for
   character.
3. **Otherwise refused, with the reason:**
   - "hunk N no longer matches the file at line L, or anywhere else"
   - "hunk N matches K places in the file, so which one is not certain"

Out-of-order hunks are still refused as overlapping. A hunk with no lines
on its new side (a deletion with no context) is placed only where
recorded, since there is nothing to find.

The D27 test that pinned the old rule ("refuses to put deleted lines back
where the file has moved on") had the user add a line _above_ a deletion
whose three context lines each side were intact. It now expects the
deleted line back between its own context, with the user's line kept, and
gains the case the rule is really about: a context line the user changed
is refused.

## Tests

`test/unit/patchApply.test.ts`:

- moved down (lines added above, and kept);
- moved up (lines removed above);
- two hunks with the move carried and lines added between them kept;
- a repeated block placed by the carried move;
- refused when the same lines occur in two places;
- refused when the hunk's own lines changed.

`test/unit/modelApiTools.test.ts`: the D27 case, as above.
