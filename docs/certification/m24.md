## Findings recorded during the milestone

- `ToolIo.listDirectory` lost its last caller when the context loaders moved
  to `ContextIo` (m24-context.md) and was removed.
- One full gate run failed in teardown only: removing `toolIo.test.ts`'s
  temporary folder raised `EBUSY` with all 1,164 tests green. A probe
  (`scratchpad/probe-taskkill-race.mjs`: the tree-kill test's command, killed
  at every 50 ms from 100 ms to 1.5 s, then the folder removed) found no
  process escaping `taskkill /T`, and the hold was taken for a transient one.
  The suites that use real temporary folders now remove them through
  `removeFolder` (`test/unit/helpers/temporaryFolders.ts`), which retries
  five times, 200 ms apart and growing, and still fails on a folder held
  longer. **Superseded:** that conclusion was wrong. The 0.6.0 gate failed
  the same way with the retries in place, and a logged run showed a child
  started during the kill outliving it (the idle probe never hit the
  window). Fixed and certified as M27 ([m27.md](m27.md)).

## The review of PR #11

The Codex review raised two threads.

- **Atomic replacement loses the target's identity (P1): real, fixed.** A
  rename replaces the directory entry: a symbolic link inside the workspace
  became a regular file while the file it led to kept the old content, and
  on POSIX a script lost its executable bits. `writeFileAtomically` now
  resolves an existing target (`realpath`), writes the temporary file beside
  the real file, carries its permission bits (`chmod` before the rename) and
  refuses a read-only file at once (`access(W_OK)`: EACCES, or EPERM on
  Windows, with no busy-rename retries), as a write in place would. What a
  new inode cannot carry is recorded in the module and in D27: a hard link's
  other names keep the old content, the owner is the writer, Windows' hidden
  and system attributes are not copied.
- **Nested folders' paths computed from the folder itself (P2): not a
  defect.** `workspace.asRelativePath` passes `resolveParent: true` to
  `getWorkspaceFolder`, which moves a folder's own URI to its parent before
  the lookup (microsoft/vscode `src/vs/workbench/api/common/extHostWorkspace.ts`,
  fetched 2026-09-23), so a nested folder's own URI is relative to the
  folder around it, as `FolderLookup.relativePath` documents and the
  `workspaceRoot` tests model; it is never the empty string.

| Break                                                           | Caught by                                                                     |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| U the link itself replaced (renamed over the textual path)      | `fsAtomic.test.ts` "replaces the file a link leads to, never the link"        |
