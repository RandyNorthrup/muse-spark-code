### Recovery, retention and activation

- New daily files are `<workspace ledger>/<window instance>/team-<day>.jsonl`.
  One window appends and syncs only its own files. All owned partitions and
  legacy shared files can be read; legacy/foreign files are never rewritten
  or pruned by this instance. Lane K remains responsible for authorized
  cleanup of another instance's material after takeover, and for copies,
  refs, process retirement and exclusive-resource leases.
- A fresh, stale or missing hint authorizes nothing. Foreign interruption
  needs `{ kind: 'userTakeover', ownerId }`; the target id must match. The
  recovering window writes its own snapshot and records that user decision.
  A source snapshot cannot overwrite the takeover in history or meters.
  No same-window stable identity is presumed before lane K's capture.
- Every state acknowledgement waits for `FileHandle.sync()`. A failed
  publication retains its batches. A newline separates a crashed partial
  tail from subsequent rows. Usage batches are grouped by their own day.
- Retention skips active owned tasks and foreign records. Deterministic
  terminal rollups preserve each delegation's reset boundary; reset markers
  survive retention. `sourceTaskId` coalesces a rollup with its original
  snapshot after a crash before removal, and cumulative versions count once.
- Git exclusion and landing are lanes I/K and M96c Q, not changed here.
  No ledger recovery operation commits, moves or deletes a working copy/ref.
  A quarantined replacement still uses ordinary admission while the old
  attempt's slots remain counted; the caller must acquire all exclusive
  resources before starting it.
- `teamActivationGraph.test.ts` bundles the extension activation entry,
  Model API entry and ACP entry without writing output. Their complete
  esbuild input graphs contain **zero `src/core/team/` or `src/host/team/`
  modules**. The paid tests also prove zero activation confirmations and no
  team-worker feature for single-model/unavailable setups. Full golden
