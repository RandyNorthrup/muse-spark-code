todo-summary follow-up and the memory flush stay unbuilt and off: no code,

## What was built

- `/handoff`, optionally with a goal after it (`/handoff Ship it Friday`),
  as a palette row, a slash-menu entry (Enter and Tab ready `/handoff `
  for the goal) and a prompt parse (`src/shared/handoff.ts`).
- The host asks the model, as the user's own turn in the current
  conversation, for a distilled brief (goal, decisions, files touched,
  open work, todo list). The request turn's card stays in the transcript.
- The brief opens in a dialog before anything starts: review it, edit it,
  then **Start new conversation**, or **Cancel** and nothing starts.
- Starting seeds the new conversation through M79's `startFromBrief`
  path (`ConversationBrief`, one path, no duplicate): the brief alone is
  the first message, the goal and the open items travel in the model's
  note, and the open items (never completed or dropped ones) become the
  todo list before the first request. The old conversation stays in
  History.
- Untrusted content stays labelled (D49): the request makes the model
  mark tool-output, fetched-page and imported-file content `[untrusted]`
  in the brief, and the seeded note tells the new conversation what the
  label means.
- Model API backend only: on Muse Code the command says it is unavailable
  there. Side chats are refused; one handoff runs at a time; a `/handoff`
  while a reply runs is refused ("Wait for the reply to finish, or stop
  it, first."; nothing waits or queues); an oversized (over 256 KB) or
  empty brief is refused with the reason.
- Sixteen UI strings in the English table and all fourteen `l10n/ui.*.json`
  tables with real translations (`/handoff` itself stays English in
  `untranslated.json`, as `/compact` does); six English-only model texts
  (`MODEL_TEXT`).

## RV74 review fixes (2026-10-01)

The independent review of `41ed14bf` (RV74) found ten things; each fix
below is its own commit, with its test and its red drill (the RV74 drill
table under Red drills).

- **Finding 1, the start mode (P2, security; the lead's decision).** The
  brief is model-written, yet every handoff started approved, in the
  starting mode (Auto or Bypass where allowed), and a handoff from Plan
  mode left Plan. Now `handoffBrief` counts it approved only when the
  dialog showed the user all of it before Start: the brief in full (the
  dialog's text box holds it as the model will read it) and the open items
  it seeds, which `handoffReady` now carries (`todos`) and the dialog lists
  under Tasks, with no control or format character the dialog does not
  show (`hasUnshownCharacters`, as for a plan). Otherwise it starts in the
  asking mode (`untrustedBriefMode`, as a plan picked from Plans… does) and
  the panel says so (`handoffUnshownMode`, translated in all fourteen
  tables). A handoff from Plan mode stays in Plan
  (`ConversationBrief.shouldKeepPlanMode`, read by `briefStartMode`). Tests:
  "starts a brief the dialog showed whole in the starting mode, and one
  hiding a character in a mode that asks (D49)" (Auto kept; a zero-width
  space in the brief and a direction override in an open item each start
  in Manual with the notice), "keeps a handoff from Plan mode in Plan,
  whatever the starting mode", the open items in `handoffReady` (the
  seeding test), and the dialog's Tasks list (`handoffDialog.test.tsx`).
- **Finding 3, a rebuilt panel (P3).** The dialog lives only in the
  webview's state, so a rebuilt webview (Developer: Reload Webviews, the
  view moved) lost it while the host kept the waiting brief, and every
  later `/handoff` answered "already running" until a new conversation.
  Now `surfaceReady` posts the waiting brief's `handoffReady` again
  (`postHandoffReady`, shared with the first post), last, after the
  surface state that may clear a stale restored conversation; nothing is
  posted while the distillation turn still runs or once nothing waits.
  Test: "brings a waiting brief back to a rebuilt panel, so a later
  handoff is never stuck busy".
- **Finding 4, the typed goal (P3).** The panel cleared the composer as it
  posted `requestHandoff`, so a refused handoff (Muse Code, a running
  reply, a side chat, one already running) lost the typed goal. Now the
  host answers every request with `handoffCommandResult` (`requestHandoff`
  wraps `distilHandoff`, which is true once the distillation turn was
  accepted), and the panel keeps `/handoff …` until that answer, as for
  `/goal`: `pendingHandoffCommand` holds the request and the draft's
  revision, an accepted request clears the draft only if it was not edited
  meanwhile, a refused one leaves it, and a second Enter before the answer
  sends nothing. Tests: "posts the command with its goal, sending nothing,
  and clears the draft only once the host takes it", "keeps a refused
  handoff in the composer, its goal not lost, ready to send again", "keeps
  a draft edited while the host answered, even when it takes the command"
  (`handoffDialog.test.tsx`), and the host's results in the distillation,
  refusal, running-reply and busy tests.
- **Finding 5, an English reason (P3, l10n).** A distillation turn that
  left no reply said "Could not prepare the handoff: the distillation turn
  left no reply" with the reason in English in every language. The reason
  is now `UI_TEXT.handoffNoBrief` ("The model returned no brief."),
  translated in all fourteen tables (`check:l10n`: 0 problems). Test: the
  empty-brief case of "refuses a confirm after the conversation changed,
  and a brief that is too large or empty" now requires the whole notice,
  `handoffFailed: handoffNoBrief`.
- **Finding 6, one refusal said twice (P3).** When an ordinary turn
  started while the handoff's request was being sent, `send` called
  `canDistilHandoff`, which posted the "wait for the reply" notice, then
  threw the same words, which failed the request's card with them: the
  refusal showed twice. `send` now checks `activeTurnId` itself (the
  handoff's currency is checked on the line before), so the refusal is
  said once, as the reason on the request's failed card. Test: "says
  once, on the request's card, that a turn started during its send
  refused it" (a host lookup held after the card is up, an ordinary turn
  started meanwhile: the words appear once, and the request is answered
  refused).
- **Finding 7, release notes (P3, docs).** `CHANGELOG.md` listed "Handoff
  to a new conversation" under `[Unreleased]` and again under the released
  `[0.10.0] ### Added`; the 0.10.0 entry is removed, so the changelog's
  only change against `8e9d3a1e` is the `[Unreleased]` entry. `README.md`
  had "Plans as files" (a duplicate of the 0.10.0 bullet) and "Handoff"
  under "Earlier in 0.9.0"; both are removed. The History above now says
  what the port actually left.
- **Finding 8, "a running turn is waited for" (P3, docs).** Nothing waits:
  a `/handoff` while a reply runs is refused with "Wait for the reply to
  finish, or stop it, first." and nothing is queued. CHANGELOG, PLAN and
  this record now say so, and the test once named "waits for a running
  turn before distilling" is "refuses a handoff while a reply runs,
  queuing nothing, and takes one once it is done", with a check that no
  request card appeared when the reply finished.
