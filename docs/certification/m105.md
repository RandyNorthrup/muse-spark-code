### Design

- **One production media service per session.** `createModelApiHost`
  (`src/host/backend/modelApiEntry.ts:148`) loads
  `dist/productionMedia.js` through the deferred cohort and builds one
  `ReplayMedia` per session through `createProductionMediaReplay`. It is
  assembled from the per-account upload ledger under the shared
  `core/fileLock` mutex, the calibrated estimator merged under that lock,
  the captured codec and capabilities, and the Files transport that every
  provider wrapper carries. VS Code (`extension.ts`), the CLI/ACP runtime
  (`runtime/backends.ts`, through `ModelApiBackendManager`) and exec all reach
  this one factory.
- **One admission path.** `ReplayMedia.price` (`src/core/media/replayMedia.ts:242`)
  is the only pricing function. `budgetParts` (`:309`) and `reserveRequest`
  (through `requestMedia`, `:256`) price every media item a request carries:
  - upload records, which are host-issued attachments and adopted tool
    uploads;
  - inline records, which are images and PDFs whose identity
    `inlineVisualIdentity` (`:101`) reads from the data URL on the wire.

  Attachments (`content` → `admitInline`, `:457` → `:343`) and tool reads
  (`admitVisual`, `ModelApiHost.ts:8503`, `tools.ts:1382`) are admitted
  through that same function before anything queues. Inline parts restored
  with a session are priced on their next request. The always-undefined
  attachment resolver and the tool-read-only pricing (`vetVisual`,
  `priceInlineVisual`, `VisibleFile.priced`) are deleted. The resolver is now
  optional and absent until lane V.

- **Inline is never upload.** Inline records live in their own `WeakMap`
  (`inlineVisuals`), and `inlineVisual` (`:213`) refuses any part already held
  as an upload record. Nothing inline enters `parts`, so `delivered`,
  `prepare`, `project` and `snapshot` never treat a priced image as a file to
  reopen.
- **Capped-only refusal.** `ModelApiHost.isMediaCapped` (`:3808`) is true for
  an M82 session cap or a D95.3 scheduled run. It reaches the service per
  request through `createMediaReplay(sessionId, { isCapped })` (`:2788`).
  - Capped with an unknown rate: the honest refusal.
  - Uncapped: the seeded bound where one exists, otherwise the part's own
    byte count.
  - A model with no captured media record (standard 1.3, other vendors)
    keeps the established inline path.
  - A no-media request never consults capabilities.
- **Transcription is absent in production, by lead decision.** No audio port
  is installed. RVMEDIAW2 2 corrects the earlier "no dormant port" claim: the
  host's `prepareAudioMessage` option and its turn branch survived, and the
  factory's `hostDeps` spread accepted a caller's callback. Since lane V's
  first commit the factory drops any caller-supplied `prepareAudioMessage`
  (`modelApiEntry.ts`, typed away in `ModelApiBundleDeps.host`), so the only
  audio path is the one the bundle binds itself. The adapter defects are fixed:
  - a video keeps its visual part beside the transcript
    (`audioMessagePreparation.ts:112`);
  - a converted WAV is disposed on every path from its creation
    (`transcribeBatchHttp.ts:253`).

  Lane V's scope is the five missing production seams:
  1. attach-port tokens with a part-to-source registry: no audio/video
     `TurnPart`, and the attach port refuses video/audio at `modalityGate`
     before `bind`;
  2. the transcription POST transport: `requestFile` allows only `/files`
     routes and throws on non-OK;
  3. a trusted converter binding: `locateMediaConverter()` without
     `trustedPath` always refuses;
  4. paid consent and reserve adapters for both hosts;
  5. an ACP and exec media port, with ACP able to turn voice on.

- **Bundles.** The new output is `dist/productionMedia.js`
  (`deferredBundles.mjs:150`, `:915`; `build.mjs:1187`, `:1302`; cap

### Seam 3 core — trusted converter binding

**Design (lead decisions).**

- **One POSIX verifier.** `src/runtime/trustedPath.ts` is M104's REDM104L3
  file (blob `9fb91c4a`) verbatim, plus an additive executable-file mode,
  `verifyTrustedExecutable`:
  - it resolves the real path first;
  - every ancestor of the canonical path passes the same StrictModes walk;
  - the target must be a regular file owned by root or the user, with no
    group or other write, and executable;
  - the open handle must still be the pathname (no swap).

  `posixTrustedPathVerifier` exposes it through the shared
  `TrustedPathVerifier` port (`trustedPathPort.ts`), whose
  `{ ok, path } | { refused, component, reason }` contract is unchanged.

- **Windows.** `converterTrustedPath` (`src/runtime/converterTrust.ts`)
  resolves the canonical target first, then runs the existing owner, ACL and
  reparse verifier (`windowsTrustedPath.ts`) on it. A winget link, or a
  profile folder that is a junction or lives on another drive, is judged by
  what it resolves to. PowerShell is launched from `%SystemRoot%`, never
  found on `PATH`.
- **Where converters come from** (`locateMediaConverter`, `convert.ts`):
  - A configured path, when given, is the only candidate. If it fails, the
    refusal names the reason (`converterConfiguredRefused`) and there is no
    fallback to discovery.
  - Otherwise, documented installs:
    - Linux: `/usr/bin`, `/usr/local/bin`.
    - macOS: avconvert, `/opt/homebrew/bin`, `/usr/local/bin`,
      `/opt/local/bin`.
    - Windows: `%ProgramFiles%\ffmpeg\bin` and winget's
      `%LOCALAPPDATA%\Microsoft\WinGet\Links`, read from the environment.
      There is no drive literal, and no guessed fallback when the variable
      is absent.
  - `PATH` is never consulted.
  - Launcher shims (Chocolatey, Scoop, `/snap`) are refused at their
    canonical path, because they launch a second binary that was never
    verified.
  - A converter found under a shared-writable folder (Intel Homebrew's
    `/usr/local/bin`) names the fix (`converterSharedFolder`).
- **The verified canonical path is what runs.** The version probe launches
  it. The recheck immediately before encoding must verify the same canonical
  path again, or the conversion refuses.
- **Memory watch.** Encoding runs under either a bounded RSS sampler or a
  kernel-enforced cap (`memoryLimitedRun`, the Windows job object that
  MEDIAVB builds). A cap hit is reported as "memory cap". With neither
  available (off Linux), conversion refuses before launch.
- **Reaped-PID fix.** Node reaps the child before `exit`. From then on an RSS
  sample proves nothing, so:
  - a sample that loses the race with the exit no longer fails the
    conversion;
  - after `close`, only the output's type and size cap decide;
  - a live child's failed sample still refuses.
