# M27 certification — the tree kill's orphans (PLAN.md D25, M27)

Recorded 2026-09-23 on Windows 11 (Node 24.20.0).

## How it was found

The 0.6.0 release gate failed three times in a row in `toolIo.test.ts`'s
teardown: removing its temporary folder raised `EBUSY` while every test
passed. Retrying the removal for three seconds (M24) did not help, so the
hold was not transient. A run with the tree kill and the shell runner
logging to a file, and the teardown listing the processes created in the
last minutes, showed it:

- the timed-out shell (`Start-Process … ping …; Start-Sleep 30`) was
  spawned at 00:11:50.837, its 500 ms timeout started `taskkill /T /F`;
- `taskkill` reported killing the console host and the shell (00:11:52.090)
  and nothing else;
- a `PING.EXE` whose parent was that shell, created at 00:11:51.928 (during
  the kill), was still running at the teardown, its working directory the
  test folder.

One orphan of an earlier run (a ping from the same test, 16:18) was still
there at 17:00, suspended: PowerShell had been killed between creating it
and letting it run. It was a test process and was ended by hand.

Idle, the same kill never missed (`scratchpad/probe-taskkill-race.mjs`, 29
kill delays from 100 ms to 1.5 s, with and without CPU load, and
`scratchpad/probe-spawn-loop.mjs`, a shell starting pings in a loop); the
parallel coverage run hit it on every kill.

## The first fix, and the review of PR #12

The first commit swept the process table for the dead shell's orphans.
The Codex review raised three threads, all real:

- **A launcher's child is unreachable.** A process the shell started
  during the kill that itself starts a child and exits leaves that child
  with no parent link to the shell. Only a job object holds such a child.
  Replaced: job objects are now the primary path (below).
- **`PSModulePath` under two spellings.** A PowerShell 7 environment's
  upper-case `PSMODULEPATH` stayed beside the new `PSModulePath`, and
  Windows hands a child the first it sorts, so Windows PowerShell could
  load 7.x modules and fail. Fixed with `setEnvironmentVariable`, which
  removes every other spelling.
- **An id reused between the look and the kill.** The sweep passed a bare
  id to `taskkill`. Each kill now runs in the PowerShell that checks the
  process's creation time against the one the table showed, microseconds
  earlier.

The probes behind the job design (`scratchpad/probe-job.mjs`,
`probe-job2.mjs`): a PowerShell that Node spawned can put itself in a new
job (nested under libuv's), and ending the job ended both a
`Start-Process` child and a `cmd /c start /b` launcher's orphaned
grandchild; joining costs nothing measurable (median 271 ms against 281 ms
without); kill-on-close was ruled out because it also killed background
processes at a normal end, and PowerShell's `Exiting` event did not
release it.

## Built

- `shellJob.ts`: a C# type (`CreateJobObject`, `AssignProcessToJobObject`,
  `OpenJobObject`, `TerminateJobObject`) compiled once per machine by
  `Add-Type` into the extension's storage, named by the source's digest
  (unique temporary names, so two windows never share one; earlier
  versions removed), then self-tested by joining a job as a command does.
  Where that fails (Constrained Language Mode forbids `Add-Type`) the log
  says so and there is no job.
- Each Windows command starts by joining a job named for it (a swallowed
  failure means no job, found at the kill). The job has no limits and no
  kill-on-close: a normal end leaves background processes running.
- `killTree` (`processTree.ts`) terminates the command's job, which ends
  everything in it at once; without a job, or when the job cannot be
  terminated, it falls back to `taskkill /T /F` and the sweep: the process
  table read by parent id, a child counted only if created after the shell
  started and before its parent died, killed after the identity check, one
  generation per round, five rounds at most. What it cannot do, it logs.
- `runCommand` (`toolIo.ts`) answers a killed command once the kill is
  done.
