### Finding 3: confirm application independently of pending recovery

The controller retains `dirty` for uncertain dispatch/restoration, but records
`applied` only after exact OS readback. Irreversible recovery requires both
that prior confirmation and fresh registered membership/policy proof. It
never promotes an unconfirmed write, even when a later read sees its target.
A new irreversible dispatch first reads the current policy; an uncertain
previous write is retried only if that read proves the original state.

Before the fix, the complete controller suite failed five new regressions
(three failed-write modes, stale recovery policy and unknown prior state):
**5 failed / 18 passed**, exit 1. After the fix and the additional regression
for a write that changed the OS but returned null: **24 passed**, exit 0.
The controller/Linux/macOS run passed **55 tests**, including both real
Kubuntu nice/ionice and delegated CPU-weight/memory.high probes.

Each drill ran the complete controller file, exited 1 with assertion failures,
and restored the source byte-exact in `finally`. Receipts are under ignored
`temp/fixm107a-confirmation-drills.json` and `temp/fixm107a-drill-*.log`.

| Guard broken                                          | Named failing regression                                                              |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Confirmation required before irreversible recovery    | never promotes an unconfirmed irreversible write even if a later read sees the target |
