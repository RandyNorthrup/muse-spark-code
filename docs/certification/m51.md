## Source contract

- [Muse Code SDK 1.3.0 settings-level hooks](https://meta-models.github.io/muse-code-sdk/next/guides/extend/hooks/): managed, user, project order; project trust; JSON config; matcher and handler rules; shell execution and cleared environment. Its examples include observed stdin frames.
- [Muse Code SDK 1.3.0 hook events and payloads](https://meta-models.github.io/muse-code-sdk/next/guides/plugins/reference/hook-events/): 17 events, common and event-specific stdin, closed output schema, exit codes, 256 KiB stdin and independent 16 KiB output caps.

## Implemented in the isolated M51 worktree

- Machine-scoped `museSpark.modelApiHooks`, off by default. A new Model API session loads managed, user and trusted-project sources in that order.
- Config validation warns and skips unsupported or malformed entries. All 17 documented event names have dispatch points at the Model API backend's supported operations; `SessionEnd` runs on orderly host shutdown within a 10 second total budget, and `Notification` starts after an approval has waited six seconds. Bounded regex matchers, asynchronous observation handlers and three levels of `onFailure` are implemented. Hook answers can deny prompts/tools, request ordinary approval, rewrite tool inputs before normal validation and approval, add model context or keep a stopped turn working within a continuation cap. A `PermissionRequest` hook may allow an ordinary approval; paid calls, protected writes and a `PreToolUse` forced approval still require the user's card. This follows the SDK's documented `decision.behavior` semantics with the project's stricter D24/D30 guards.
- `PreLLMCall` runs before each logical Model API response stream and compaction request. Its captured `decision: "block"` refuses before HTTPS. `PostLLMCall` runs after a completed response with the captured success fields. The local `provider` is `meta`, not a claim about Muse Code's provider id. Hook stdin contains bounded text summaries: last 32 messages, four text parts per message, 256 characters per part, 50 tools with 256-character descriptions, and 1,024 characters of output preview. Inline media bytes, full tool outputs and the API key are excluded. A foreground post-call block stops with a failed turn before returned tools or another request; returned function calls receive failure outputs for valid replay. Its continuation behavior in Muse Code remains uncaptured. Compaction keeps prior history on a post-call block while counting the completed response's usage. A whole-stream retry has a fresh PreLLMCall and a PostLLMCall only after success; automatic HTTP retries inside one stream share the logical hook boundary.
- Commands use JSON stdin and a narrow environment without provider keys. Relative PATH entries are removed. Managed hooks receive only valid `managed_hooks_env_vars` grants; duplicate and provider credential names are rejected. Timeout, 16 KiB per-stream output cap, process-tree cancellation and Stop cancellation use the host's existing process runner. A global four-command cap prevents many sessions from spawning unbounded hook processes.
- `test/unit/modelApiHooks.test.ts`, `modelApiHost.test.ts`, `modelApiBackendManager.test.ts`, `toolIo.test.ts` and `settings.test.ts` cover the bounded runtime. The manager case independently asserts the machine opt-in prevents a `SessionStart` command from running. A real `runHook` process test sends JSON over stdin and reads its answer; it uses no Model API key or model call.

## Hosted Windows hook start delay, 2026-10-01

**Symptom.** On GitHub's `windows-latest` runner (image
`windows-2025-vs2026` 20260925.250.1), `toolIo.test.ts` "delivers hook JSON
on stdin without placing it in the command line (M51)" sometimes ran into
its 60 s budget with `"exitCode":1,"isTimedOut":true,"stdout":"","stderr":""`
(CI run 36885000890 attempt 1, Release run 36947244221 attempt 1), and
`toolIoCommandAdmission.test.ts` "runs a real unchanged local shell command
with the final callback" ran into vitest's 60 s timeout once (36885000890
attempt 1). Passing runs were slow too. Across both attempts of those two
runs and diagnostic run 36951787376 below, the hook test took 17.9 to
48.8 s and the admission test 17.2 to 28.8 s; across the CI and Release
attempts, `checkpointShellProof.test.ts` "still records native uncertainty
after a real command that launched and exited normally" took 22.9 to
38.9 s. "captures stderr and the exit code of a failing command", a shell
test in the hook test's file that hands the shell tool the host's whole
environment, took 331 to 371 ms in the three of those logs that list it.

**Cause.** Windows PowerShell finds a cmdlet that is not yet loaded, such
as `Add-Type` or `New-Object` (module `Microsoft.PowerShell.Utility`), by
module auto-loading. Without a usable module analysis cache, auto-loading
analyses every module on the module path first. The runner image keeps its
prebuilt cache at `C:\PSModuleAnalysisCachePath\ModuleAnalysisCache` and
reaches it only through the machine variable `PSModuleAnalysisCachePath`
(the per-user default folder held no cache). Its module path holds
AWSPowerShell, 40 `Microsoft.Graph` modules, SqlServer and more. A hook
gets the narrow hook environment, which does not carry that variable, and
the wrapper's first statement, the job join, began with `Add-Type`. The two tests with a `PATH`-only environment lost the
variable the same way and ran `Write-Output`. Evidence from the temporary
diagnostic branch `diag/hook-stdin`:

- Run 36951787376 (the two files five times on each of four runners, 20
  runs) reproduced one 60 s timeout. Timestamps written from inside the
  wrapper showed its first statement at 193 ms and the job join finished at
  22,962 ms with 22,859 ms of CPU, one thread `Running`. The timed-out run
  was still inside the join when killed (12 s snapshot: 5.7 s of CPU, 5.3 s
  of it in user mode, the fresh runner 45 % busy). Its hook never started,
  and stdin was never the problem: the payload's write end is flushed when
  the reader takes it, which happened at 23,016 ms in the slow passing run
  and only at the kill (60,385 ms) in the timed-out one.
- Run 36954845386 measured the old wrapper statements in the hook
  environment at 22,295 to 28,901 ms (22.6 to 23.0 s of the process's
  CPU). Adding back only `PSModuleAnalysisCachePath` made them 214 to
  233 ms. The .NET-only statements took 20 to 22 ms without it. With module auto-loading off, the
  old statements failed with "The term 'New-Object' is not recognized"; the
  new ones ran cleanly.

**Fix.** The job join loads the helper with
`[void][Reflection.Assembly]::LoadFrom(...)`, and the UTF-8 preamble
builds its encoding with `[Text.UTF8Encoding]::new($false)`, so the
statements the wrapper runs before a hook or command name no command and
need no module discovery. The hook environment is unchanged. The admission
and checkpoint shell tests now hand the shell tool the host's whole
environment, as the extension does; the `PATH`-only one was not a product
environment.

The helper's first-use self-test and a stopped command's job termination
load it the same way (`loadJobAssembly` in `processTree.ts`), so the
self-test proves the very load each command makes. Neither ran in a hook's
environment, so neither caused the timeout. The load is the one `Add-Type
-Path` made: in one Windows PowerShell 5.1 session on the Windows host,
`[Reflection.Assembly]::LoadFrom` after `Add-Type -Path` on the same DLL
returned the same assembly object from the same location. A missing file
throws inside `try` either way: `Add-Type` a `ParameterBindingException`,
`LoadFrom` a `MethodInvocationException` around `FileNotFoundException`.
The join swallows it, as before, and the kill logs it. The self-test did
not, before or after this change: a failing .NET call (or `Add-Type`) ends
only its own statement, so the script still printed `joined` and exited 0,
and a present but unloadable assembly was accepted (independent review
RV68, reproduced with both versions against a missing DLL on Windows
PowerShell 5.1). The self-test now runs inside `try { … } catch { exit 1 }`,
so a load or join that fails never answers `joined`, and the extension says
job objects are unavailable and uses taskkill and the orphan sweep.
Constrained Language Mode refuses the .NET load as it refused `Add-Type`
("Method invocation is supported only on core types in this language
mode", on the same host), so the self-test fails there and commands run
without a job.

Cmdlets left in the PowerShell the extension writes, none of them in a
command's or hook's wrapper, each run with the extension host's whole
environment:

- the helpers' compile (`Add-Type -OutputAssembly`, once per source);
- the orphan sweep, which runs only when a command has no job
  (`Get-CimInstance`, `ForEach-Object`, `Get-Process`, `Stop-Process`);
- the sandbox setup's UAC relaunch (`Start-Process`).
