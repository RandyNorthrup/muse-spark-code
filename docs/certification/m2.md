## Findings recorded during the milestone

- `Connection.onNotification` in `@muse-code/sdk` replaces its single handler,
  so the extension uses the raw connection and its own dispatcher instead of
  composing `MuseClient`.
- The SDK's `Connection.command` verifies that a `turn/start` ack echoes the
  minted `commandId`; the in-memory fake server must echo it (a fake that did
  not was the only unit-test failure during development).
- `muse serve` has no `--provider` flag; the credential-free echo provider is
  TUI/`exec` only, so every live check needs a signed-in CLI.
- Without a credential the host still answers `session/start`; the first
  `turn/completed` is `terminal: failed`, `error.kind: authRequired`, which the
  controller maps to the signed-out gate.
- `Promise.withResolvers` (required by `unicorn/prefer-promise-with-resolvers`)
  needed the TypeScript `ES2024` lib; the base target was raised accordingly.

## Security

- The API key is validated (`LLM|<id>|<secret>`) before it is stored, lives
  only in VS Code secret storage, and reaches the CLI only through the child
  environment. The logger redacts it in every path that could print it.
- `muse login` / `muse logout` run in a visible terminal; the extension never
  handles the browser token itself.
- `approvalMode: denyUnmatched` until M4: the agent cannot write files or run
  commands through this extension yet.
