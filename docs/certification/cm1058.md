Rules as built (round 4 refines round 3's three rules):

- USE BEATS INTENT (P1-1) — every ledger entry carries a use generation
  that rises on each session (re)use (`ensure` reuse, `syncSession`
  re-attach). A delete intent records the generation it saw; the delete
  runs only when the generation is unchanged under the lock at the moment
  of the remote call, otherwise the intent is dropped.
- PINS ARE COUNTED REFERENCES WITH AN OWNER (P2-1/P2-2) — each request
  that carries a file holds one row (owner = process birth plus request
  id). The file unpins only when the count reaches zero; references of a
  process proven gone (ESRCH on signal 0, any doubt keeps the row) release
  at the start of a pin run and of a listing. A failing unpin is kept for
  the next end and never throws out of the turn's finally.
- UPLOAD AND PIN IN ONE LOCK SCOPE (P2-3) — `ensureAndPin` does both under
  one lock hold; no stale save lands between them.
- THE CANCEL SIGNAL REACHES EVERY CLEANUP (P2-4/P2-5) — every listing
  carries the signal, including the post-delete listings; a cancel before
  dispatch drops an intent this call recorded, so no later listing runs a
  cancelled delete (an abort during/after dispatch keeps the intent: the
  remote call was already sent).
- ONE FAILING ENTRY NEVER BREAKS A LISTING (P2-6) — per-entry attempt
  count and backoff (30 s base, doubling to a 10 min cap); listings skip
  entries inside their backoff and isolate failures. The release scope
  still reports a failing delete honestly to its caller.
- THE LAST-ACCOUNT POINTER CHANGES ONLY FOR THE CURRENT ACCOUNT (P2-7) —
  opens for old accounts never move it; a fresh factory per call does not
  rewrite an unchanged pointer.
