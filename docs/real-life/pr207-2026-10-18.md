## What "automatic delivery is still off" means in this code

`SCHEDULE_EDITOR_DELIVERY_CERTIFICATION.isReady` is `false`
(`src/shared/constants.ts:4424`). With it off:

- The runtime schedule binding loads without delivery ports
  (`src/runtime/schedules/binding.ts`), so the engine host reports
  unavailable (`src/runtime/schedules/engine.ts:141`) and every dispatch
  refuses: `run-now`/`fire` with "This process no longer holds the
  workspace.", `run-due` earlier with the wake-launcher refusal (below).
- Palette commands, ACP `/schedule`, the extension schedule activity and the
  v1 migration stay gated; compact CLI help and the reference omit the
  `schedule` routes (C-X-1 dormant-hidden, pinned by `cx1r2Truth`).
- Management (add/list/remove/pause/resume/timeline) works from the terminal.

Nothing in 0.19.0 was found to say anything untrue about this: the VS Code
setting text ("Schedule management and scheduled prompt execution are
unavailable.") matches the editor surface it documents — execution refuses
everywhere, including the terminal — and the roadmap still says
"Scheduled prompts v2 is in progress."

## The "fire for real" step: blocked by design, 0 model calls

Letting a schedule fire for real needs delivery, which is uncertified and
off (see above): `run-now`/`fire` refuse at the host, `run-due` refuses at
the wake check. Flipping the switch needs the PLAN receipts (cross-platform
admission, native modal decline, independent reviews, live check) and is
explicitly reserved to the lead — this lane does not flip it, so no model
call was spent and none is owed: 0/40 calls, $0.00/$2.00. The terminal
fire path itself is proven up to the refusal boundary (steps 9–12).
